# Windows 版上机验证清单

> **归属** windows-port。配套文档：[移植方案.md](移植方案.md)；脚本：[探针脚本/](探针脚本/)（**脚本未经运行**，见该目录的 README）。
>
> 移植方案是在一台 Mac 上写的，里面所有标着【推断】的关键结论、以及官方文档没写明的地方，都在这里列成了待验证的条目。
> 每一条写明：**怎么验证、预期结果、如果不成立的备选方案**。
> **排序**：第一组决定方案的骨架站不站得住，**V01–V05 十分钟内能跑完**（每项的时间含操作）；第二组不用装东西，半小时左右；
> 第三组要准备环境，所以放在最后——但其中 **V17（技术选型）和 V18（未签名程序的拦截）对决策同样要紧**，有条件的话和第一组一起做。

## 怎么用这份清单

1. 找一台 Windows 10 或 11 的电脑（真机最好；虚拟机也行，但 V08、V10、V11 的结果会打折扣）。**不需要安装任何东西**就能做完第一、二组。
2. 桌面上请先准备：十来个图标（文件、文件夹、快捷方式都有，最好有一个 zip 压缩包），回收站图标显示着，关掉"自动排列图标"。
   再新建一个自己的空文件夹和一个文本文件，专门用来拖——**不要拿重要的东西做实验**。
3. 按 [探针脚本/README.md](探针脚本/README.md) 的办法逐个运行脚本，照下面每一条的"怎么验证"操作。
4. 把每个脚本的**全部输出**存下来（外加标了"截图"的几处），交给负责 Windows 版的人。
   脚本不输出文件名和窗口标题；截图里会有你的桌面，请先确认上面没有不想给人看的东西。

除了 05、06 两个脚本会新建并清理它们自己的临时文件，其余脚本只读：不移动图标、不改系统设置。
清单里有几步需要你自己动手切换系统设置（例如"显示桌面图标"），都标了"可选"或写明了要切回去；做不做由你定。

## 第一组

### V01 读得到图标

**要验证的结论**：经资源管理器的桌面视图接口，一个普通权限的外部程序能读出每个桌面图标的位置和种类、格子大小、图标大小、视图设置，并认出回收站（方案 §2.1、§2.3）。这是整个 Windows 版的地基。

**怎么验证**

```
powershell -NoProfile -STA -ExecutionPolicy Bypass -File .\01-read-icons.ps1
```

**预期结果**

- 不报错，几秒钟跑完。
- 「桌面视图」一节：视图窗口类名 `SHELLDLL_DefView`，列表窗口类名 `SysListView32`、可见 `True`，顶层窗口类名 `Progman` 或 `WorkerW`、归属 `explorer`。
- 「图标个数」和你在桌面上数出来的一样。
- 每个图标一行，位置都读到了（没有"读取失败"）；种类和实际相符（文件 / 文件夹 / 快捷方式 / 系统图标 / 回收站）。**zip 压缩包应当显示为"文件"**。
- 「回收站：找到了」。
- 「图标边长」和桌面右键 → 查看里选的档位相符（100% 缩放下：大 96、中 48、小 32）。
- 「视图标志」和「Shell 视图脚本对象的读数」两行里的标志值、图标边长一致。
- 文件、文件夹、快捷方式的修改时间是"有"；系统图标和回收站是"没有"或"读不到"。

顺便留意（不影响结论）：桌面背景是"Windows 聚焦"时多出来的"了解此图片"图标显示成什么种类；桌面同步到 OneDrive 的电脑上读数是否正常。

**如果不成立**

| 现象 | 备选方案 |
|---|---|
| 整条路线走不通（打不开桌面视图、读不到位置） | 先按探针 README 末尾的表排除脚本自己的毛病。确认是系统不允许之后，改走界面自动化（V15）。如果那条也不行，在"不读写别的进程内存"的硬约束下没有第三条路——停下来报告总览，由用户决定要不要放宽约束 |
| 位置读得到，种类或回收站认不对 | 换识别办法：回收站用文件夹对象的"比较两个项目是不是同一个"（方案 §2.3 备选）；zip 被认成文件夹就加上"带数据流的算文件"这条规则 |
| 不支持 `IFolderView2`，或两行读数不一致 | 标志和图标大小改从 Shell 视图的脚本对象读（脚本里已经演示了） |
| 修改时间经 Shell 读不到 | 见 V14 的备选 |

### V02 位置的含义与叠加窗口的基本表现

**要验证的结论**

1. `GetItemPosition` 给的是桌面列表窗口客户区里的坐标，换算成屏幕坐标后对得上（§2.1）。
2. 图标图像的矩形可以由"位置 + 图标边长 + 格子宽"推出来，两个候选公式里有一个是对的；文字矩形的估算大致框住名字（§2.2）。
3. 带分层 + 穿透样式的窗口，鼠标点得穿（§3.1）。
4. 沉到 Z 序最底的窗口，在桌面图标之上、普通窗口之下（§3.2）。

**怎么验证**

```
powershell -NoProfile -STA -ExecutionPolicy Bypass -File .\03-overlay.ps1
```

40 秒内依次做：

1. 看每个图标上的框。**截一张图**。
2. 在画着框的地方照常操作桌面：单击选中一个图标、在图标上点右键再按 Esc、在空白处拖出一个选框。
3. 把任意一个普通窗口拖到图标上面。
4. 看终端里每 2 秒一行的报告。

**预期结果**

- **红框、青框、绿框之一正好套住每个图标的图像**（偏差不超过两三个像素）。请记下是哪种颜色。缩放是 100% 时红框和青框重合；
  缩放不是 100% 时，如果青框套准而红框偏小，说明读到的图标边长是"按 100% 算的"，要乘以缩放。
- **橙框**（文字矩形的估算）大致框住图标下面的名字；蓝框是整个格子。
- 第 2 步的所有操作和没有这个窗口时完全一样；正在别处打字的话不受影响。
- 第 3 步：框被普通窗口盖住；任务栏照常在最上面。
- 终端：窗口样式里有 `LAYERED | TRANSPARENT | NOACTIVATE | TOOLWINDOW`；「叠加窗口在桌面窗口之上」；
  「图标 #0 中心处最上面：桌面图标层…」；「前台是」一项从来不是"本进程的窗口"。

**如果不成立**

| 现象 | 备选方案 |
|---|---|
| 两种框都没套准，但所有图标偏得一样多 | 把这个偏移记下来当常数用（macOS 版的图像矩形也是这样校准出来的）。换一种图标大小再跑一遍，看偏移是固定的还是随大小变 |
| 框和图标完全对不上，或各偏各的 | 位置不是相对列表窗口的。改用界面自动化给的屏幕矩形（V15） |
| 橙框和名字差得远 | `labelRect` 本来就是估算；按截图调整估算公式，或用界面自动化的整项矩形减去图像矩形 |
| 点击没有穿透 | 这是官方文档写明的行为，多半是脚本的窗口样式没生效（看终端里打印的样式）。修脚本后重试。没有别的同样安全的办法（方案 §3.1） |
| 叠加窗口被桌面盖住（终端显示"在桌面窗口之下"），框看不见 | 沉底这个办法在这台系统上不成立。看 V04 的 `owner` 模式；它成立就以属主法为主方案 |
| 普通窗口盖不住框 | 检查是否误用了置顶模式；仍然如此则每次前台窗口变化时重新沉底 |

### V03 拖动图标期间，读取会不会卡住

**要验证的结论**：未知，两种结果都可以接受——要的是**知道是哪一种**（§2.9；macOS 上访达在拖动期间完全不回应）。另外要知道：卡住的调用最后会不会自己返回。

**怎么验证**

```
powershell -NoProfile -STA -ExecutionPolicy Bypass -File .\02-drag-watch.ps1
```

40 秒内，用你自己的测试图标：①拖到另一个空位，立刻松手；②再拖一次，按住至少 8 秒，中途慢慢移动，再松手；③拖出去一小段又拖回原位松手。

**预期结果**（看结尾的"小结"）

| 可能的结果 | 含义 |
|---|---|
| "按住期间读取没有明显卡顿"，"松手之前就读到了位置变化：没有"，"松手后几十到几百毫秒读到新位置" | 比 macOS 省心：拖动期间接口照常回应，位置在松手后更新 |
| "按住期间有一次读取被卡了 N 毫秒"，N 接近按住的时长 | 和 macOS 一样：拖起来之后不回应，直到松手 |
| "松手之前就读到了位置变化：有" | 拖动途中报告的位置在跟着变 |
| 输出最后有"（后台线程 20 秒内没有结束：最后一次读取一直没有返回）" | 有一次调用一直不返回——正式实现必须能取消调用（方案 §2.9） |

另外请留意"鼠标位移"与"图标位移"相差多少（macOS 上差 2～4 点；对齐网格开着时会差更多）。

**如果不成立 / 各种结果怎么办**

| 结果 | 对策 |
|---|---|
| 拖动期间不回应，松手后返回 | 图标桥沿用 macOS 版"访达一时没空"的处理：保留上一份快照、不上报、只留一个最便宜的请求排队，回应后立刻完整读一遍（icon-bridge 模块说明 §4.3）。读取放在专用线程上 |
| 有调用一直不返回 | 专用线程开启调用取消，超时就取消；取消不掉就弃用这条线程另起一条（方案 §2.9） |
| 拖动期间照常回应 | 那套处理可以大大简化，但保留"超时不等于不可用"的原则 |
| 拖动途中位置就在变 | 不影响正确性：交互感知的结局判定只认"松手之后才开始读的快照" |
| 松手后很久（超过 1 秒）才更新，或一直不更新 | 交互感知的"挪了位置"会全部变成"取消"或"未知"。改用别的办法得知新位置：界面自动化的矩形（V15），或界面事件通知（V21） |
| 读取直接报错 | 记下错误码。若只在拖动期间报错，当作"不回应"处理 |

### V04 "显示桌面"（Win+D）时的表现

**要验证的结论**：系统执行"显示桌面"时会把桌面窗口提到 Z 序顶部，沉底的叠加窗口因此被盖住；"发现后上浮"或"属主设为桌面窗口"能让它留在图标上面（§3.2、§3.3）。

**怎么验证**：把下面两条各运行一次。每次都做：按 Win+D，等 3 秒，再按一次 Win+D；点一下任务栏最右端那一小条（也是"显示桌面"）；最后随便打开一个普通窗口。
如果任务栏设置里开着"把鼠标移到任务栏末端的显示桌面按钮时预览桌面"，再把鼠标停在那里试一次。

```
powershell -NoProfile -STA -ExecutionPolicy Bypass -File .\03-overlay.ps1 -Mode follow
powershell -NoProfile -STA -ExecutionPolicy Bypass -File .\03-overlay.ps1 -Mode owner
```

多出几分钟时，再用 `-Mode bottom` 跑一次，把问题本身重现出来。

**预期结果**

| 模式 | 按 Win+D 之后 | 打开普通窗口之后 |
|---|---|---|
| `follow` | 半秒之内框回来；终端出现「[follow] 桌面被提到了叠加窗口上面（显示桌面），已把叠加窗口提到最上」 | 终端出现「[follow] …已把叠加窗口沉回最底」；框被窗口盖住 |
| `owner` | 先确认终端开头那行"实际属主"是 `Progman` 或 `WorkerW`（不是的话这一项不作数，见探针 README 末尾的表）。框一直在，没有消失的瞬间 | 框被窗口盖住 |
| `bottom`（可选） | 框消失；终端显示「在桌面窗口之下（被桌面盖住了）」 | 框（如果还看得见）被窗口盖住 |

**如果不成立**

| 现象 | 备选方案 |
|---|---|
| `bottom` 模式下 Win+D 后框还在 | 好消息：这个系统版本上不需要特殊处理。在别的版本上再确认（V20） |
| `follow` 不管用，`owner` 管用 | 以属主法为主方案。同时做 V19 里"`owner` 模式下重启资源管理器"那一步，确认窗口被连带销毁后能重建 |
| `owner` 不管用，`follow` 管用 | 以"沉底 + 上浮"为主方案；正式实现时把定时核对换成"前台窗口变化"的事件通知，反应更快 |
| 两种都不管用 | 照 Rainmeter 的完整做法重写上浮那一步（先置顶，再插到最靠后的置顶窗口之后；思路见方案 §3.3）。还不行，就只能"显示桌面时没有脸"——这是方案 §10 第 6 问的选项 b，要用户点头 |
| `owner` 模式下桌面变卡，或脚本结束后桌面有异常 | 属主法的副作用（两边的输入队列被绑在一起）。不用它 |
| 上浮之后盖住了本该在上面的东西（例如开始菜单） | 上浮时不要提到最上，而是插到桌面窗口的紧上面 |

### V05 命中判断与起拖阈值

**要验证的结论**

1. 用"这个点上是哪个窗口"能认出鼠标在桌面图标层上，被别的窗口挡住时也认得出（§4.2）。
2. 这个查询会跳过我们自己的点击穿透窗口（§4.2）。
3. 系统的起拖阈值就是资源管理器开始拖图标的距离（§4.3）。

**怎么验证**

```
powershell -NoProfile -STA -ExecutionPolicy Bypass -File .\04-pointer.ps1
```

把鼠标依次移到：桌面空白处 → 一个图标上 → 一个普通窗口上 → 任务栏上。然后在测试图标上：单击；按住不动两秒再松开；按住**慢慢**拖出去再松手。

多出几分钟时再做两件（可选）：
- 带着叠加窗口再做一遍：开两个终端，一个先运行 `03-overlay.ps1 -Seconds 90`，另一个运行上面这条。
- 以管理员身份打开一个程序（例如右键"命令提示符"→ 以管理员身份运行），让它在前台，再去桌面上按住拖一下图标，看本脚本还认不认得出按下（方案 §4.1 的推断）。

**预期结果**

- 开头打印：列表窗口 `SysListView32` ← 视图窗口 `SHELLDLL_DefView` ← 顶层窗口 `Progman` 或 `WorkerW`；起拖阈值 4 / 4 像素（100% 缩放时）。
- 鼠标在桌面空白处和图标上：都是「桌面图标层（SysListView32 ← SHELLDLL_DefView ← 顶层 …）」。
- 在普通窗口上：「别的程序的窗口」；在任务栏上：「资源管理器的其它窗口（…）」。
- 单击、按住不动：「松手（没有越过阈值，算点击）」。

**如果不成立**

| 现象 | 备选方案 |
|---|---|

### V09 虚拟桌面

**要验证的结论**：我们的顶层窗口属于某一个虚拟桌面；在哪个桌面上新建窗口，它就属于哪个桌面（§3.4）。

### V16 合成引擎要用的那种窗口点不点得穿（只测命中）

**要验证的结论**：方案 §3.8 的方式 ① 要求窗口带"不分配后台画布"的样式（`WS_EX_NOREDIRECTIONBITMAP`），介绍它的官方文章又说这时不要用分层样式；

**怎么验证**：`03-overlay.ps1 -NoRedirectionBitmap`。这种模式下窗口不分层、不画任何东西，沉在最底。运行期间在桌面上照常单击图标、拖选框。
如果桌面点不动了，按 Esc 结束即可恢复（窗口在最底，PowerShell 窗口照常能点）。

**预期结果**（两种都可能，记下是哪一种）：

| 结果 | 含义 |
|---|---|
| 桌面照常能点；终端里「图标 #… 中心处最上面：桌面图标层」 | 这种窗口不分层也点得穿，方式 ① 没有障碍 |
| 桌面点不动；终端里那一项是「另一个 PowerShell 进程的窗口」或「本进程的窗口」 | 点不穿（预计如此）。方式 ① 要另想办法 |

终端开头的窗口样式里应当有 `NOREDIRECTIONBITMAP`、没有 `LAYERED`。

**局限**：这只测"不画东西的这种窗口"。用合成引擎真的画出了脸之后是否点得穿，要等实现阶段做 V25 时一起验证。

**如果点不穿**：方式 ① 换一种组合在 V25 里试（例如分层样式和合成引擎一起用、看系统接不接受）；都不行就用分层窗口（方式 ②）。这只影响性能上限，不影响可行性。

### V18 未签名程序实际遇到的拦截

**怎么验证**

1. 把 V17a 编出的 exe 打成 zip，放到一个能下载的地方（自己的网盘、一个私有仓库的发布页），用 Edge 下载回来。记录浏览器有没有提示。
2. 用资源管理器自带的解压，双击 exe。**截图**每一步提示，记下按钮上的原文。
3. 打开「Windows 安全中心 → 应用和浏览器控制 → 智能应用控制」，记下它的状态（开 / 评估 / 关）。如果是开着的，记录 exe 被拦时的提示原文，以及有没有放行的办法。
4. 换 7-Zip 解压再试一次。
5. （可选，发布阶段再做）经 winget 本地清单、Scoop 自建仓库各装一次，看有没有 SmartScreen 提示。

**预期结果**：第 2 步出现 SmartScreen 的整屏提示，要点「更多信息」才有「仍要运行」；智能应用控制开着时被直接阻止，没有放行按钮。

**用途**：把实际的提示文字和截图写进 README 的"首次打开"说明；并据此决定方案 §8.3 的几条路哪些必须做。

**如果不成立**

| 现象 | 对策 |
|---|---|
| 没有任何提示就运行了 | 好消息，但要换一台全新的电脑、换一个下载渠道再试一次，确认不是偶然（例如这台机器关了 SmartScreen） |
| SmartScreen 连"仍要运行"都没有 | 未签名的下载版走不通，签名（SignPath）或商店变成必须，要用户尽早定 §10 第 11 问 |
| 智能应用控制开着却放行了 | 说明这个程序被信誉服务认得了（方案 §8.1 的推断不成立），记录下来，签名的紧迫性降低 |

### V19 资源管理器重启后的恢复

**怎么验证**：`01-read-icons.ps1 -Watch -Seconds 90` 运行期间，打开任务管理器，在"Windows 资源管理器"上点右键 →「重新启动」。再用 `03-overlay.ps1 -Mode owner -Seconds 90` 做同样的事。

**预期结果**：01 先打印「读取失败（资源管理器可能正在重启）」，几秒内打印「重新连上了桌面视图」，之后读数正常。`owner` 模式的叠加窗口会随旧的桌面窗口一起消失（脚本随之结束）——这是预料之中的，正式实现要重建。

**如果不成立**：重连不上 → 监听任务栏重建时系统发出的广播消息（未核对，实现时查），收到后再重连；实在不行，状态停在 `finderUnavailable`，要不要在菜单里提示"请重新打开本应用"由用户和总览定。

### V20 各版本的桌面窗口层级

**怎么验证**：在每一种打算支持的系统上（至少：Windows 10 22H2、Windows 11 23H2、Windows 11 24H2 或更新）运行 `04-pointer.ps1`，记下开头「桌面窗口的层级」那几行和「系统版本」。壁纸设成"幻灯片放映"时再记一次（据说这会改变层级，没有核对到出处）。

**预期结果**：都是 列表窗口 `SysListView32` ← 视图窗口 `SHELLDLL_DefView` ← 一个属于资源管理器的顶层窗口；顶层窗口的类名在不同版本上可能不同。

**用途**：定下"桌面图标层""桌面顶层窗口"的认法，写成一张版本对照表。实现时不写死顶层窗口的类名，从系统给出的桌面窗口出发找（方案 §3.2）。

**如果不成立**

| 现象 | 对策 |
|---|---|
| 某个版本上子窗口的类名也不一样 | 把那个版本的类名加进认法里；子窗口的类名都不稳定的话，改为"属于资源管理器、盖满整块屏、在桌面层级的那个窗口"这种不看类名的认法 |
| 某个版本上找不到 `SHELLDLL_DefView` | 那个版本上读图标（V01）也会受影响，暂不支持那个版本，并报告总览 |

### V25 绘制方式对比

实现叠加层时的**第一件事**，照 macOS 版 `OverlayDemo --bench-compare` 的做法：30 张脸、每帧全部重画，分别量方案 §3.8 的三种方式——
① 系统合成引擎每张脸一个图层；② 分层窗口自己画位图（再分"整窗一张"和"每张脸一个小窗口"两种）；③ 视觉层——的帧率和处理器占用，在 100% 和 150% 缩放的屏上各量一次；再量"空闲""只挪不画"。
同时验证 V16 没覆盖的那一半：画出了脸的窗口是否仍然点得穿。

**目标**沿用 macOS 版：空闲接近 0，30 张脸同时动时约 60 帧。"30 张脸每帧全部重画时本进程不超过约 15%"这一条 macOS 版自己也没有达到（实测 25%～33%，overlay 模块说明 §4.2），所以只作参考。达标的方式里选实现最简单的。

**如果都不达标**：照 macOS 版的经验从调用方这一侧省——视线取整、视线的重画限到每秒 30 次；仍不够就选最省的那种方式，把占用数字如实写进已知限制。
**画出东西后点不穿**：那种方式作废。
