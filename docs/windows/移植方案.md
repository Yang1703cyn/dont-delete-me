# Windows 版移植方案

> **归属** windows-port · **状态** 第一段（平台可行性调研，§0–§12）已验收；第二段（工作拆分、测试环境，§13）已完成。
>
> **重要前提：这份方案没有在任何一台 Windows 电脑上实测过。** 写它的机器是 Mac。文中每条结论都标了可信程度和来源；
> 凡是"仅为推断"的，以及官方文档没有写明的，都列进了 [上机验证清单.md](上机验证清单.md)，并配了探针脚本（[探针脚本/](探针脚本/)，同样未经运行）。
> 拿到 Windows 电脑后，请先按清单把前五项跑一遍（约十分钟），再决定是否照本方案开工。
>
> 模块名、类型名、概念名都沿用 [接口约定.md](../接口约定.md)；macOS 版的实际做法以 [模块说明/](../模块说明/) 为准。
> **有几处 Windows 的事实和现行接口约定对不上，需要总览定**，集中列在 §1.1。

## 0. 结论先行

### 0.1 可行吗

**可行，而且读图标这一环比 macOS 更顺。** 理由：

- Windows 的桌面是资源管理器（Explorer）里的一个"文件夹视图"，系统提供了公开的、给别的程序用的接口来读每个图标的位置、图标大小、排列设置——
  不注入、不读写别的进程内存、不需要任何授权弹窗（§2）。
- 透明、点击穿透的窗口是系统原生支持的窗口样式（§3）。
- 读鼠标位置和按键、问"这个点上是哪个窗口"都是免权限的普通查询（§4）。
- 回收站就是一个桌面图标，位置是**读到的**，不必像 macOS 那样估算（§5）。

### 0.2 最大的三个风险

| # | 风险 | 为什么大 | 怎么尽早排掉 |
|---|---|---|---|
| 1 | **叠加层的层级**：Windows 没有"桌面图标之上、普通窗口之下"这样一个现成的层。只能把窗口"沉到最底"，再专门处理"显示桌面"（Win+D）——那时系统会把桌面提到所有窗口上面，沉底的窗口反而被盖住。Windows 11 24H2 还重排过桌面窗口的层级 | 这是整个产品"脸贴在图标上"的根基；做法依赖系统没有写进文档的行为，而且随版本变 | 验证清单 V02、V04、V20。已有成熟开源项目（Rainmeter）用同样的思路做到了，有路可走 |
| 2 | **未签名程序打不开**：从网上下载的未签名程序，会被 SmartScreen 警告；在开着"智能应用控制"的 Windows 11 上，未签名、又不被微软的应用信誉服务认得的程序会被**直接阻止，没有为单个程序放行的办法**；"S 模式"的电脑上则只能装商店里的应用 | 直接冲撞"下载后打开即用"这条硬性要求 | §8：上架微软商店（注册免费，商店代签名）或申请开源项目的免费签名，都不花钱，但都要走审核 |
| 3 | **拖动图标期间，读图标的调用会不会卡住**：macOS 上访达一把图标拖起来就不再回应询问。Windows 上是否如此，查不到任何说明；而且 Windows 的跨进程调用不像 Apple 事件那样自带超时，卡住了就一直卡着 | 决定"被拖着走向回收站"这段戏里图标桥拿不拿得到数据，以及怎样把 macOS 版那套"访达没空"的处理搬过来 | 验证清单 V03，两分钟。对策见 §2.9：macOS 版"没空就保留旧快照"的思路可以沿用，但要先给读取配一条"等不来就放弃"的路 |

次一级的风险：桌面整理类软件（腾讯桌面整理、Fences 等）接管图标后位置对不上（§9.3）；杀毒软件误报（§9.4）；
坐标单位要和总览重新约定（§1.1）；没有 Windows 电脑，方案里的推断无法验证（第二段 §13 处理）。

### 0.3 推荐的技术路线（一句话）

用 **C#** 写 Windows 版：系统自带运行库（.NET Framework 4.8，Windows 10 1903 起预装），下载一个很小的 exe 就能跑；
macOS 版里不依赖系统的纯逻辑（情绪引擎、交互判断、快照比对等）手工移植成 C#，再拿 macOS 版的逐帧输出对拍、按容差比较，保证两边一致。
如果更看重"两端规则永远是同一份代码"，备选是 Swift 路线：逻辑沿用 macOS 版的同一份代码，平台层也用 Swift 写，个别 Swift 调不顺的系统接口（如绘图合成）用一小层 C++ 转接。理由和比较见 §7；最终由用户或总览定（§10 第 16 问）。

## 1. 与 macOS 版的对照

Windows 版沿用同一套模块划分（接口约定 §0.1）：五个功能模块只依赖 DDMCore，彼此不认识；应用入口把它们接起来。

| 模块 | macOS 版的做法 | Windows 版的推荐做法 | 差别大不大 |
|---|---|---|---|
| **图标桥** IconBridge | 向访达发 Apple 事件，读 desktop position；需要"控制访达"一项授权 | 向 Explorer 的桌面文件夹视图发进程外调用（`IFolderView`）；不需要任何授权 | 读取方式全换；"轮询 + 立即刷新 + 快照比对"的骨架照旧 |
| **叠加层** Overlay | "桌面图标层 +1"的透明窗口；每张脸一个小图层 | 沉底的透明穿透窗口 + "显示桌面"时上浮；每张脸一小块画面 | 层级的做法全换；帧循环、重画判定照旧 |
| **表情绘制** Faces | CoreGraphics 画到 `CGContext` | 换成 Windows 的二维绘图接口；姿态计算（只有数字）照旧 | 绘制调用要换，画什么不变 |
| **交互感知** InputSense | 轮询鼠标；问窗口服务器"点在这里会落到谁身上"；程序坞里的废纸篓靠估算 | 轮询鼠标；`WindowFromPoint`；回收站是桌面图标，位置直接读 | 读系统的薄层全换；判断器（纯逻辑）照旧；废纸篓估算那一大块不需要了 |
| **情绪引擎** Emotion | 纯逻辑 | 逻辑代码原样移植；以"点"为单位的几个调参值可能要按缩放换算（§1.1 第 1 条） | 代码不变 |

概念上的对应：

| 接口约定里的概念 | Windows 上是什么 |
|---|---|
| 访达 | 资源管理器（Explorer）进程里的桌面视图 |
| 废纸篓 | 回收站。它是一个桌面图标，不在任务栏上 |
| 程序坞 | 任务栏。和回收站无关，所以 `TrashInfo` 的"估算 + 自学习"用不上 |
| 全局坐标（原点主屏左上角、y 向下、可为负） | 虚拟屏幕坐标：主屏含原点 (0,0)，主屏不在左上时其它屏的坐标为负【官方】[S42]。原点和方向与 DDMCore 的全局坐标相同；**单位不同**，见 §1.1 第 1 条 |
| `IconProviderStatus.finderUnavailable` | Explorer 没在运行、正在重启，或桌面视图接口失效 |
| `IconProviderStatus.permissionDenied` | Windows 上没有对应的授权弹窗，建议不用这个状态（§1.1 第 4 条） |
| `IconProviderStatus.stacksEnabled` | Windows 没有"叠放"。但有同类情形：桌面整理软件接管图标后位置不可信（§9.3、§1.1 第 3 条） |
| "系统隐藏了桌面图标" | 桌面右键 → 查看 → 取消"显示桌面图标"（§2.6） |
| 桌面空间（Spaces） | 虚拟桌面（任务视图）。所有虚拟桌面共用同一套桌面图标【推断】 |

### 1.1 需要总览定的接口问题

按接口约定 §12.2，下面这些不在 windows-port 的权限内，只提建议。前三条影响开工。

| # | 问题 | Windows 上的事实 | 选项 | 建议 |
|---|---|---|---|---|
| 1 | **坐标单位和 `DisplayInfo.scale`** | 接口约定 §1.1 规定全局坐标的单位是"点"，`scale` = 1 点等于几个像素。Windows 上声明了"每显示器 V2"缩放感知的程序，看到的一律是每块屏的原始像素【官方】[S25]；系统没有提供"按点计"的全局坐标【推断】 | **a.** Windows 上 1 点 = 1 像素：全局坐标就是物理像素，每块屏的 `scale` 都是 1。系统给的所有坐标（鼠标、窗口、图标位置）不用换算。代价：情绪引擎、交互感知里以"点"为单位的手感常数（甩动每 24 点一段、`fearRadius`、`waveSpeed` 等）在 150% 缩放的屏上实际变小了；办法是**构造时**把调参表里的这些数乘以主屏的缩放，对拍时缩放取 1（**第二段更正**：起拖距离不在此列，Windows 上直接读系统参数；情绪引擎的调参表能在构造时传入，交互感知的现在不能；表情绘制里按点定的门槛也要换算——见 §13.1.1）。混合缩放的多屏上副屏的手感会差一点。<br>**b.** 自己拼一张"点"的平面：每块屏的像素矩形除以它的缩放，再按排列拼起来。含义和 macOS 完全一样、常数不用改。代价：每一个系统读数都要换算；相邻两块屏缩放不同时怎么拼没有标准答案，接缝处容易差一两个点 | **a**。需要在接口约定里写明"Windows 上 1 点 = 1 物理像素、`scale` 恒为 1"，并给两个模块的调参表加一个"按缩放换算"的约定 |
| 2 | **标出回收站** | 交互感知要从图标快照里找到回收站才能给出 `TrashInfo`（§5.1），但 `DesktopIcon` 里没有这个信息，交互感知又不能依赖图标桥 | a. `IconKind` 加一个 `trash`；b. `DesktopIcon` 加一个布尔字段；c. `IconSnapshot` 加一个"回收站是哪个编号" | a 或 c（改动最小）。macOS 版填"没有" |
| 3 | **图标被隐藏、被桌面整理软件接管时用什么状态** | 这两种情况下图标桥读到的位置都不能用来画脸（§2.6、§9.3）。按接口约定 §2.4，只有状态不是 `ok` 时快照才是空的；在 `ok` 状态下清空快照会对每个图标发出"消失" | a. 复用 `stacksEnabled`（含义放宽为"位置不可信"）；b. 新增一个状态；c. 图标桥不管，交给叠加层的 `isDesktopVisible`（macOS 版对"图标被隐藏"就是这样处理的 [icon-bridge 模块说明 §9.2]） | 图标被隐藏用 c（和 macOS 一致）；整理软件接管用 a 或 b，视 V22 的结果定 |
| 4 | **`permissionDenied`** | Windows 上没有授权弹窗。本程序和 Explorer 权限级别不同时调用可能被拒，但那不是"用户拒绝了"【推断】 | a. 不用这个状态，这类失败归 `finderUnavailable`；b. 放宽含义 | a，不用改接口 |
| 5 | **`DesktopAppearance` 怎么填** | `iconSize` 可以读到（§2.5）；`textSize` 是桌面图标字体的大小，推断能从系统的"图标标题字体"设置读到，没有核对；`labelPosition` 在 Windows 桌面上推断永远是"在下" | 照这三条填；`textSize` 读不到时用 `.finderDefault` 的 12 | 不用改接口，只需在 Windows 版的模块说明里写清 |
| 6 | **谁去找桌面窗口** | 叠加层和交互感知都要知道"哪个窗口是桌面"（§3.2、§4.2），而桌面视图的窗口句柄是图标桥拿到的 | 两个模块各自用窗口查询找：从系统给出的桌面窗口（`GetShellWindow`【官方】[S103]）出发，找带 `SHELLDLL_DefView` 子窗口的那个顶层窗口。这只是窗口查询，不向 Explorer 发调用，和 macOS 版叠加层、交互感知各自读窗口列表是同一种做法 | 不用改接口。向 Explorer 发调用的只有图标桥一家（和 macOS 版"只有图标桥问访达"的约定一致） |

## 2. 读图标（对应图标桥）

### 2.1 推荐做法：向 Explorer 的桌面视图发进程外调用

**路线**【官方·博客】[S01]，每一步的接口【官方】[S07][S08]：

```
ShellWindows 对象
  └─ FindWindowSW(桌面, SWC_DESKTOP)            找到"桌面"这个特殊的资源管理器窗口
       └─ QueryService(SID_STopLevelBrowser)    → IShellBrowser
            └─ QueryActiveShellView             → 桌面的文件夹视图
                 ├─ IFolderView / IFolderView2  读图标
                 └─ IShellView::GetWindow       视图窗口的句柄（换算坐标用）
```

这是微软工程师 Raymond Chen 在微软官方博客上给出的做法，示例程序就是一个独立的 exe，从外面读（和改）桌面图标的位置 [S01]。
`SWC_DESKTOP` 从 Windows Vista 起可用【官方】[S07]。我们**只调用读的方法**，从不调用会移动图标、改设置的方法
（`SelectAndPositionItems`、`SetCurrentFolderFlags`、`SetViewModeAndIconSize`）。

**为什么符合"不注入、不读写别的进程内存"**：这些是系统的组件对象接口，跨进程调用由系统的远程调用机制代办，
我们的进程里没有任何 `OpenProcess`、`ReadProcessMemory` 之类的调用【推断：依据是 [S01] 的示例就是这样写的；文档没有专门讲这一点】。

| 要读什么 | 怎么读 | 可信程度 |
|---|---|---|
| 有几个图标 | `IFolderView::ItemCount(SVGIO_ALLVIEW)`，一次调用 | 【官方】[S08][S11] |
| 第 i 个图标是谁 | `IFolderView::Item(i)` 给出它的标识（PIDL） | 【官方】[S08] |
| 图标的位置 | `IFolderView::GetItemPosition`：给出"该项左上角"的位置 | 【官方】[S03] |
| 位置是相对谁的坐标 | 文档没写。推断是桌面列表控件的客户区坐标，用列表窗口换算成屏幕坐标 | 【推断】→V02 |
| 位置的单位（混合缩放时） | 文档没写。推断是物理像素 | 【推断】→V10 |
| 图标大小 | `IFolderView2::GetViewModeAndIconSize`：以像素为单位的图标边长 | 【官方】[S05] |
| 每个图标占的格子多大 | `IFolderView::GetSpacing`：一项连同四周留白的宽和高 | 【官方】[S06] |
| 是否自动排列 | `IFolderView::GetAutoArrange`：开着返回 S_OK，关着返回 S_FALSE | 【官方】[S09] |
| 其它视图设置 | `IFolderView2::GetCurrentFolderFlags`：一组标志位 | 【官方】[S10][S04] |

**备选**：界面自动化（§2.7）。直接给桌面列表控件发消息的办法排除了（§2.8）。

### 2.2 图标部分和文字部分的矩形

接口给的是"一个点 + 图标边长 + 格子大小"，两个矩形要自己推——和 macOS 版一样（那边访达也只给一个点，图像矩形是推算后用截图校准的）。

| 矩形 | 推算办法 | 可信程度 |
|---|---|---|
| `imageRect`（图标图像） | 两个候选：①位置是格子的左上角，图像在格子里水平居中：`x + (格子宽 − 图标边长)/2`；②位置就是图像的左上角。纵向可能还有几个像素的固定边距 | 【推断】→V02（探针会把两个候选用不同颜色画在屏幕上，一眼就能看出哪个对） |
| `labelRect`（文字标签） | 估算：从图像下沿往下到格子下沿、宽度等于格子宽。接口里本来就是可空的估算值，`hitTest` 在没有标签时退化为只认图像矩形（接口约定 §12.1） | 【推断】→V02（探针画的橙框就是这个估算） |

**推荐**：上机前定不下用哪个公式，所以两个候选都实现好，用一个常数切换，按 V02 的截图选定；纵向边距、标签的上下沿也按截图校准成常数（macOS 版就是这样校准的，见 icon-bridge 模块说明 §3）。
**备选**：用界面自动化读出"整项"的屏幕矩形（§2.7），减去图像矩形得到文字部分；还可以用它反推出图像矩形的公式（V15）。

### 2.3 种类

| 要判断什么 | 怎么读 | 可信程度 |
|---|---|---|
| 是文件夹、快捷方式，还是文件系统里的东西 | 项目属性标志：`SFGAO_FOLDER`（文件夹）、`SFGAO_LINK`（快捷方式）、`SFGAO_FILESYSTEM`（是文件系统的一部分）、`SFGAO_STREAM`（带数据流） | 【官方】[S16] |
| 压缩包 | 资源管理器能把 zip 当文件夹打开，所以 zip 文件推断同时带 `SFGAO_FOLDER` 和 `SFGAO_STREAM`。规则：带 `SFGAO_STREAM` 的一律算文件 | 【推断】→V01 |
| 是不是"此电脑""回收站"这类系统图标 | 不带 `SFGAO_FILESYSTEM` 的就是虚拟项；官方文档说这类虚拟文件夹的解析名**可能**是 `::{GUID}` 的形式 | 【官方】[S16][S17] |
| 是不是回收站 | 取"回收站"这个已知文件夹（`FOLDERID_RecycleBinFolder`，虚拟文件夹）的标识，和桌面上每一项的解析名比对。不要把某个 GUID 写死在代码里 | 已知文件夹编号【官方】[S18]；比对的做法【推断】→V01 |

对应到 `IconKind`：文件夹 → `folder`；普通文件、压缩包 → `file`；`.exe` 程序 → `application`（按扩展名在图标桥内部判断）；系统图标 → `other`；
**快捷方式 → `file`**，这是 macOS 版的先例（替身、网址快捷方式都算"文件"，icon-bridge 模块说明 §8.2）。Windows 桌面默认不显示磁盘，`volume` 推断用不上。
（快捷方式被删时要不要反应得轻一些，是另一回事，属于产品问题，见 §10 第 5 问。）

**推荐**：上面这套属性标志 + 已知文件夹比对。**备选**：回收站的识别改用文件夹对象自带的"比较两个项目是不是同一个"（`IShellFolder::CompareIDs`，返回 0 表示相同）【官方】[S112]；
种类改用解析名的形式（`::{` 开头的是系统图标）。

`IconID` 的算法照旧：每次安装随机生成的盐 + 项目的解析名，取哈希。解析名只在图标桥内部使用，不进日志、不进任何 DDMCore 类型。
Windows 的桌面是"当前用户的桌面文件夹 + 公用桌面文件夹 + 系统图标"三者合并显示的【官方：两个文件夹各有已知文件夹编号 [S18]；合并显示是推断】，
所以要用完整的解析名（而不是显示名）来算编号，免得两个文件夹里的同名项撞车。

### 2.4 怎样发现新增、消失、移动

**推荐：沿用 macOS 图标桥的骨架**——快速检查（只数个数）+ 完整读取（位置）+ `refreshNow()`（松手时立即重读）+ 快照比对出 `IconChange`。
这部分是纯逻辑，macOS 版已经写好并测过（`BridgeCore`、`SnapshotDiff`、`PollSchedule`）。

| 事情 | 做法 | 可信程度 |
|---|---|---|
| 快速检查 | `ItemCount` 一次调用 | 【官方】[S08] |
| 完整读取 | 对每个图标调一次 `Item` + `GetItemPosition`（接口里没有"一次取回全部位置"的方法 [S08]）。每次调用多少毫秒、Explorer 要花多少处理器——未查到 | 【推断】→V11 |
| 用鼠标造成的变化 | 松手时 `refreshNow()`，和 macOS 版一样 | 【推断】→V03 |

**备选（可以和推荐做法叠加，用来减少轮询）**：

| 做法 | 说明 | 可信程度 |
|---|---|---|
| 文件夹变化通知 | 向系统登记 `SHChangeNotifyRegister`：桌面文件夹里创建、删除、改名时系统发消息给我们的一个窗口。这样空闲时轮询可以放得比 macOS 版更慢 | 接口【官方】[S12][S13]；能否覆盖到所有情形【推断】→V21 |
| 进程外的界面事件钩子 | `SetWinEventHook` 加 `WINEVENT_OUTOFCONTEXT`。官方写明这种钩子的回调"不会被映射进产生事件的那个进程"，也就是不注入 | 不注入这一点【官方】[S14]；桌面列表会不会为图标挪动发事件【推断】→V21 |

图标在桌面上挪位置不会产生文件夹变化通知【推断】，所以完整读取的轮询少不了。

### 2.5 图标大小、对齐网格、自动排列的影响

| 设置 | 影响 | 可信程度 |
|---|---|---|
| 图标大小（Ctrl + 滚轮，或右键 → 查看） | 所有矩形一起变 → 按接口约定以**整体重载**上报。每次完整读取都重读图标大小和格子大小 | 读取接口【官方】[S05][S06] |
| 自动排列 | 开着时，用户拖一个图标，其它图标会跟着挪——一次松手可能带出好几条 `.moved`。读得到（`GetAutoArrange`） | 读取【官方】[S09]；连锁移动【推断】→V12 |
| 对齐网格 | 松手后图标被吸到网格点上；以系统报告的新位置为准（macOS 版也是这样处理的）。**读不读得到这个开关不确定**：官方枚举里 `FWF_SNAPTOGRID` 写着"不支持"【官方】[S04]，而官方博客的示例又在用它【官方·博客】[S01] | 【推断】→V12。对我们影响不大：我们只读位置，不需要知道开关 |

**推荐**：每次完整读取都把图标大小、格子大小、自动排列一起读，变了就整体重载。**备选**：图标大小读不到时，从桌面视图的脚本对象读（探针 01 演示了这条路）。

### 2.6 "不显示桌面图标"时怎么判断

macOS 版的教训：图标被系统隐藏时，图标窗口照常存在，只看"窗口在不在"判断不出来（overlay 模块说明 §6.3）。Windows 上有三个候选信号，哪个管用要实测：

| 候选信号 | 依据 | 可信程度 |
|---|---|---|
| ① 视图标志里有 `FWF_NOICONS` | 官方枚举：`FWF_NOICONS` = "视图不应显示图标"。但桌面右键菜单的"显示桌面图标"是不是对应这个标志，官方页面没写 | 标志的含义【官方】[S04]；与那个菜单项的对应【推断】→V07 |
| ② 桌面的列表控件窗口变成了"不可见" | 没有出处 | 【推断】→V07 |
| ③ 注册表里当前用户的资源管理器设置项 | 没有找到官方文档 | 【推断】→V07 |

**推荐**：分工照 macOS 版——图标看不看得见归**叠加层**的 `isDesktopVisible` 管（它为 false 时应用让图标桥停止读取）。叠加层不能依赖图标桥，所以它用窗口层面的信号 ②。
**备选**：② 不管用时，叠加层改读 ③；三个都不管用就用界面自动化看列表项还在不在（V07 的备选）。图标桥要不要也据 ① 改状态，是接口问题（§1.1 第 3 条），不要在 `ok` 状态下清空快照。

### 2.7 备选做法：界面自动化（UI Automation）

系统自带的辅助功能接口。官方说明：微软为每一种标准控件都配了提供程序，标准控件自动对界面自动化的客户端可见【官方】[S19]；
元素的 `BoundingRectangle` 是物理屏幕坐标下的矩形【官方】[S20]。

| 种类、回收站的识别 | 有属性标志，可靠 | 只有显示名，要靠名字认，不可靠 |

### 2.8 排除的做法：直接给桌面列表控件发消息

网上最常见的办法是找到桌面的列表控件窗口，给它发"取第 i 项的位置 / 矩形"的消息。它其实能直接给出图标部分和文字部分的矩形
（`LVIR_ICON`、`LVIR_LABEL`）【官方】[S15]。**但我们不用**：

- 这个消息的参数是"指向一块内存的指针"【官方】[S15]，跨进程使用就必须在 Explorer 进程里申请并读写内存——正是硬性要求里不许做的事
  【推断：这是这类消息跨进程使用时的通行做法，文档没有专门写这一句】。
- 微软工程师在官方博客上专门写过一篇《访问和修改桌面图标位置的正确办法》：从 Windows 10 1809 起桌面图标位置的管理方式变了，
  直接和列表控件打交道"从来就没有保证过能用"，"不要再给一个未公开的窗口发消息、利用内部实现细节"；文中点名受支持的是文件夹视图接口【官方·博客】[S02]。
  题目里就有"访问"，所以读位置也在此列。

### 2.9 拖动期间、Explorer 重启时

| 情形 | 现状 | 对策 |
|---|---|---|
| 用户正拖着图标 | 系统通用的拖放函数在拖放期间会进入一个专门的循环，跟踪鼠标和按键直到松手【官方】[S53]；Explorer 拖桌面图标用的是不是它、这期间还回不回应我们的调用——**未查到** →V03 | 照 macOS 版的约定办：没回应就保留上一份快照、不上报，回应了立刻完整读一遍（接口约定 §2.4"访达一时没空，不算不可用"）。这部分是纯逻辑，可以照搬。**但有一处不能照搬**，见下一行 |
| 一次调用迟迟不返回 | macOS 版那套处理建立在"Apple 事件会超时"之上（15 秒超时、5 分钟才算不可用）。Windows 的跨进程调用没有看到默认超时的说明，推断会一直等下去；系统提供了"请求取消一次正在等待的调用"的函数，但要先在那个线程上开启取消功能【官方】[S104]（默认不超时是【推断】） | 读取放在图标桥自己的一条专用线程上，主线程从不等它；这条线程开启调用取消，超过时限就取消这次调用，再按 macOS 版"这一轮作废、保留旧快照"处理。取消不掉时，弃用这条线程、另起一条 →V03 |
| 拖动途中位置变不变、松手后多久更新 | 未查到 →V03 | 拖动**途中**位置变了不会出错：交互感知的结局判定只认"松手之后才开始读的快照"（input-sense 模块说明 §4.6）。但如果松手后很久、甚至一直不更新，结局会变成"取消"或"未知"，那就要换办法得知新位置（V03 的备选） |
| Explorer 崩溃或被重启 | 手里的接口全部失效 | 状态置 `finderUnavailable`、快照清空；定时重新走一遍 §2.1 的路线，成功后以整体重载上报【推断】→V19 |

## 3. 叠加层（对应 Overlay）

### 3.1 透明、点击穿透的窗口

**推荐**：每块显示器一个无边框的顶层窗口，带这几个扩展样式：

| 样式 | 作用 | 可信程度 |
|---|---|---|
| `WS_EX_LAYERED` + `WS_EX_TRANSPARENT` | 官方原话的意思：分层窗口带上 `WS_EX_TRANSPARENT` 后，窗口形状被忽略，鼠标事件会传给它下面的其它窗口 | 【官方】[S22] |
| `WS_EX_NOACTIVATE` | 用户点它不会让它变成前台窗口；前台窗口被最小化或关闭时，系统也不会把它提到前台；默认不出现在任务栏 | 【官方】[S21] |
| `WS_EX_TOOLWINDOW` | 不出现在任务栏和 Alt+Tab 里 | 【官方】[S21] |

单独加 `WS_EX_TRANSPARENT`，点击并不能穿过它落到别的程序的窗口上（窗口属于不同进程时这个样式不起作用）【官方·博客】[S28]；必须和 `WS_EX_LAYERED` 一起用才行【官方】[S22]。

对应安全线"所有窗口从创建那一刻起就必须点击穿透"：这些样式在创建窗口时就给，不是事后再加。

**备选**：没有同样安全的备选。分层窗口不带 `WS_EX_TRANSPARENT` 时，命中测试按窗口的形状和透明度来【官方】[S22]，也就是画了脸的那些像素会接住点击——违反安全线。
所以这一条只能实测确认（V02），不成立就修窗口样式，不换别的办法。

### 3.2 压在桌面图标之上、普通窗口之下

**Windows 没有 macOS"桌面图标层 +1"这样的层。** 官方文档里讲到的层级只有"置顶"和"不置顶"两档【官方】[S22][S24]
（没有找到别的公开层级——"没有"这一点是推断）；比"置顶"更高的那几层，只开放给签名并装在受保护位置的辅助工具，
而且微软写明它不是给"只是想盖在别的程序上面"的应用用的【官方】[S37]。

**推荐做法：沉底 + 显示桌面时上浮**

1. 平时把窗口放到 Z 序最底（`SetWindowPos` 的 `HWND_BOTTOM`，不激活）【官方】[S24]。桌面推断是一个排在更后面的窗口，所以我们在图标之上【推断】；
   别的程序的窗口新建或被激活时都会排到同类窗口的最前面【官方】[S22]，所以我们在它们之下，被窗口挡住时脸也自然被挡住。
2. 窗口永不激活，所以不会被系统提到前面。
3. 专门处理"显示桌面"，见 §3.3。

可信程度：单个接口的行为【官方】；合起来能稳定地"夹"在图标和普通窗口之间——【开源】：Rainmeter（桌面小部件工具，GPL-2.0）的"On Desktop"位置
就是这个效果，它的官方文档写明这个位置"在显示桌面（Win+D）时保持可见，并待在其它普通程序窗口后面"【官方】[S32]。→V02

**备选 A：把叠加窗口的"属主"设成桌面窗口。** 官方规则：被拥有的窗口在 Z 序上永远在它的属主之上【官方】[S22]，
设置属主有公开接口【官方】[S41]。这样"显示桌面"把桌面提上来时，我们自动跟着在它上面，不用自己盯。
代价：跨进程的属主关系"技术上合法"，但会把两边线程的输入队列绑在一起，后果很难管【官方·博客】[S40]；属主被销毁时系统会连带销毁被拥有的窗口【官方】[S22]
（Explorer 一重启我们的窗口就没了，要重建）。Rainmeter 没有用这个办法【开源】[S33]。→V04 里两种都试。

**备选 B：把窗口挂进桌面窗口的子窗口树里。** 不推荐：动态壁纸软件就是这么做的（挂在图标后面）【推断】，Windows 11 24H2 重排桌面窗口层级后它们集体出过问题，
微软为此一度暂停向装了这类软件的电脑推送更新，列出的症状里就有"桌面图标消失"
（Lively 为 24H2 重写核心部分一事【开源】[S34]；暂停推送和症状【推断，有旁证】[S35]，是媒体转述微软的公告）。

**怎样找到桌面窗口**：不要假设承载桌面图标的顶层窗口叫什么、挂在谁下面——24H2 前后不一样【开源】[S33]。
从系统给出的桌面窗口（`GetShellWindow`）出发【官方】[S103]，找带 `SHELLDLL_DefView` 子窗口的那个顶层窗口；子窗口的类名在各版本上推断是稳定的 →V20。
叠加层自己做这件事，不经过图标桥（§1.1 第 6 条）。

### 3.3 "显示桌面"（Win+D）

系统的做法：先把所有**能最小化**的窗口最小化，再把桌面窗口挪到 Z 序的顶部【官方·博客】[S39]。
我们的窗口不能最小化（也不该能），于是沉在底下的它会被提上来的桌面盖住——偏偏这时用户正看着桌面。

**推荐**（Rainmeter 的思路，【开源】[S33]，只学思路）：

- 用进程外的界面事件钩子监听"前台窗口变了"（`EVENT_SYSTEM_FOREGROUND`【官方】[S107]；不注入【官方】[S14]），再加一个低频的定时核对；
- 判断"现在是不是显示桌面状态"：看自己的窗口在 Z 序里是不是落到了装着桌面图标的那个窗口后面；
- 是：把叠加窗口临时提到桌面之上（Rainmeter 的做法是先置顶，再插到最靠后的那个置顶窗口之后）；不是：沉回最底。

**备选**：§3.2 的备选 A（属主法）。

任务栏最右端的"显示桌面"按钮、鼠标停在那里时的"桌面预览"：推断同理 →V04。

### 3.4 虚拟桌面

- 公开接口只有三个方法：某窗口在不在当前虚拟桌面、它在哪个虚拟桌面、把窗口挪到某个虚拟桌面。**没有**"切换了"的通知，也没有"显示在所有桌面"【官方】[S29]。
  微软工程师的说法：虚拟桌面是给用户整理窗口用的，不是给程序用的；这个接口只为让程序"考虑到虚拟桌面的状态"【官方·博客】[S30]。
  Chromium 的文档也写着：窗口换了虚拟桌面，Windows 不给通知；而且这几个调用不要放在界面线程上【开源：Chromium，BSD 三条款式许可证】[S38]。
- 我们的顶层窗口属于某一个虚拟桌面，用户切走后它留在原来那个桌面上，新桌面上没有脸【推断】→V09。

**推荐**：照 macOS 版叠加层的做法——**每个去过的虚拟桌面各留一个窗口**（macOS 版每块屏最多留 6 个，overlay 模块说明 §6.1）：
巡检时发现当前虚拟桌面上还没有我们的窗口，就新建一个（新窗口推断出生在当前桌面 →V09），晚零点几秒淡入；
之后再回到这个桌面，它的窗口本来就在那里，随桌面一起出现。所有窗口共用同一批画面。巡检的调用放在后台线程。
**备选**：实测如果"工具窗口"本来就在所有虚拟桌面可见（有这种说法，没找到出处），就只需要一个窗口 →V09。

### 3.5 全屏应用、桌面被挡住、锁屏、睡眠

`isDesktopVisible` 为 false 的各种情形（接口约定 §7.4 列了：全屏应用、锁屏、屏幕睡眠、图标被隐藏、桌面窗口全被挡住），Windows 上的信号：

| 情形 | 信号 | 可信程度 |
|---|---|---|
| 全屏应用、全屏游戏、演示模式 | `SHQueryUserNotificationState`：`QUNS_BUSY`（有全屏应用在运行或启用了演示设置）、`QUNS_RUNNING_D3D_FULL_SCREEN`、`QUNS_PRESENTATION_MODE` | 【官方】[S31] |
| 锁屏、屏保、切到别的用户 | 同一个函数的 `QUNS_NOT_PRESENT`；锁屏、解锁另有会话通知（`WTSRegisterSessionNotification`，收到 `WTS_SESSION_LOCK` / `WTS_SESSION_UNLOCK`） | 【官方】[S31][S106] |
| 屏幕睡眠（息屏） | 电源设置通知 `RegisterPowerSettingNotification` + `GUID_CONSOLE_DISPLAY_STATE`：显示器关、开、变暗（Windows 8 起） | 【官方】[S105] |
| 电脑睡眠 | 睡着时程序本来就不运行；醒来时按上面两条重新判断 | 【推断】 |
| 桌面被普通窗口盖满 | 没有现成信号。自己沿 Z 序看我们上面的可见窗口有没有把这块屏盖住；在别的虚拟桌面上的窗口要排除（它们带"被隐藏"的标记，`DWMWA_CLOAKED`） | 标记【官方】[S36]；做法【推断】→V13 |
| 图标被隐藏 | §2.6 | →V07 |

**推荐**：锁屏、息屏用系统通知（立刻知道）；全屏、被盖满、图标被隐藏靠巡检（和 macOS 版一样每秒一次，被盖满时放慢）。
**备选**：全部靠巡检（每秒问一次 `SHQueryUserNotificationState`），实现最简单，代价是最多晚一秒。

沉底的窗口在全屏应用下面本来就看不见；这些信号的用途是**停止出帧和停止读图标**（省电），与 macOS 版一致。

### 3.6 多显示器与不同缩放比例

- 进程在清单文件里声明"每显示器 V2"缩放感知（Windows 10 1703 起）。这样程序看到的是每块屏的原始像素，系统不会把我们的窗口当位图拉伸【官方】[S25]。
  不声明的话，在缩放不是 100% 的屏上画面会被拉糊，系统还会把给程序的数值换算成"假装是 96 DPI"的值【官方】[S25]。
- 每块屏的缩放从 `GetDpiForMonitor` 读（Windows 8.1 起；读到的值取决于调用方的缩放感知）【官方】[S44]。
  它填进 `DisplayInfo.scale` 还是只用来换算调参值，取决于 §1.1 第 1 条怎么定。
- 显示器插拔、改分辨率、改缩放：重读布局、重建窗口、下一帧全部重画（与 macOS 版一致）。
- Explorer 报告的图标位置在混合缩放下是哪种单位：未查到 →V10。

**推荐**：每块显示器一个窗口（和 macOS 版一样），各按自己的缩放作画，不同缩放的屏上画面都清晰【推断】。
**备选**：一个横跨整个虚拟屏幕的大窗口（探针 03 就是这样，实现最简单），代价是混合缩放时有一块屏会发虚、整窗重画更贵【推断】。

### 3.7 拖拽层（最上层窗口）

**推荐**：同样的透明穿透窗口，另加置顶样式（`WS_EX_TOPMOST`）；只在这一帧有 `.drag` 项时显示，没有就隐藏（接口约定 §7.1）。
置顶窗口盖在所有非置顶窗口之上，失去焦点也保持【官方】[S21][S22]。

不确定的两点（→V08）：

- 系统拖放时的拖影推断也是一个置顶的窗口，我们的脸能不能盖在它上面【推断】；
- 任务栏也是置顶窗口，拖到任务栏上方时脸会不会被盖住。回收站在桌面上而不在任务栏里，所以这一点推断没有 macOS 上"拖到程序坞"那么要紧【推断】。

**备选**：不用拖拽层，被拖图标的脸也画在桌面层——拖到普通窗口上方时脸会被窗口盖住，但拖向桌面上的回收站这条主线不受影响【推断】。
更高的层需要 UIAccess（签名 + 装在受保护位置），不适合我们【官方】[S37]。

### 3.8 绘制技术

macOS 版实测的结论是"每张脸一小块画面，只重画变了的，位置变了只挪不画"；整窗一张大画布**在 2 倍屏上**贵 4 倍多，1 倍屏上全员都在变时反而略省，
但别的情形都输（overlay 模块说明 §4.1）。Windows 上 100%、125% 缩放的屏很常见，这一点要重新量。可选的方式：

| 方式 | 说明 | 评价 | 可信程度 |
|---|---|---|---|
| **① 系统合成引擎（DirectComposition）+ 二维绘图（Direct2D），每张脸一个小图层** | Windows 8 引入的位图合成组件【官方】[S26]，由显卡驱动【官方·博客】[S23]。窗口带 `WS_EX_NOREDIRECTIONBITMAP`，系统就不再为整扇窗口准备一张后台画布，画面直接交给合成引擎拼【官方】[S21][S23] | 推断最流畅省电，也最接近 macOS 版选定的方式。**一处疑点**：介绍这种做法的官方文章说这时"不要用 `WS_EX_LAYERED`"[S23]，而我们的点击穿透正要靠它；只带穿透样式的窗口预计点不穿（§3.1）→V16、V25 | 接口【官方】；性能与能否并用穿透样式【推断】 |
| **② 分层窗口 + 自己画位图**（`UpdateLayeredWindow`） | 最老、最简单的逐像素透明办法【官方】[S43]。官方文章指出分层窗口由处理器处理【官方·博客】[S23] | 整屏大小的窗口每帧上传整张位图会很贵；可以"每张脸一个小窗口"，或只更新变了的矩形 | 性能【推断】→V25 |
| ③ 视觉层（Windows.UI.Composition）嵌在普通窗口里 | Windows 10 1803 起【官方】[S45] | 和 ① 同一套合成引擎，接口更新；最低系统要求更高 | 【官方】；性能【推断】 |

（探针 03 的画框窗口用的是分层窗口最简单的"颜色键"模式：某一种颜色当作透明，不支持半透明。它只用来核对位置和穿透，不代表正式的绘制方式。）

**推荐**：先用 ② 把功能跑通（实现量最小），上机后按 macOS 版 `--bench-compare` 的办法实测 ①②③（V25），哪个达标用哪个。若 V16 成立，长期方案是 ①。
**备选**：都不达标时，照 macOS 版的经验从调用方这一侧省：视线取整、视线的重画限到每秒 30 次（overlay 模块说明 §4.2）。
目标沿用 macOS 版：空闲接近 0，30 张脸同时动时约 60 帧；"30 张脸每帧全部重画时本进程不超过约 15%"这一条 macOS 版自己也没有达到（实测 25%～33%）。

**帧循环与省电**：照接口约定——按 `FrameDemand` 出帧，`.idle` 时什么都不开，桌面不可见时一帧不出。连续出帧时的节拍：
Windows 11 有"等合成器下一个节拍"的函数（要求系统版本 22000 以上，即 Windows 11）【官方】[S27]；Windows 10 上用定时器【推断】。
总览在 macOS 上实测，桌面露着、鼠标不动时约 4.3%～4.6% 的占用，主要花在睡着的脸的小动画上 [事实清单]；这一点和平台无关，Windows 上推断同样是空闲时的主要开销。

## 4. 交互感知（对应 InputSense）

### 4.1 读鼠标

**推荐：和 macOS 版一样，每帧问一次"现在是什么状态"，不监听事件。**

| 要读什么 | 怎么读 | 可信程度 |
|---|---|---|
| 位置 | `GetCursorPos`，屏幕坐标 | 【官方】[S46] |
| 按键 | `GetAsyncKeyState`，返回值最高位表示"此刻按着" | 【官方】[S47] |
| 左右键被用户对调过 | 这个函数查的是**物理**按键，不是逻辑按键；要用 `GetSystemMetrics(SM_SWAPBUTTON)` 换算 | 【官方】[S47][S49] |
| 鼠标多久没动 | 自己记：位置没变就累加（和 macOS 版一样）。不用 `GetLastInputInfo`——它给的是最近一次**任何**输入的时刻，包括键盘【官方】[S52]，用了等于知道了键盘活动 | — |

都不需要特殊权限。已知的限制：文档列出的失败原因之一是"界面特权隔离不让调用方访问前台线程"，这时返回 0【官方】[S47]——
也就是前台是权限更高的程序（例如以管理员身份运行的窗口）时，读不到按键【推断】。那时鼠标仍可能在桌面上，后果是这期间认不出按下和拖拽【推断】→V05。

**和 macOS 版不一样的一处**：macOS 版靠系统告诉它"最近一次左键按下是多久以前"来折算两帧之间的按下点，从而把抓取偏移算准。
Windows 上没找到等价的免权限查询；`GetAsyncKeyState` 返回值的最低位（"上次调用之后按过没有"）官方明说不可靠【官方】[S47]。
所以只能二选一：上一帧鼠标是静止的，就把那个位置当按下点；否则用这一帧的位置。抓取偏移可能因此差一两个像素【推断】。

**备选（想更准时）**：原始输入（Raw Input）——登记之后，程序在后台也能收到鼠标的输入消息【官方】[S51]。不注入、不拦截。
**不推荐**：低级鼠标钩子。它确实不注入别的进程【官方】[S50]，但回调超时会被系统悄悄摘掉、程序自己无从得知【官方】[S50]，而且装全局钩子是杀毒软件重点盯的行为【推断】。

### 4.2 "点在桌面图标上且没被窗口挡住"

**推荐**：`WindowFromPoint` 取"这个点上的窗口"，再看它是不是 Explorer 的桌面图标列表；是的话，用图标桥的快照做 `hitTest`（和 macOS 版同一个思路）。

| 环节 | 现状 | 可信程度 |
|---|---|---|
| `WindowFromPoint` 不会返回隐藏或禁用的窗口 | 文档有写 | 【官方】[S48] |
| 它会不会跳过我们自己的点击穿透窗口 | 文档只说"鼠标事件会传给下面的窗口"[S22]，没说这个函数的行为 | 【推断】→V05 |
| 认出"桌面图标层" | 看窗口类名（`SysListView32`，它的上级是 `SHELLDLL_DefView`）、所属进程是不是 Explorer。这里认的是子窗口的类名，不是顶层窗口的类名（§3.2） | 【推断】→V05、V20 |
| 拖拽期间 | 鼠标底下是系统的拖影，要跳过它再看下面（macOS 版同样跳过系统拖影和本应用的窗口，input-sense 模块说明 §2 第 6 条） | 【推断】→V08 |

**备选**：取到的窗口属于本进程或是拖影时，macOS 版的做法是"再问它下面的那个"（input-sense 模块说明 §4.4）。Windows 的这个函数没有"问下面那个"的版本，
所以备选是自己沿 Z 序从上往下找第一个"可见、没被隐藏到别的虚拟桌面、包含这个点、不属于本进程、不是穿透窗口"的窗口【推断】。

`isMouseOverDesktop`、悬停、"按下那一刻一定现查"、各档查询频率，都照 macOS 版的判断器，不用改。

### 4.3 拖拽的开始与结束

| 事情 | 做法 | 可信程度 |
|---|---|---|
| 起拖阈值 | 系统参数 `SM_CXDRAG` / `SM_CYDRAG`：鼠标从按下点往两边各能移动多少像素才算开始拖 | 【官方】[S49]。和 macOS 版"横向或纵向 4 点"是同一个概念 |
| Explorer 是不是就用这个数 | 未查到 | 【推断】→V05 |
| 结束 | 左键松开 → `ReleasedDrag` → 请求图标桥立即重读 → 按新快照判结局。和 macOS 版相同 | — |
| 拖动途中被拖图标画在哪 | `currentImageRect` = 鼠标位置 − 抓取偏移（接口约定）。拖影相对鼠标的偏移是否等于抓取偏移 | 【推断】→V08 |

**推荐**：照上表，和 macOS 版一样只看鼠标和按键。
**备选**：① 系统定义了"拖放开始 / 结束"两个界面事件（`EVENT_SYSTEM_DRAGDROPSTART` / `END`），但官方写明系统不发，要由支持拖放的程序自己发【官方】[S107]；
Explorer 发不发未知 →V21。② 照 macOS 版探针的办法，看"拖影窗口出现了没有"来确认拖拽真的开始了【推断】。

Windows 特有的两点：

- **Esc 取消**：macOS 版不读键盘，发现不了。Windows 上同一个免权限函数可以查到 Esc 键此刻是否按着，于是能立刻知道拖拽被取消了。
  但这意味着读键盘状态（哪怕只读一个键）——是否这样做，见 §10 第 8 问。
- **右键拖动**：Windows 可以用右键拖图标，松手后弹出"移动到此处 / 复制到此处 / 创建快捷方式"的菜单。算不算拖拽，见 §10 第 7 问。

## 5. 回收站

### 5.1 读到它的位置

回收站是桌面图标之一，在 §2 的读取结果里认出它即可（§2.3）。于是：

- `TrashInfo.estimatedRect` = 回收站图标的可点击区域（图像 ∪ 标签），`confidence` = 1。
- macOS 版"公式 → 实测程序坞 → 自学习"的三级估算（input-sense 模块说明 §6）在 Windows 上**整个不需要**。
- `distance`、`closingSpeed`、`isApproaching`、`isOver` 的算法照旧（纯逻辑）。
- 交互感知要知道快照里哪个图标是回收站，这需要接口加一个标记（§1.1 第 2 条）。

可信程度：回收站是一个虚拟文件夹、有已知文件夹编号【官方】[S18]；"它默认显示在桌面上、在视图里是一个普通的项"【推断】→V01。
**备选**：识别办法见 §2.3 的备选（`CompareIDs`）。

### 5.2 图标"进了回收站"还是"挪去了别处"

图标从桌面消失时，**图标桥**要给出 `TrashVerdict`（是 / 否 / 查不出）。它能用的线索有两条：

| 线索 | 怎么读 | 可信程度 |
|---|---|---|
| ① 回收站里的项目数变多了没有 | `SHQueryRecycleBin`：取回收站的大小和项目数。对应 macOS 版的"废纸篓项目数"。文档说传空字符串或空指针会查所有驱动器的回收站，又注明从 Windows 2000 起传空指针会失败；现在的系统上该怎么传，要实测 | 接口【官方】[S54]；传法【推断】→V06 |
| ② 回收站里有没有一项"原位置是桌面、名字相同、删除时间就在刚才" | 把回收站当作文件夹来枚举，读每一项的"原位置"和"删除日期"两个属性。官方博客有完整示例（C++ 和脚本两种写法） | 【官方·博客】[S55][S56][S57] |

**推荐**：以 ② 为准，① 作为"值不值得去枚举"的快速判断（项目数没变就不必枚举）。② 查到 → 是；项目数没变、② 也没有 → 否；② 查询失败 → 查不出。
② 比 macOS 版多一个"删除时间"可以用：macOS 版会误判的罕见情形是"废纸篓里本来就有同名旧物，**而且恰好**有别的东西刚进了废纸篓"（icon-bridge 模块说明 §8.3），
这里可以靠删除时间排除。
**备选**：② 读不到原位置或删除时间时，退回 macOS 版的判断表（"同名 + 计数变多"，icon-bridge 模块说明 §8.3）。

"松手点是不是在回收站图标上"这条线索属于**交互感知**：按接口约定，图标桥给了"查不出"时，由交互感知凭自己掌握的事实（例如松手点）决定发不发删除事件（接口约定 §3.2），这一点和 macOS 版一样。

隐私：枚举回收站会接触到里面别的文件的名字。和 macOS 版一样，只在内存里比对，不保存、不输出。

**不进回收站的删除**（Shift+Delete 永久删除、回收站被设成"不保留"、文件太大、U 盘等没有回收站的位置）：
图标消失而 ①② 都没有动静 → `no`。按现有约定这种删除没有幽灵（和 macOS 版"立即删除没有幽灵"一致）；要不要改，见 §10 第 9 问。
哪些情形会绕过回收站，没有找到一份官方的完整列表【推断】→V06。

### 5.3 回收站图标被用户隐藏了

Windows 允许在"桌面图标设置"里把回收站图标从桌面上去掉【推断：常见设置项，没有核对到微软的说明页】。这时 §2 的读取结果里推断没有它【推断】→V06 → `facts.trash == nil`。

按现有约定（emotion 模块说明 §2 第 12 条）会自然得到：主角不害怕、没有围观；真被删了（比如按 Delete 键）照样出幽灵。
**推荐**：照现有约定，不做额外处理。**备选**：见 §10 第 2 问的几个选项（那是产品取舍）。

## 6. 打瞌睡的依据（对应 `DesktopIcon.modifiedAt`）

### 6.1 最近访问时间：不可靠，不用

| 事实 | 可信程度 |
|---|---|
| NTFS 对最近访问时间的更新会延迟最多 1 小时 | 【官方】[S58] |
| 从 Windows Vista 起，NTFS 默认不更新最近访问时间；Windows 10 1803 起多了一种"系统管理"的模式：处于这种模式时，只有启动卷不大于某个阈值（以 GB 计，由另一个注册表值给出；默认值未查到）的客户端电脑才更新访问时间，服务器和其余情况一律不更新 | 【官方】[S60] |
| 这个开关是全机设置，在 `HKLM` 下（改它推断需要管理员权限） | 【官方】[S59]；需要管理员【推断】 |
| FAT 文件系统上访问时间的精度只有 1 天 | 【官方】[S58] |
| 不是所有文件系统都记录访问时间 | 【官方】[S58] |
| 杀毒扫描、搜索索引、生成缩略图这类"程序替你读了一下"也会改它 | 【推断】 |

结论：同一个文件在不同电脑上表现完全不同，不能用。

### 6.2 最近修改时间：可靠，沿用

和 macOS 版同一个含义（"很久没改过"）。
**推荐**：**经 Shell 问**：属性 `System.DateModified`【官方】[S61]，通过文件夹对象的属性接口取【官方】[S64]——应用自己不去碰文件，和 macOS 版"只向访达询问"是同一个姿态。
系统图标（此电脑、回收站）推断没有这个属性【推断】→V14 → `modifiedAt` 为 nil → 不打瞌睡，接口本来就支持。
读取频率照 macOS 版：第一次读取、名字列表有变化时（包括增减和改名）、以及每分钟一次。→V14
**备选**：经 Shell 读不到时，图标桥对文件系统里的项直接读文件的属性（只读属性、不读内容）。这让姿态从"只问资源管理器"变成"自己看一眼文件的属性"，要先问总览。

### 6.3 桌面上大量的快捷方式怎么算

快捷方式是一个独立的小文件（扩展名 .lnk），里面记着怎么找到目标【官方】[S63]。它自己的修改时间通常就是创建它的那天（多半是装软件那天）【推断】。
所以按字面算，一个天天在用的程序的快捷方式也"半年没改"，会打瞌睡——意思就不对了。

| 选项 | 做法 | 好处 | 坏处 |
|---|---|---|---|
| A 快捷方式不打瞌睡 | 图标桥对快捷方式一律给 `modifiedAt = nil` | 不会出现"天天用却在睡"的错；零额外读取 | 桌面上全是快捷方式的用户几乎看不到打瞌睡 |
| B 照字面算 | 用 .lnk 自己的修改时间 | 实现最简单；情绪引擎已有"同时睡着的最多三分之一"的上限 [事实清单]，不至于全睡 | 睡不睡和用不用无关 |
| C 看目标的修改时间 | 快捷方式的目标路径是一个可读的属性【官方】[S62]，再去读目标的修改时间 | 比 B 稍有意义（软件更新过就算"动过"） | 仍然不代表"用过"；要多读一层，还可能碰到失效的目标 |
| D 看系统记录的"最近使用" | 读资源管理器私下记的使用记录 | 最贴近"很久没用" | 那是没有公开文档的系统内部数据，涉及用户的使用习惯，不该碰 |

**技术上的推荐**：A（实现最省、不会出错）；备选 C。D 不建议。这是产品取舍，由用户定（§10 第 4 问）。

### 7.3 推荐

**推荐 C#，先用 .NET Framework 4.8。** 用户给的四条标准里它占了三条（不装运行库、体积、难度）；输掉的那条"复用"用下面的办法补：

- 纯逻辑从 Swift 逐文件手工移植成 C#；
- **对拍**：macOS 版的情绪引擎是确定性的——同样的种子和输入序列永远得到同样的输出，随机数算法"跨平台结果一致"（接口约定 §5.2、§10.3）。
  但现有的"时间线打印程序"按 0.5～2 秒采样、只打印不为零的参数（emotion 模块说明 §8），不够用来逐帧比较；要先给 macOS 版加一个逐帧导出输入和输出的小工具，
  C# 版读同样的输入、逐帧比较输出。两种语言的数学函数实现不同，**逐比特一致不现实，要定容差**（例如每个参数差不超过 1e-6）。交互判断器、快照比对同理；
- 探针脚本里的 C# 代码（读图标、画框窗口、鼠标命中）上机验证通过后，就是平台层的雏形。

发布形态先 4.8；如果实测绘制性能需要 §3.8 的方式 ①、要出 ARM 版，或者想甩掉旧框架，再评估换到"新版 .NET + 原生预编译"（→V17 量体积和启动时间）。

**备选：Swift 路线**（逻辑沿用同一份代码；平台层用 Swift 直接调系统接口，个别调不顺的用一小层 C++ 转接——第二段 §13 的工作量就是按这个估的）。 适合"更看重两端规则永远是同一份代码，能接受更大的包和更重的工具链"的取舍。
上机第一天可以用一个小时判断它走不走得通（→V17）：Swift 工具链能不能在 Windows 上把 DDMCore 和 Emotion 编过并跑通它们的测试；带上运行库后整个包多大。

**不推荐 C++**（难度和风险最高，没有换来别的选项给不了的好处）。**Rust** 是体面的第二备选：单文件、体积小、编译器把关严，代价是全部重写且写的人少。

这个取舍最终由用户或总览定（§10 第 16 问）。

### 9.2 动态壁纸

Wallpaper Engine、Lively（GPL-3.0【官方】[S34]）这类软件放的是动态的桌面壁纸【官方】[S34]，推断它们的窗口在桌面图标**后面**，我们在图标前面，按理互不相干【推断】。
但它们会改变桌面窗口的层级结构，可能影响我们"找桌面窗口"和"判断显示桌面状态"的逻辑 →V22。

**推荐**：找桌面窗口时按 §3.2 的办法从系统给的桌面窗口出发、认子窗口的类名，不认顶层窗口的类名，这样不怕它们插进来的窗口【推断】。
**备选**：认不出时把这种情况当作"图标层不可见"，不画脸，并在第二段列为已知限制。

### 9.3 桌面整理类软件

Stardock Fences（付费，支持 Windows 10/11，把桌面内容收进一块块带底色的区域，可以"快速隐藏"）【官方】[S100]（厂商自己的产品页）；
腾讯桌面整理（产品页的介绍：桌面文件分类整理）【官方】[S102]（厂商自己的产品页）；360 桌面助手等同类软件在国内也很常见【推断】。

**它们是怎么接管图标的，没有查到任何技术说明**（未查到）。风险在于：图标被收进"格子"之后，系统报告的位置可能和屏幕上看到的对不上——
和 macOS 版遇到的"叠放"是同一类问题。认的办法要装上软件实测（→V22）；候选线索：桌面列表窗口不可见、大量图标位置落在屏幕外或互相重合【推断】。

**推荐**（照 macOS 版对"叠放"的原则）：认得出来就不画脸——宁可不画，也不乱画。用哪个状态表达见 §1.1 第 3 条；认出来之后是否这样做、要不要告诉用户，由用户定（§10 第 13 问）。
**备选**：尽量兼容——如果实测发现它们只是移动了图标（位置仍然读得准），就照常画。

这一条对中国用户很现实，建议开工前至少在一种国产桌面整理软件上看一眼。

### 9.4 杀毒软件误报

没有权威资料，以下都是【推断】：新发布、没签名、下载量少的程序本身就容易被"信誉"类规则拦；我们的行为里有几样看着可疑——
持续读鼠标位置、盖满全屏的置顶透明窗口、跨进程访问 Explorer。

**推荐**：设计上避开高危动作：不装钩子、不注入、不读写别的进程内存、不加壳、不联网（开机自启也是可疑行为之一，要不要做由用户定，§10 第 15 问）。
**备选**（事后）：签名（§8）；向微软提交误报【官方】[S96]；国产杀毒软件（360、火绒、腾讯电脑管家）各有申诉渠道，具体入口未查到。→V24

## 10. Windows 特有的产品问题（需要用户决定）

这里只列问题和选项，不替用户决定。技术上的影响写在括号里。

1. **回收站图标要不要有自己的脸？**
   a. 没有脸——它是那个"深渊"；b. 和别的图标一样的脸；c. 一张特别的脸（比如坏笑）——这要新增表情，而接口约定写的是"八种情绪，不再新增"。
2. **用户把回收站图标隐藏了怎么办？**
   a. 不演"害怕"那段戏，真被删了照样出幽灵（现有约定的自然结果，不用额外开发）；b. 把"拖出桌面""拖进任何窗口"都当成危险；c. 在菜单里提示一句"把回收站图标显示出来更好玩"（只提示，不替用户改设置；菜单现在只有两项，要加一项）。
3. **系统图标（此电脑、网络、控制面板、用户文件夹、Windows 11 的"了解此图片"）要不要脸？** 它们删不掉，只能隐藏。
   a. 都有脸，表现和别的图标一样；b. 只给文件、文件夹、快捷方式脸；c. 有脸，但不参与"怕被删"的戏。
4. **快捷方式怎么算打瞌睡？**（§6.3）A. 不打瞌睡；B. 照字面按它自己的修改时间；C. 按目标的修改时间。
5. **删掉一个快捷方式并没有删掉程序。它也哭得一样惨吗？** a. 一视同仁；b. 快捷方式的反应轻一些（要让情绪规则认得种类）。
6. **"显示桌面"（Win+D）时脸要不要在？** a. 要在（这时桌面最显眼；需要 §3.3 的专门处理，是风险 1 的一部分）；b. 不强求，不在也行。
7. **右键拖动算不算拖拽？**（Windows 特有，松手后弹菜单）a. 算；b. 不算，只认左键。
8. **要不要识别 Esc 取消拖拽？** a. 识别——需要查询 Esc 这一个键此刻是否按着（不记录、不读别的键），隐私说明里要如实写"会查看 Esc 键的状态"；b. 不识别，和 macOS 版一样等松手后判为"取消"。
9. **Shift+Delete 永久删除（不进回收站）要不要幽灵？** a. 不要（和 macOS 版"立即删除没有幽灵"一致，不用额外开发）；b. 要——需要另想办法区分"真没了"和"挪走了"。
10. **最低支持到哪个 Windows？** a. Windows 10 1903 及以后；b. 只支持 Windows 11（测试的组合少很多，但 Windows 10 的用户用不了）。
11. **分发走哪几条路？**（§8.3）GitHub 下载 / 开源免费签名 / 微软商店 / 包管理器。其中：商店要用证件和自拍做实名验证；开源免费签名要接受证书上的发布者显示为 SignPath Foundation、在项目主页放一页签名政策、团队开双重验证、发布物改由自动构建产出。
12. **要不要支持 ARM 的 Windows 电脑？**（§9.1）a. 支持（要多出一个版本、多测一种机器）；b. 先不支持。
13. **检测到桌面整理软件时怎么办？**（§9.3）a. 不显示脸，并在菜单里说明原因；b. 不显示脸，不说明；c. 尽量兼容（工作量和风险都不确定）。
14. **常驻的位置**：Windows 上对应 macOS 菜单栏图标的是任务栏右下角的托盘图标，但新图标默认会被收进"隐藏的图标"那个小箭头里。a. 接受；b. 第一次运行时提示用户可以把它拖出来。
15. **要不要开机自动启动？** a. 不要（和 macOS 版现状一致；也少一个杀毒软件盯的行为）；b. 在菜单里给一个开关，默认关。
16. **技术选型的取舍**（§7.3）：C# 重写逻辑（包小、省事，两端规则靠对拍保持一致）还是 Swift 复用逻辑（规则永远同一份，包大、工具链重）。

## 13. 第二段：工作拆分与测试环境

> 写于 2026-11-13，此时 macOS 版已整合（五个模块都是真实实现，见共享笔记里的《产品事实清单》）。总览对 §1.1 的决定以 [接口约定.md](../接口约定.md) §12.3 为准。
> 这一段里的行数、测试个数、类型和函数的形状，都是对着 macOS 版的源码（提交 9e09ce7）核对出来的，只读。**工作量全部是【推断】**，依据写在 §13.4。

**这一段用到的几个词**：
- **人日**：一个人干一天的活。
- **对拍**：给两个版本喂同样的输入，逐帧比较输出是否一致。
- **自动构建（CI）**：每次改完代码，自动编译、跑一遍测试。
- **沿用**：两条路线上意思不同。Swift 路线是"同一份文件直接在 Windows 上编译"；C# 路线是"照着它一行行翻译成 C#"。
- **重写**：两条路线都要为 Windows 新写。
- **回归**：改完以后把原来的测试和检查再跑一遍，确认没改坏。
- **仿射变换**：图形的平移、旋转、缩放。**光栅化**：把图形画成像素。**画布池**：画好的位图画布反复使用，不每次新建。
- **执行器**：决定一段代码在哪条线程上运行的那一层。**防抖**：一个状态要连续成立一小段时间才算数，免得来回跳。
- **vCPU**：云电脑里的处理器核数。

### 13.0 先说结论

- **开工第一步**：改 DDMCore 的两处——快照里标出回收站、写明 Windows 上的坐标约定。核实下来，**这两处改动本身不需要 macOS 各模块改代码**，只补文档和一两个测试（§13.1）。
- **两处要更正或补充**（§13.1.1）：
  - 接口约定 §12.3 和本方案 §1.1 都说"交互感知的调参表能在构造时传入"，与代码不符；
  - "1 点 = 1 像素"不只影响情绪和交互的手感常数，也影响表情绘制里按点定的几个门槛。
- **代码能沿用多少**：macOS 版 11,895 行源码里，
  - 约 4,900 行可以直接沿用；
  - 约 3,000 行大部分沿用、要改一部分；
  - 约 2,600 行要为 Windows 重写；
  - 约 1,300 行在 Windows 上用不着（程序坞估算、访达特有的读取办法）（§13.2）。
- **工作量**【推断】：C# 路线约 49–76 人日，Swift 路线约 47–72 人日（§13.4）。
  - 总量相近，性质不同。C# 路线要把逻辑再写一遍，以后每改一条规则都要改两处。
  - Swift 路线（逻辑和平台层都用 Swift，个别调不顺的系统接口用一小层 C++ 转接）逻辑只有一份，但要**由总览改 DDMCore 的两个绘制接口和工程清单**，并改 macOS 的几乎每个模块（§13.4 差别表）。

- **子任务**：C# 路线拆成 9 个子对话、Swift 路线 8 个，外加总览自己做的 2 件事（§13.5）。每个子任务标明：开工前必须跑完哪些上机验证、验收前还要补哪些、依赖哪几个产品问题。产品问题建议**分两批问**：10 个现在就能问，6 个要等验证结果。

  - 它能完整做 26 项验证里的 15 项，部分做 9 项；做不了的 2 项都是量性能的。
  - 真实的多屏缩放、性能、Windows 10、普通家用电脑上的拦截提示和国产杀毒软件，要靠一台 **x64 真机**：最晚在整合阶段的验收前要有；想让叠加层一次选对绘制方式的话，叠加层开工时就要有。

#### 13.1.1 更正与补充：手感常数按缩放换算

1. §12.3 写的是"两个模块的调参表本来就能在构造时给"。核实结果：

- C# 路线对 macOS 没有影响，C# 版自己给交互感知加参数。

**两种组合，供用户选**（不替用户定）：

- **省钱的组合**：
  1. 先在这台 Mac 上用免费的虚拟机软件加评估版，跑第一组和第二组的大部分。这样各子任务"开工前"要的验证项基本都能做（§13.5）。
  2. 需要 x64 时，用 Windows 365 的 30 天试用补（前提是愿意以组织身份开通），或者用 Azure 的新用户额度补。
  3. **仍然缺** V10、V11、V25（真实多屏、性能）、V20 的 Windows 10、V18 和 V24 在普通家用电脑上的表现。这几项都在各子任务的"验收前"一栏（§13.5），所以最晚在第 5 步（win-shell 验收前）要有一台真机；想让叠加层一次选对绘制方式，叠加层开工时就要有。
- **一步到位的组合**：借或买一台 x64 Windows 笔记本，接一块外接屏，除 V17a、V20（要几个系统版本）以外一次做完；ARM（V26）用这台 Mac 上的虚拟机补。

### 13.8 第二段新增的、需要用户决定的事

只列问题和选项。

1. **Windows 版的应用图标要不要去掉 macOS 风格的圆角方形底板？** a. 保留，两个平台长得一样；b. 去掉底板，只留图形，更像 Windows 的应用图标。（托盘图标无论选哪个，都要做深色、浅色两版。）
