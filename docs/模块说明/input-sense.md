# 交互感知（InputSense）模块说明

> **归属** input-sense · **代码** `Sources/InputSense/` · **测试** `Tests/InputSenseTests/` · **演示** `Demos/InputSenseDemo/`
>
> 交互感知负责"看懂用户在干什么"：鼠标在哪、停在哪个图标上、正在拖哪个、甩得多猛、离废纸篓多近、松手后这个图标怎么样了。
> 它只给出事实和数值，这些事实对应什么情绪归情绪模块。接口定义见 [接口约定.md](../接口约定.md) 第 3 节，
> 这里只讲本模块自己的结论、做法、实测数据和限制。
>
> **它向系统打听的东西**，全部是只读查询、不需要任何系统授权：
> 鼠标的位置和按键（每帧问一次"现在是什么状态"，不是监听事件）；
> "鼠标点在某个点上会落到哪个窗口"，以及窗口的所属进程、层级、边界、透明度（**不读窗口标题**）；
> 程序坞自己的偏好设置（靠哪边、图标大小、放大、自动隐藏、常驻项目列表）和正在运行的应用列表——后两样只用来**数程序坞里有几项**，不保存、不输出。
> 它不产生、不拦截、不修改任何输入事件，不改任何系统设置，不读任何用户文件。
> 唯一写入的东西：学到的废纸篓位置（几个数字），存在应用自己的偏好设置里。
>
> 文中所有实测都在 macOS 27.0.1（Apple Silicon）、内屏 1512×982 @2x（主屏）+ 左侧外接屏 1920×1080 @1x 的机器上完成，
> 开发期间用户正在使用这台电脑（两块屏多数时候停在全屏应用的空间里，系统设置里桌面项目是隐藏的）。
> 凡是需要真人动鼠标、或者需要桌面图标显示出来才能验证的，列在 §9 的人工检查清单里。

## 1. 结论一览

| 问题 | 结论 | 把握 |
|---|---|---|
| a. 窗口查询要多久 | "某个点上最上面是什么窗口"一次 0.02 毫秒（连着问）～ 0.2–1 毫秒（隔一会儿问一次，这才是实际情形）；整份在屏窗口列表 0.2 ～ 3 毫秒；全部窗口列表 4 毫秒。后两样只在后台线程用 | 已实测（§5） |
| a. 悬停判断每秒几次 | 鼠标移动时每秒 15 次；**按键按下或松开的那一帧立刻查，进入一个图标时尽快查**（最多再等 1/30 秒）；停在图标上每秒 2 次；停在空白处每秒 1 次；拖着或按着键时每秒 5 次 | 已实测：`update` 平均 0.02～0.04 毫秒；要查窗口的那些帧 0.2～1 毫秒（§5） |
| b. 废纸篓估算 | 三级：**公式**（按程序坞设置推算，可信度 0.45）→ **实测**（量出程序坞那一条此刻的实际范围，废纸篓是末端那一格，0.75）→ **自学习**（真的删过之后用松手点修正，0.7～0.95） | 程序坞那一条的范围：公式与实测相差 0～5 点（已实测）。废纸篓那一格在这一条里的位置：**待用户配合**（§6.4，§9 第 3 项） |
| c. 自动隐藏 / 放大 / 左右 / 外接屏 | 外接屏：跟着程序坞窗口走，已在本机实测（程序坞在两块屏之间换过）。自动隐藏、放大、左右两侧：有处理、有单元测试，但本机都没开，**没有真机验证过** | §7 |
| d. 起拖阈值 | 系统的起拖距离参数是 4×4 点，判断器按 4 点（横向或纵向）起拖。访达实际的阈值、拖影偏移是否等于抓取偏移：**待用户配合**，量它的探针已备好 | §8，§9 第 5、6 项 |
| 遮挡判断 | 用窗口服务器自己的命中规则判断"鼠标点在这里会落到谁身上"，只有落在访达的桌面图标窗口上才算。系统用来遮住图标的那块窗口**会接住点击**，直接认得出来 | "被遮住"已在本机实测（§4.4）；"图标看得见"这一面**待用户配合**（§9 第 2 项） |
| 结局判定 | 挪了位置 / 进了废纸篓 / 离开桌面去了别处 / 取消 / 超时未知，外加没有拖拽过程的删除 | 逻辑有 50 多个单元测试；与真实图标桥的联动**待整合阶段验证** |

**需要总览知道的两件事**：

1. 这台机器的桌面项目是被系统隐藏的，所以在这台机器上交互感知平时不会报任何悬停和拖拽（鼠标处最上面是那块遮挡窗口，不是访达的图标窗口）——这是对的。需要真实图标的验证，前提都是用户先让桌面项目显示出来。
2. 废纸篓估算最关键的一个数（废纸篓那一格离程序坞末端多远）没有办法自己验证：当前环境没有"辅助功能"权限（没有申请），只能请用户把鼠标停在废纸篓上读一次偏差（§9 第 3 项，半分钟）。

## 2. 怎么用（给总览的集成注意事项）

```swift
let sensor = InteractionSensor()                 // 应用里就这样构造；入口类型名和构造方式没变
let facts = sensor.update(time: time, icons: iconUpdate)   // 每帧一次
if facts.wantsIconRefresh { icons.refreshNow() }
sensor.reset()                                   // 暂停后恢复、桌面重新可见时
```

现有的 `FramePipeline` 一行都不用改。

1. **没有定时器、没有常驻的后台任务。** 一切读取都发生在 `update` 里（或由它发起）；没人调用 `update` 就什么都不读。
   暂停或桌面不可见时开销为零。少数较慢的读取（程序坞设置、显示器布局、图标是否被遮住）由 `update` 发起、在后台线程做完，结果下一帧用上。
2. **务必按 `facts.demand` 出帧。** 鼠标 0.5 秒内动过、有按键按着、正在拖：`.continuous`；停在图标上：每 33 毫秒；
   停在别处：每 100 毫秒，静止超过 30 秒后每 200 毫秒；松手后等结局期间：最迟到下一次该请求重读图标的时刻。
   不要比它更稀——停在图标上那一档是为了尽快看到"按下"，读得太稀，起拖会晚、抓取偏移会不准。
3. **`wantsIconRefresh` 的节奏**：松手的那一帧、0.15 秒、0.3 秒各一次，之后每 0.35 秒一次，结局一出就停（最多到 3 秒超时，共 10 次）。
   典型情形：挪位置 1～2 次重读；拖进废纸篓 1～2 次；取消——松在桌面上 3 次，松在窗口或程序坞上 5 次。
   图标桥自己保证相邻两次读取至少隔 0.15 秒，所以每帧照办就行。
4. **松手到结局之间**（`releasedDrags` 不为空）被拖图标的脸画在哪，由情绪模块决定；建议画在 `ReleasedDrag.imageRectAtRelease`——
   这时快照里它还在原位置，访达的新位置要等重读才知道。"挪了位置"最快约 0.1 秒确认；
   "取消"是故意多等一会儿才下的结论（§4.6）：松在桌面上约 0.4 秒，松在窗口、程序坞上约 1.1 秒。
5. **多选拖拽只认鼠标抓住的那一个**（已知限制）。一起被拖进废纸篓的其它图标会各自得到一条 `DeletionEvent`（`wasDragged == false`），所以幽灵一个不少。
6. **`isMouseOverDesktop` 在拖拽期间也有效**（每秒查 5 次，查的时候跳过系统的拖影和本应用自己的窗口）。但它最多可能旧 0.2 秒；按下、松开的那一帧是现查的。
7. **`TrashInfo.isApproaching` 停在废纸篓上方不动约 0.3 秒后会变回 false**（字面意思：没在朝它移动了）。"在废纸篓上方"请看 `isOver`。
8. **废纸篓的估算区域按可信度留了余量**：可信度越低，`estimatedRect` 沿程序坞方向越宽（只靠公式时两边各多留约 0.3 格）。
   所以 `isOver` 在估算不准时宁可多报一点。是否真的删了不看它，看 `DragOutcome` / `DeletionEvent`。
9. **隐私说明要如实写**（给 release）：除了鼠标位置和窗口的层级边界，本模块还会读**程序坞的偏好设置**（含常驻项目列表）和**正在运行的应用列表**，
   用途只有一个——数程序坞里有几项，好推算废纸篓在哪。不保存、不上传、不输出。
   应用自己的偏好设置里多一个键 `InputSense.trashLessons`（学到的废纸篓位置：程序坞设置的指纹 + 松手点的偏差，纯数字）。
10. **打包后的 .app 身份下**，以上读取应当都不弹任何授权窗口（它们都不是受保护的资源；命令行身份下实测不弹）。请在整合阶段首次真机启动时确认一次。
    将来如果应用要进沙盒，读程序坞的偏好设置会失败——那时公式这一级就没有输入了（会退回"底部、48 点、项目数未知"的默认值），实测和自学习两级不受影响。
11. **窗口服务器的连接**：`LiveEnvironment` 构造时会取一次 `NSApplication.shared`（应用里本来就有；命令行程序里是为了能问窗口服务器），不激活、不建窗口。
12. **排查问题**：`sensor.lastSurface`（最近一次查到鼠标处最上面是什么：桌面图标层 / 被遮住的桌面 / 别的窗口 / 查不出来）、
    `sensor.surfaceSampleCount`；`(sensor.environment as? LiveEnvironment)?.diagnostics`（程序坞靠哪边、几项、在哪块屏、量到的范围、学了几次）。都不含用户数据。

## 3. 结构

分成两部分，中间只隔着一个很窄的接口（`SensorTypes.swift` 里的 `InteractionEnvironment`）：

```
InteractionSensor（入口：把下面两部分接起来，自己没有逻辑）
├── 纯逻辑的判断器 —— 不读时钟、不读系统、不依赖 AppKit，同样的输入永远得到同样的输出
│   ├── InteractionJudge     一帧的全部判断：按下 / 起拖 / 松手 / 悬停 / 结局 / 删除 / 省电信号，以及"现在该不该查一次窗口"
│   ├── PointerMotion        速度（平滑）、静止时长
│   ├── ShakeMeter           甩动强度
│   ├── TrashApproach        到废纸篓的距离、靠近速度、"正朝它移动"（防抖）、是否在上方
│   └── TrashEstimator / DockModel / DockBarScan   废纸篓在哪：公式、量程序坞的算法、自学习
└── 读系统的薄薄一层 —— InteractionEnvironment
    ├── LiveEnvironment      真实实现
    │   ├── WindowProbe        某个点上最上面是什么窗口；图标是否被系统遮住
    │   ├── SystemDockReader   程序坞的设置、所在显示器（后台读）；量那一条（主线程，4 次查询）
    │   └── TrashLocator       什么时候去读、去量；学到的位置存在哪（`PersistentTrashMemory`）
    └── SimulatedEnvironment 模拟实现：鼠标、窗口、程序坞都是编的，给演示的"剧本回放"用
```

判断器的输入是"时间 + 鼠标 + 图标快照与变化事件 + 废纸篓估算"，外加一个回调"这个点上最上面是什么窗口"——
判断器自己决定什么时候值得问（那是一次系统查询），不需要时不问。图标快照和变化事件由应用从图标桥转交，本模块不依赖图标桥。

| 文件 | 内容 |
|---|---|
| `InteractionSensor.swift` | 模块入口 |
| `SensorTypes.swift` | 两部分之间的接口：`PointerSample`、`PointerSurface`、`TrashEstimate`、`InteractionEnvironment` |
| `InteractionJudge.swift` | 判断器，以及全部可调参数（`JudgeTuning`，每个都有注释） |
| `PointerMotion.swift` · `ShakeMeter.swift` · `TrashApproach.swift` | 速度与静止时长 · 甩动强度 · 与废纸篓的关系 |
| `TrashEstimator.swift` | 程序坞的几何模型、废纸篓估算、自学习、量程序坞的算法（全是纯函数） |
| `TrashLocator.swift` | 读取的时机、测量结果的有效期、学到的位置的存取 |
| `LiveEnvironment.swift` · `WindowProbe.swift` · `DockReader.swift` | 读系统的真实实现 |
| `SimulatedEnvironment.swift` | 读系统的模拟实现 |

## 4. 各项事实是怎么定的

### 4.1 鼠标

- **位置、按键**：每次 `update` 读一次。位置换算成全局坐标（用 DDMCore 的换算）。
- **速度**：相邻两次读数的位移 ÷ 间隔，再做指数平滑（时间常数 0.05 秒）。停稳后归零。
- **静止时长**：位置没变的时间。一动就归零；`reset()` 之后从零算起。
- **读取频率**：见 §2 第 2 条。实测鼠标停着不动时每秒读约 10 次（`swift run InputSenseDemo --live`）。

### 4.2 悬停

鼠标下面有图标（`DesktopIcon.hitTest`：图像或标签）、没有任何按键按着、没在拖、而且**该处最上面的窗口是访达的桌面图标层**，才算悬停。
时长从满足条件的那一帧算起；离开再回来、换一个图标都重新计时；在同一个图标的图像和标签之间移动不重新计时。
鼠标进入一个图标后，要等查过一次窗口才开始算悬停（通常就在当帧，最多晚 1/30 秒），所以悬停不会建立在进来之前的遮挡结果上。

### 4.3 拖拽

- **开始**：左键**单独**按下（右键、中键同时按着的不算）时鼠标在某个图标上、该处是桌面图标层，之后在左键没松开的情况下，
  鼠标离按下点的横向或纵向距离达到 **4 点**。单击、双击、右键、按住不动、在空白处按下再划过图标，都不算。
- **按下点**：我们只在每帧读一次鼠标，按下发生在两帧之间。系统说得出"最近一次左键按下是多久以前"（不需要授权），据此折算：
  上一帧鼠标是停着的 → 按下点就是停着的位置（人总是先停稳、按下、再移动）；上一帧鼠标在动 → 在两帧的位置之间按时刻比例取。
  这套折算只在两次读数相隔不超过 0.05 秒时用；隔得更久（鼠标静止时每 0.1～0.2 秒才读一次）说明鼠标是这一段里才挪过来的，按下点取当前位置。
  读不到这个时刻也用当前帧的位置。松手点同理。这样**抓取偏移**（按下点 − 图像矩形左上角）不会因为"按下后鼠标已经走了一段"而偏掉。
- **进行中**：位置、速度同鼠标；`currentImageRect` = 鼠标位置 − 抓取偏移。
- **甩动强度 0…1**：把轨迹每 24 点切成一段，相邻两段之间拐的弯（减去 0.12 弧度的死区）按"拐弯之前这一程最快有多快"加权
  （400 点/秒以下不算，3000 点/秒以上算满），累进一个 0.6 秒衰减的能量里，强度 = 1 − e^(−能量)。
  直线和平缓的弧线是 0；来回甩每次掉头拐 180°；画圈也算，但比来回甩温和。停手后 1～2 秒回落。

  | 动作（鼠标轨迹） | 强度 |
  |---|---|
  | 直线拖动 900 点/秒 | 0.00 |
  | 慢悠悠地左右晃（每秒 1.5 个来回，幅度 ±60 点） | 0.07 |
  | 每秒 2 个来回，±80 点 | 0.30 |
  | 每秒 2.5 个来回，±100 点 | 0.58 |
  | 每秒 3 个来回，±100 点 | 0.72 |
  | 使劲甩（每秒 4 个来回，±120 点） | 0.95 |
  | 画圈（每秒 2.5 圈，半径 110 点） | 0.40 |

  这些档位是按编出来的正弦轨迹定的；真人甩起来顺不顺手**待用户配合**（§9 第 4 项），不顺手只需要调 `ShakeMeter.Tuning` 里的三个数。
- **Esc 取消**（左键还按着）看不到键盘，发现不了：拖拽状态会持续到松手，然后结局判为"取消"。见 §10。

### 4.4 遮挡判断

问窗口服务器"鼠标点在这个点上会落到哪个窗口"（`NSWindow.windowNumber(at:belowWindowWithWindowNumber:)`）。
这用的是系统自己的命中规则：窗口透明的部分、不接收点击的窗口都会被跳过。所以：

- 本应用的叠加窗口（点击穿透）天然不会被命中；万一命中了本进程的窗口，或层级是"系统拖影"的窗口，就再问它下面的那个。
- 程序坞的窗口是整屏大小的透明窗口——按窗口边界算它"盖住"了整个桌面，按命中规则只有那一条才算。这是不用窗口列表做几何判断的原因。
- 落到的窗口**层级是桌面图标层、所属进程是访达** → `desktopIcons`，只有这一种才算"在桌面图标上"。
- 层级是桌面图标层、但不是访达的 → `shieldedDesktop`：系统用来遮住图标的那块窗口。
- 程序坞的窗口 → `dock`（就是程序坞那一条）。松手时落在它上面，"取消"会多等一会儿，松手点才有资格用来学废纸篓的位置。
- 其它 → `otherWindow`；查不出来 → `unknown`。除了第一种，都不会有悬停，也不会开始拖。
- 一个窗口"是谁的、在哪一层"查过之后记 60 秒（查一次也是一趟往返）；唯独"桌面图标层上、不是访达"这个结论只记 3 秒——
  访达刚重启时可能一时查不到它的进程信息，不能因此把桌面当成被遮住一分钟。

**本机实测**（开发期只读探针，每秒在外接屏上取 23×15 个点问一遍，持续约 4 分钟，期间用户在正常使用）：

- 桌面图标被系统隐藏、遮挡窗口在位时：露出墙纸的点全部落在"系统窗口管理程序、桌面图标层"的窗口上（每次 53～60 个点），
  **从来没有一个点落到访达的图标窗口上**。也就是说遮挡窗口会接住点击，直接认得出来。
- 切换桌面空间的过渡期间，遮挡窗口会短暂地不在窗口列表里（叠加层的说明 §6.3 也观察到了），这时那些点落在一个过渡用的窗口上，同样不是访达的图标窗口。
- 所以在这台机器上，鼠标在墙纸上时 `lastSurface` 是 `shieldedDesktop`，不会有悬停和拖拽。

作为后备（万一别的系统版本上遮挡窗口不接点击）：落到访达的图标窗口时，再按窗口次序核对一遍"同一层级、它前面有没有别的进程的整屏窗口"
（与叠加层的判断方法一致）。这要看整份窗口列表，所以结果记着用，每 0.5 秒在后台线程复查，只在鼠标确实落在访达图标窗口上时才查；
记着的结果超过 5 秒没更新（例如应用暂停了一阵）就不再用，当场重查一次。显示器布局同样：每秒在后台重读，旧到超过 5 秒就当场重读。

**没有验证的一面**：桌面项目显示出来时，落到的是不是访达的图标窗口（层级、所属进程是否如预期）。访达的图标窗口本身在窗口列表里看得到
（层级 −2147483603，每块屏一个），但这台机器上它前面一直有遮挡。见 §9 第 2 项，十秒钟的事。

### 4.5 废纸篓

见 §6、§7。`TrashInfo` 的其余字段：

- `distance`：鼠标到估算区域的最短距离；在区域内为 0。
- `closingSpeed`：距离的减小速度（平滑后的鼠标速度在"指向区域上最近一点"方向上的分量）；在区域内为 0。
- `isApproaching`：靠近速度 ≥ 60 点/秒、且占总速率一半以上，连续成立 0.08 秒才变成 true；
  靠近速度 < 20 点/秒或占比 < 0.3，连续成立 0.3 秒才变回 false。朝废纸篓去的路上手顿一下不会来回跳。
- `isOver`：鼠标在估算区域内。

### 4.6 结局判定

松手的那一帧，拖拽变成 `ReleasedDrag`，同时请求重读图标。之后：

| 看到什么 | 结局 | 备注 |
|---|---|---|
| 图标的消失事件，图标桥说"进了废纸篓" | `trashed` + `DeletionEvent` | 同一帧。`lastImageRect` 是被抓起时的原位置。松手处最上面是程序坞的话，松手点记下来用于自学习 |
| 消失事件，"没进废纸篓" | `leftDesktop` | 不发删除事件 |
| 消失事件，"查不出来" | 松手点在废纸篓估算区域内、且估算可信度 ≥ 0.6 → `trashed` + `DeletionEvent`；否则 `leftDesktop` | 拿不准就不"送葬"。这种认定不用于自学习 |
| 松手**之后**才开始读的快照里，图标的位置和原位置不同 | `moved`，`newImageRect` 取快照里的 | 访达可能吸附到网格，以它为准 |
| 松手之后过了**稳定期**才开始读的快照里，图标还在原位置 | `cancelled` | 稳定期：松在桌面上 0.28 秒（防"访达还没来得及更新"）；松在别处（程序坞、窗口、别的应用）0.95 秒——那时访达可能要真的去搬文件，等短了会把"拖进废纸篓但慢了半拍"先判成取消。等待期间一旦看到位置变了或图标消失，立即按上面几行下结论 |
| 松手之后读的快照里图标不在了，却没有收到它的消失事件（只有整体重载会这样） | 同"查不出来"那一行 | 例如拖拽期间访达一时没有回应，图标桥超时后恢复，只给一份新快照 |
| 松手后 3 秒仍无结论 | `unknown` | 例如图标桥读不到访达 |

- "松手之后"的判断用快照的 `capturedAt`（读取开始的时刻）和松手时刻比；松手之前读的快照不用来下结论。
- **"拖动途中访达报告的位置不变、松手后才更新"这条假设如果不成立**（待用户做图标桥的拖动检查才知道）：
  途中来的"位置变了"事件不会被当成结局（拖着的时候不看它们）；松手后照样按"松手之后读到的位置和原位置比"下结论。不会出错。
  如果是另一种不成立——松手后访达很久甚至永远不更新位置——结局会是"取消"或"未知"，脸回到快照里的位置。这需要图标桥那边换方案，本模块无能为力。
- **没有拖拽过程的删除**（快捷键、右键菜单）：消失事件 + "进了废纸篓" → `DeletionEvent`（`wasDragged == false`），位置是它消失前的位置。
  "没进"和"查不出来"都不报。发现的早晚取决于图标桥的轮询（活跃时约 1 秒）。
- **`wasDragged == true` 的删除事件一定同帧带着一条 `trashed` 结局**（接口约定 §3.2 的原话）。所以一次拖拽已经判了"取消""未知"或"挪了位置"，
  之后这个图标才被报告进了废纸篓时，照样发 `DeletionEvent`，但 `wasDragged` 为 false——结局已经给过了，这一条按普通删除报。
- 松手和图标的消失事件落在同一帧（主线程卡了一下）：按"松手之后消失"结算，`ReleasedDrag` 不会出现，直接给结局。
- 左键还没松，图标就从桌面消失了（例如被别的程序删掉）：拖拽当场结束，按上表下结论；但"查不出来"时不凭鼠标位置认定被删（用户并没有松手），这个位置也不拿去学。
- 按着还没拖起来，图标就消失了：这次按下作废。
- **整体重载**（`isReset`）：按着还没拖起来的作废；正拖着的继续拖，"原位置"按新快照重取；等着结局的照常按新快照下结论。
  如果这次重载是因为图标大小或显示器排列变了（所有矩形一起变），等着结局的那一个可能被误判成"挪了位置"——很少见，后果只是一次多余的"虚惊一场"。
- 上一次的结局还没出来，同一个图标又被拖走：上一次记为 `unknown`。

## 5. a. 窗口查询要多久，悬停判断每秒做几次

`swift run -c release InputSenseDemo --bench`。"连着"是一口气调很多次；"隔着"是每隔 50 毫秒调一次——应用里的查询都是隔一会儿才来一次，
这时系统那边的缓存是凉的、窗口服务器要被叫醒，比连着调慢一个数量级，而且随系统忙闲波动很大。**做预算要看"隔着"的数。**

| 查询 | 连着（中位） | 隔着（中位 / 95%） | 在哪个线程用 |
|---|---|---|---|
| 读一次鼠标（位置、按键、最近按下/松开的时刻） | 0.0002 毫秒 | 0.004～0.008 / 0.03～0.18 毫秒 | 主线程，每帧 |
| 某个点上最上面是什么窗口 | 0.02～0.04 毫秒 | 0.17～0.94 / 0.4～3.9 毫秒 | 主线程，限频（见下） |
| 在屏窗口列表，整份（12～21 个窗口） | 0.17～0.30 毫秒 | 0.86～3.3 / 1.0～4.0 毫秒 | **后台** |
| 全部窗口列表（约 340 个窗口） | 3.4～6.2 毫秒 | — | **后台**，只在程序坞窗口不在屏上时找它用 |
| 显示器布局 | 0.05～0.13 毫秒 | 0.28～0.97 / 0.4～4 毫秒 | **后台**，每秒一次 |
| 数一遍正在运行的应用（估程序坞项目数） | — | 约 10 毫秒 | **后台**，每 3 秒一次（鼠标静止超过 10 秒后每 30 秒一次） |

每一格里的范围是同一天里三次运行的最好和最差：机器闲的时候（第三次）"某个点上最上面是什么窗口"隔着问的中位数是 0.17 毫秒，
忙的时候（第二次，别的对话正在编译）是 0.94 毫秒。这类查询是和窗口服务器的一趟往返，快慢主要取决于系统当时忙不忙，我们控制不了，只能少问。

**悬停判断的频率**，以及为什么是这些数：

| 情形 | 多久查一次窗口 | 理由 |
|---|---|---|
| 按键按下、按键松开 | **当帧立刻查** | "点在图标上"的认定、松手处是什么，不能建立在旧结果上 |
| 鼠标进入一个图标 | **尽快查**：离上一次查询满 1/30 秒就查 | 悬停不能建立在进来之前的结果上。留 1/30 秒的间隔是为了飞快扫过一排图标时不至于每帧都查 |
| 鼠标在动 | 每秒 15 次 | 只为让"是否在桌面上"别太旧，以及发现"从图标露出的一半挪到了被挡住的一半"。再勤没有意义——图标只有几十点宽。离开图标不用急着查（没有图标就没有悬停） |
| 鼠标停在某个图标上 | 每秒 2 次 | 发现"窗口自己冒出来盖住了图标"（最迟 0.5 秒悬停消失）。不必更勤：图标被窗口盖住时脸也被盖住了，晚半秒是看不见的 |
| 鼠标停在别处 | 每秒 1 次 | 这时答案几乎不影响任何判断 |
| 正在拖，或者有键按着（框选、拖别的窗口） | 每秒 5 次 | 不可能有悬停，只维持 `isMouseOverDesktop` |

合起来：鼠标移动时通常每秒查 15 次，飞快扫过一排排图标时最多每秒 30 次。

**整个 `update` 的开销**（发布版，30 个假图标，连续出帧 3 秒，鼠标由用户在正常使用——演示不会去动鼠标）：

| 哪一次运行 | 3 秒里查了几次窗口 | 平均 | 中位 | 95% | 最大 | 超过 0.5 毫秒的帧 | 折合占用一个核心的 |
|---|---|---|---|---|---|---|---|
| 机器忙时 | 7 | 0.043 毫秒 | 0.022 | 0.047 | 1.44 | 145 帧里 2 帧（0.64、1.44） | 0.2% |
| 机器闲时 | 3 | 0.016 毫秒 | 0.009 | 0.025 | 0.31 | 130 帧里 0 帧 | 0.07% |
| 改完审阅意见之后，机器忙时 | 3 | 0.053 毫秒 | 0.029 | 0.041 | 2.98 | 145 帧里 1 帧（第一帧，2.98：头一次查窗口） | 0.26% |

不查窗口的帧（绝大多数）只有读鼠标和纯逻辑，0.01～0.02 毫秒。要查窗口的帧多一趟往返：闲时约 0.2 毫秒，忙时可能到 1 毫秒以上——
**这样的帧会超过 0.5 毫秒的目标**。鼠标一直在动时这样的帧通常每秒 15 帧（飞快扫过图标时最多 30 帧），按上表推算合计每秒 3～14 毫秒（0.3%～1.4% 的一个核心）；
没法再往后台挪（这个查询只能在主线程做），所以办法是限频。它不会造成掉帧（一帧的预算是 16 毫秒）。
鼠标不动时每秒只读约 10 次（静止 30 秒后 5 次），其中每秒查 1 次窗口，开销再低一个数量级。

改到现在这个样子之前量到过的两个坑，记下来免得以后有人改回去：

- 数一遍正在运行的应用要约 10 毫秒，在主线程上做会每隔几秒卡一帧——所以程序坞的设置整个放到后台读。
- 一开始鼠标移动时每秒查 30 次窗口、每秒在主线程读一次显示器布局、每半秒看一次整份窗口列表，同样的测法 `update` 的平均是 0.33 毫秒、
  95% 分位 1.2 毫秒、最大 12.6 毫秒；收紧频率并把后两样挪到后台之后是上表的样子。

## 6. b. 废纸篓估算

### 6.1 思路

废纸篓永远是程序坞的最后一项：程序坞在底部时是最右边那个，在左右两侧时是最下面那个。
所以"废纸篓在哪"= "程序坞那一条在哪 + 最后一格占多宽"。三个信息来源，可信度依次升高。

### 6.2 第一级：公式

**用到的程序坞设置项**（偏好设置域 `com.apple.dock`，只读）：

| 键 | 用途 |
|---|---|
| `orientation` | 靠哪边：`bottom` / `left` / `right` |
| `tilesize` | 图标大小（点） |
| `magnification`、`largesize` | 是否放大、放大后的大小 |
| `autohide` | 是否自动隐藏（只进设置的"指纹"，不影响公式） |
| `persistent-apps`、`persistent-others` | 常驻的应用、文件夹和文稿：数个数（占位空格算一格，小的算半格） |
| `recent-apps`、`show-recents`、`static-only` | "最近使用的应用"那一段有几项 |

再加上：正在运行的普通应用里，有几个不在常驻应用中（它们也各占一格）；程序坞所在的显示器（看程序坞窗口的边界，它和所在显示器一样大）。

**项目数** N = 访达 1 + 常驻应用 + max(运行中但不常驻的应用数, min(3, 运行中但不常驻的 + 最近使用但没在运行的)) + 常驻的文件夹文稿 + 废纸篓 1。
分隔线 S = 1 条，有"运行中 / 最近"那一段时 2 条。

**几何**（单位点；W 是程序坞所在那条边的长度）：

```
每一项占的宽度   p0 = tilesize + 4.5
那一条的长度     L0 = N × p0 + 2 × 10 + S × 12          （两端各留 10，每条分隔线 12）
放不下时         若 L0 > W − 2 × 34：  L = W − 68，  p = (L − 20 − 12 S) / N     （图标被自动缩小）
                 否则：                L = L0，       p = p0
那一条的厚度     T = p + 12.5                              （从屏幕边缘算起的可点击范围）
那一条的位置     沿所在的边居中，贴着屏幕边缘
废纸篓那一格     从那一条的末端往里 10 点开始，宽 p，厚 T
```

**这些常数的来历**：都是从本机的实测反推的，而且本机的程序坞一直处于"项目多到放不下、被挤满"的状态（设置里图标大小 64，共 32 项）。
"放得下"那一支（`p0 = tilesize + 4.5`）**没有校准过**。另外 4.5、12.5、10、12 这四个数里只有它们的两个组合是被数据钉住的
（"厚度 − 每项宽度"和"两端留白 + 分隔线"分不开），单个数是合理的猜测。这就是公式这一级只给 0.45 的原因。

### 6.3 第二级：实测程序坞那一条的范围

程序坞的窗口是整屏大小的透明窗口，只有那一条接收鼠标点击。所以"鼠标点在这个点上会落到程序坞窗口"的那些点就是那一条。
从所在那条边的中点出发，用二分法找出厚度和两端，一共三十来次查询（`DockBarScan.measure`）；之后每次只花 4 次查询核对
"上次量到的范围还成立吗"（厚度内外各一点、末端内外各一点），对不上才重新量。平时每 10 秒量一次，**一开始拖立刻量一次，拖拽期间每 0.5 秒一次**。

量到之后，废纸篓那一格 = 末端往里 10 点、宽 `T − 12.5`、厚 `T`。这一级不需要知道项目数，也不依赖"放得下 / 放不下"，所以可信度给 0.75。
程序坞不在屏上时（全屏空间里、自动隐藏着）量不到：沿用上一次量到的范围（前提是设置、项目数、显示器都没变，且不超过 5 分钟），否则退回公式。
前提一变（比如多开了一个应用），旧的测量当帧作废并立刻重新量，不等下一个 10 秒。

**本机上的误差**（开发期间程序坞露出来的几次，都在外接屏底部，外接屏 x 从 −1920 到 0、底边 y = 1022）：

| 时间 | 估计项目数 | 量到的那一条（x 范围，厚度） | 公式推算 | 两端相差 | 厚度相差 |
|---|---|---|---|---|---|
| 约 12:25（后台探针逐点扫描，连续 14 次相同） | 32 | −1886 … −34，厚 69 | −1886 … −34，厚 69 | 0 / 0 | 0 |
| 约 13:00（`--bench`） | 32 | −1885 … −37，厚 66 | −1886 … −34，厚 69 | +1 / −3 | −3 |
| 约 13:05（逐点扫描 + `--bench`） | 32 | −1882 … −38，厚 73 | −1886 … −34，厚 69 | +3～4 / −4～5 | +4 |

第一行是公式的常数所依据的那次测量，所以"相差 0"不算验证；后两行是独立的。另一个独立的印证：程序坞在内屏时系统报告的底部留空是 56 点，
公式对内屏（宽 1512）算出的厚度是 56.0。结论：**程序坞那一条的两端，公式与实测相差不超过 5 点；厚度相差不超过 4 点**
（项目数没变时那一条自己也会有几点的变化，原因没有查清）。相对于一格约 56 点的宽度，这个误差不影响"鼠标是否在废纸篓上方"的判断。

### 6.4 没能验证的：废纸篓那一格在这一条里的位置

上面验证的是"那一条在哪"。"最后一格的中心离末端多远"（公式里是 10 + p/2 ≈ 38 点）没有任何不需要授权的办法能量到——
读程序坞里每一项的位置要"辅助功能"权限，当前环境没有（`AXIsProcessTrusted()` 为 false），按要求没有申请。
这个数如果偏了 10 点，区域还是能盖住废纸篓的大半；偏了一整格就会指到旁边那一项上。

**请用户配合一次**（§9 第 3 项）：`swift run InputSenseDemo --trash-check --show`，把鼠标停在废纸篓图标正中，读出"鼠标相对估算中心"的偏差，
顺便看红框是不是框住了废纸篓。如果有偏差，改 `DockModel.endPadding` 一个数即可。
即使不校准，产品里也有自学习兜底：第一次真的把东西拖进废纸篓之后，位置就按实际的松手点修正了。

### 6.5 第三级：自学习

一次拖拽以"图标桥确认进了废纸篓"结束时，松手点一定在废纸篓上。记下**松手点相对当时估算中心的偏差**（沿程序坞方向），而不是绝对位置——
程序坞因为开关应用变长变短之后，偏差仍然适用，绝对位置就不适用了。

- **什么样的松手点才学**，四道关都过才行：图标桥确认进了废纸篓；松手处最上面是程序坞（拖进一个打开着的废纸篓窗口不算）；
  松手点在程序坞那一带的后半段；偏差不超过 3 格（估算再不准也偏不出这么远）。
- 只取同一组设置（靠哪边、图标大小、放大、自动隐藏、显示器尺寸）、同一种估算（公式 / 实测）下最近的 5 条，偏差取**中位数**——万一混进一条离谱的，不至于把估算带偏。
- 偏差不超过 0.35 格：说明原估算是对的，位置不动，可信度按 1 −（1 − 原可信度）× 0.5ⁿ 提高（实测 0.75 → 0.875 → 0.94）。
- 偏差更大：把那一格挪到松手点上，可信度 0.7（一次）→ 0.85（两次）→ 0.925，封顶 0.95。
- 几次松手点彼此差了不止一格：可信度压到 0.5（低于"查不出时凭位置认定被删"要求的 0.6）。
- **程序坞设置变了**：每 3 秒在后台重读一次设置；指纹一变，旧的教训自动不再适用，回到公式或实测重新估算；设置换回来，旧教训又用得上。
- 存储：应用自己的偏好设置，键 `InputSense.trashLessons`，最多 40 条，内容是纯数字。读不懂的旧内容当作没学过。

### 6.6 可信度一览

| 情形 | 可信度 | 估算区域沿程序坞方向两边各多留 |
|---|---|---|
| 公式，程序坞在底部 | 0.45 | 0.28 格（约 15 点） |
| 公式，程序坞在左右两侧 | 0.30 | 0.35 格 |
| 公式，且不知道程序坞在哪块屏（假定主屏） | 再 × 0.7 | |
| 实测 | 0.75 | 0.13 格（约 7 点） |
| 开了放大 | 再 × 0.75（量到了也只有 0.56，不够"凭位置认定被删"的 0.6） | 区域另外按放大的幅度加宽加厚 |
| 自学习之后 | 0.70 ～ 0.95 | 0.15 ～ 0.03 格 |

## 7. c. 自动隐藏、放大、在左右两侧、在外接屏上

| 情形 | 怎么处理 | 验证情况 |
|---|---|---|
| **在外接屏上** | 程序坞的窗口和它所在的显示器一样大，看窗口的边界就知道在哪块屏；每 3 秒在后台复查一次，程序坞换屏（用户把鼠标推到另一块屏的底边）后跟着换。窗口不在屏上时（全屏空间里）到全部窗口里找。全程用全局坐标，外接屏的负坐标不需要特殊处理 | **本机实测**：开发期间用户让程序坞在两块屏之间来回换了两次——窗口的边界先是 (0, 0 1512×982)（内屏），变成 (−1920, −58 1920×1080)（外接屏），后来又回到内屏——每次估算都跟着换了屏（演示打印的"所在显示器"和估算区域随之变化）；§6.3 的测量都是在外接屏的负坐标上做的 |
| **自动隐藏** | 藏着的时候量不到，按公式估"它弹出来时会在哪"（可信度 0.45）；拖拽期间每 0.5 秒量一次，程序坞一弹出来就换成实测。`autohide` 进了设置的指纹：开关它之后旧的教训不再适用 | 本机没开自动隐藏，**没有真机验证过**。相当的情形有过：程序坞因为全屏空间而不在屏上时，量不到、退回公式或沿用旧测量，这条路径实际走到了 |
| **放大效果** | 鼠标靠近时图标变大、整条向两端撑开，废纸篓会往外挪、变大。估算区域相应放宽：朝末端方向多放"放大后大小 − 平时大小"，朝里多放一半，厚度也加这么多；可信度 × 0.75。拖拽期间每 0.5 秒的实测如果能反映撑开后的范围，会自动跟上 | 本机没开放大，**没有真机验证过**；放宽多少是按道理估的 |
| **在左侧或右侧** | 公式和测量都按"沿所在的边"写，三条边共用同一套代码：那一条竖着贴在左边或右边、沿这条边居中，废纸篓在最下面一格 | 单元测试覆盖了几何和测量。本机在底部，**没有真机验证过**；尤其"竖着的那一条是在整块屏的高度上居中，还是在菜单栏以下的高度上居中"不确定（会差十几点），所以公式这一级只给 0.3。量到之后不受影响 |

这三种没验证的情形，改的都是用户自己的系统设置，本对话不会去动。清单里列为可选项（§9 第 7 项）：用户哪天自己开了，跑一条命令看一眼即可。
无论哪种情形，估算偏了的后果都只是"鼠标到废纸篓的距离、是否在上方"不准——**图标是否真的被删不靠位置判断**，而且删过一次之后就学会了。

## 8. d. 访达的起拖阈值；拖影的偏移

- **系统的起拖距离参数**是 4×4 点（`HIMouseTrackingGetParameters`，系统给应用查询"按下后移动多远算开始拖"的接口，`--bench` 和 `--drag-probe` 会打印）。
  判断器取 4 点，按"横向或纵向位移达到 4 点"判断（这是保守的一侧：斜着移动时，它比按直线距离算稍晚一点才开始）。
- **访达实际上是不是用这个数**，需要真人拖一次真实的桌面图标才能量：`swift run InputSenseDemo --drag-probe`（§9 第 5 项）。
  它在左键按下期间每秒约 200 次查看"系统拖影那一层有没有出现窗口"，报告拖影出现时鼠标已经移动了多远（上一次读数和这一次读数之间就是访达的阈值）。
  如果访达的阈值比 4 点大，后果是我们比访达早一两帧认为"开始拖了"——用户在这一两点之内松手的话，会多出一次很快以"取消"收场的假拖拽；
  比 4 点小则是我们晚一两帧，没有可见的后果。量出来之后改 `JudgeTuning.dragThreshold` 一个数。
- **拖影相对鼠标的偏移是否等于抓取偏移**：无法自行确认，在清单里（§9 第 5、6 项）。探针能量的是"拖影左上角相对鼠标的偏移在整个拖动过程中变不变"
  （不变 = 拖影是跟着鼠标刚性移动的）。它是不是**正好**等于"按下点 − 图标图像左上角"，要知道图标图像的位置才能算，
  本模块的演示拿不到真实图标的位置（不依赖图标桥）；最直接的办法是整合之后肉眼看：拖动时脸是不是贴在拖影的图标上。
  如果差一个固定的量，在 `DragState.currentImageRect` 的用法上补一个偏移即可（接口不用动）。
- 这两项都需要桌面图标显示出来。

## 10. 已知限制

- **只在 macOS 27.0.1 上跑过。** 遮挡判断依赖这个版本上窗口的布置（访达图标窗口的层级、系统遮挡窗口的层级）；程序坞的几何常数来自这一台机器。
- **多选拖拽只认鼠标抓住的那一个。** 其余被一起拖走的图标没有拖拽状态；它们的删除事件照常有。
- **Esc 取消发现不了**（不读键盘）：左键还按着的话，拖拽状态持续到松手，脸会多跟一会儿鼠标，然后结局是"取消"。
- **按住 Control 点击**（等于右键）会被当成左键按下；如果接着移动，会出现一次以"取消"收场的假拖拽。
- **按下和松手在两次读数之间就完成了**（比如鼠标静止很久之后的一次极快的点击）是看不到的——只影响"点击"，而点击本来就不是本模块报告的事实。
- **废纸篓那一格在程序坞里的位置没有校准**（§6.4）；自动隐藏、放大、左右两侧没有真机验证（§7）。
- **程序坞里设置上看不出来的项目**（最小化到程序坞的窗口等）公式数不到：只靠公式时估算会偏半格到一格。实测和自学习不受影响。
- **拖进一个打开着的废纸篓窗口**：结局和删除事件是对的，只是这次松手点不拿来学（它不在程序坞上）。
- **要查窗口的那些帧，`update` 可能超过 0.5 毫秒的目标**（机器忙时实测到 0.64、1.44、2.98 毫秒；鼠标移动时这样的帧通常每秒 15 帧，
  飞快扫过图标时最多 30 帧；停在图标上每秒 2 帧）：与窗口服务器的那一趟往返只能在主线程做，快慢取决于系统当时忙不忙。不会造成掉帧。
- **显示器插拔或改排列后**，帧不断流时坐标换算最多晚 1 秒跟上（布局每秒在后台重读一次）；应用暂停期间改的，恢复后的第一帧会当场重读。
- **量程序坞假设它沿所在的边居中、那一条是连续的。** 用隐藏设置把程序坞钉在一端时量不到（公式也按居中算，会偏）；
  末端恰好被一个更高层级、接收点击的窗口盖住时会量短，而可信度仍是 0.75。
- **整体重载恰好发生在"松手等结局"期间**，而且是因为图标大小或显示器排列变了：可能把这次拖拽误判成"挪了位置"（§4.6）。
- 鼠标处落在"访达图标窗口"之上、但被第三方工具用更高层级、**不接收点击**的窗口盖住了图标时，仍会算作"在桌面图标上"（按命中规则，点击确实会落到图标上）。

## 11. 怎么运行

```bash
swift run InputSenseDemo                          # 剧本回放（瞬间跑完）+ 8 秒实时读数
swift run InputSenseDemo --script                 # 只跑剧本回放：假的鼠标轨迹和假图标，模拟时间，每次输出相同
swift run InputSenseDemo --live [--seconds N]     # 实时读数：真实的鼠标、窗口遮挡和程序坞，假的图标（默认 20 秒）
swift run InputSenseDemo --trash-check            # 废纸篓估算核对（默认 20 秒）
swift run InputSenseDemo --drag-probe             # 拖拽探针（默认 40 秒）
swift run -c release InputSenseDemo --bench       # 各种读取要多久（约 15 秒）
scripts/test.sh --filter InputSenseTests          # 142 个单元测试
scripts/check.sh InputSense                       # 编译无警告 + 依赖规则 + 测试 + 演示能自己结束
```

公用选项：`--seconds N`（最长 120）、`--ignore-shield`（桌面图标被系统遮住时也当作桌面，只为在开发机上试悬停和拖拽）、
`--show`（把假图标、废纸篓估算、量到的程序坞画在屏幕上：每块屏一个点击穿透、不抢焦点的透明窗口，退出即消失）、`--quiet`（不打印每秒一行的全貌）。
所有模式都会自己结束，不留窗口和进程；演示不往偏好设置里写任何东西（学到的废纸篓位置只记在内存里）。

**剧本回放**把全部判断走一遍并自己核对：悬停 → 单击和按住不动（不算拖）→ 图标被窗口挡住（不算悬停、拖不起来）→ 挪位置 → 甩动 →
拖进废纸篓并自学习 → 取消 → 快捷键删除 → 再拖进废纸篓（这回估算是准的）→ 鼠标不动时的省电信号。最后一行写「全部符合预期」，否则退出码为 1。
其中的图标桥是假的（`Demos/InputSenseDemo/Support.swift` 的 `FakeDesktop`），但行为照着接口约定：平时每秒读一次，被要求立即刷新时马上读、没变化也回报。

**单元测试覆盖了什么**（都是纯逻辑，用编好的鼠标轨迹逐帧驱动，不碰真实的鼠标、窗口、程序坞和桌面）：

- 什么算开始拖：单击、双击、按住不动、右键、左右键同时、空白处按下再划过图标都不算；阈值；抓取偏移（含按下发生在两帧之间时的折算、
  读得稀时挪到图标上再按下）；开始观察时左键已按着；按着时图标被删；重置。
- 松手后的结局：挪位置、进废纸篓（同一帧给出结局和删除事件、松手点交给自学习）、去了别处、取消（松在桌面上和松在别处各等多久）、超时、
  松手之前的快照不算数、访达更新得慢、拖进废纸篓但访达慢了半拍、拖进打开着的废纸篓窗口、重读图标的节奏、图标桥查不出时的几种情形、
  整体重载的五种情形、还拖着图标就消失了、松手和消失落在同一帧、结局没出来又被拖走、拖着一个时别的被删。
- 没有拖拽过程的删除：快捷键删除；确认没进、查不出来、整体重载里少了的都不报；迟到的删除、挪过位置之后的删除都不标"经过拖拽"。
- 鼠标、悬停：速度与静止时长；悬停时长、标签也算、外接矩形的空角不算、离开再回来重新计时、按着键不算、图标桥状态异常时没有。
- 被窗口挡住：不算悬停也不算拖（别的窗口、系统遮挡窗口、查不出来）；只挡住一半；悬停时窗口冒出来；按下的那一刻一定现查；开始拖之后不受影响。
- 遮挡判断的频率（移动、进入图标、飞快扫过一排图标、离开图标、按着键、拖拽中、静止）与省电信号的各档。
- 甩动强度：直线、弧线接近零；越猛越高；各个方向一样；画圈；停手回落；手抖不算；每次拖拽从零开始。
- 废纸篓：距离、靠近速度、防抖、是否在上方；程序坞几何模型（复现本机实测）；量程序坞（各种长短厚薄、左右两侧、藏着、核对上一次的结果）；
  估算与自学习（位置被修正、设置变了重新估算、换回来又适用、不像样的松手点不学、混进一条离谱的不被带偏、总量上限）；读取的时机；存下来再读回。
- 模块入口：薄层和判断器接在一起；没人调用时什么都不读；一百个图标时判断器一帧的耗时。

## 12. 接口方面的意见与待决问题

接口没有不够用的地方，DDMCore 一行没动。下面是用下来的几点意见，改不改由总览定：

0. **`DeletionEvent.wasDragged` 的含义**。接口约定 §3.2 写的是"经过拖拽的删除，同一帧里还会有一条 `trashed` 结局"。我按这句话做了：
   `wasDragged == true` 当且仅当同帧有 `trashed` 结局。于是"拖进废纸篓，但访达慢到我们已经先判了取消 / 未知"之后才到的删除，标的是 false。
   如果总览更希望这种情形标 true，需要在约定里写明"这种删除没有同帧的结局"，我这边改一行。

1. **`DragState` 之后、结局之前的那段时间脸画在哪**，接口约定没有明说。建议在约定里写明：`releasedDrags` 里的图标，脸画在 `imageRectAtRelease`（见 §2 第 4 条）。
2. **`TrashInfo.isApproaching` 在废纸篓上方静止时为 false**（§2 第 7 条）。如果情绪模块更想要"到了上方就一直算朝向"，在情绪那边写成 `isOver || isApproaching` 即可。
3. **`IconProviding` 的节奏提示**：`FramePipeline` 里"用户是否在忙"的判断已经包含了 `releasedDrags`，等结局期间图标桥会保持活跃，没有问题。
4. **待用户配合的三项**（§9 第 2、3、5 项）各要贴一段输出，其中第 3 项最要紧（校准废纸篓那一格的位置）。
5. **图标桥的那条待验证假设**（松手后访达是否及时更新位置）如果结果是"不更新"，本模块的"挪了位置"会全部变成"取消"或"未知"——需要图标桥换方案，届时请通知本模块配合。
6. **访达在自己拖着图标的时候还回不回应图标桥的询问**，不知道（图标桥的真人拖动检查第一阶段正好能看出来，请留意）。
   如果不回应，拖得久（超过图标桥的 5 秒超时）的拖拽会在途中收到一次"快照清空"的整体重载。本模块对此的处理：拖拽继续（脸照样跟着鼠标），
   松手后等访达恢复、按新快照下结论；图标没了而松手点在可信的废纸篓上就认定被删，否则记为去了别处。只有访达 3 秒内没恢复才落到"未知"。
