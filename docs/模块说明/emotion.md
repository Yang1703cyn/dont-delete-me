# 情绪状态机（Emotion）模块说明

> **归属** emotion · **代码** `Sources/Emotion/` · **测试** `Tests/EmotionTests/` · **演示** `Demos/EmotionDemo/`
>
> 情绪模块是"导演"：每帧拿到「图标快照 + 交互事实 + 时间」，决定这一帧要画哪些脸、各自在哪、画在哪一层、表情参数是什么。
> 它不读系统、不画图，是纯逻辑：不读时钟、不用全局随机数、不读写文件、不依赖 AppKit。
> 接口是 [接口约定.md](../接口约定.md) 第 5 节的 `EmotionDirecting`，入口类型 `EmotionDirector(seed:)`，都没有改动；DDMCore 一行没动。
>
> 文中的数字都是实际跑出来的（单元测试、时间线打印程序、耗时测量）。**没有任何一项在真实桌面上、由真人操作验证过**——
> 本模块按要求只用编造的图标数据；手感是否合适，要等总览整合之后由用户看（§10）。

## 2. 怎么用（给总览的集成注意事项）

```swift
var director = EmotionDirector(seed: 42)                 // 应用里就这样构造，入口类型名和构造方式没变
let output = director.update(EmotionInput(time: time, icons: iconUpdate, facts: facts))   // 每帧一次
director.reset()                                         // 暂停后恢复、桌面重新可见时

var tuning = EmotionTuning()                             // 想调手感：先改调参表，再构造
tuning.fearRadius = 500
var tuned = EmotionDirector(seed: 42, tuning: tuning)
```

现有的 `FramePipeline` 一行都不用改。下面是整合时需要知道的事。

1. **种子**。种子只影响"什么时候眨眼""无聊时谁先张望"。长相和性格只看图标自己的长相种子，与它无关——
   所以种子固定写死或每次启动随机取一个都行，图标的样子和脾气不会因此改变。
   注意 `reset()` 按接口约定会让随机数从种子重新开始：流水线每次"桌面重新可见"都调它，于是用户每次回到桌面，
   头几秒看到的是同一套眨眼时刻。介意的话，可以在那时换一个种子重新构造一个引擎，而不是调 `reset()`。
2. **请按 `output.demand` 出帧**（已经是这样接的）。三种取值的含义：
   - `.continuous`：有参数还在渐变（视线在转、脸在红、幽灵在飘、脸在飘回原位……）。
   - `.by(t)`：现在是静止的，最晚 t 时刻要再算一次。t 可能是：下一次眨眼、眨眼途中或慢慢消退途中的下一帧（见第 3 条）、
     某个瞌睡虫该重新犯困了、头晕该开始消退了、波纹该传到下一个图标了、下一个幽灵该出场了、
     松手后的停留期到了、鼠标再不动就该开始无聊了、下一次张望。
   - `.idle`：桌面上没有图标，或者所有的脸都在一个不需要再算的状态里（例如主角悬在废纸篓上方大哭、围观者全捂着眼——
     参数都到顶了，没人眨眼）。此时画面上的泪珠、发抖仍在动，那是表情模块的循环小动画，由应用按 `animationInterval` 另行出帧。
3. **有两种时候引擎给的是 `.by(现在 + 1/30 秒)`，不是 `.continuous`**（都是为了省电，都可以关）：
   - **眨眼途中**。只有眨眼、没有别的动画时，眨眼按每秒 30 次算（一次眨眼 5 帧左右），肉眼看不出区别，
     空闲时的出帧量少了四成左右（§5.2）。不想要：`tuning.blinkFrameInterval = 0`。
   - **只剩"慢"的渐变还没到位时**——汗慢慢收、脸红慢慢退、惊恐和泪消退、慢慢睡着（时间常数不小于 0.5 秒的那几条）。
     这类余韵要持续好几秒，每一步的变化本来就很小。不想要：`tuning.slowFrameInterval = 0`。

   应用因为别的原因在连续出帧时，它们照样每帧都算，画面不受影响。这种用法与接口约定 §10.2 里"`.by` = 当前没有动画"的字面意思不完全一致
   （它是"有动画，但不用每个显示刷新都算"），请总览定夺（§10 待决 2）。叠加层只要能在约定的时刻附近醒来就行；
   醒晚了也不会出错，只是那一小段动画慢一点（平滑按不超过 1/30 秒的一步算）。
4. **静止的画面，表情状态逐比特不变。** 流水线里"`shown.state == state` 就沿用旧版本号"的判断可以直接用：
   鼠标不动时每张脸的 `FaceState` 每一帧都完全相等（视线目标就是"鼠标位置 − 图标中心"，一个比特都不差）；
   睡着的脸、捂严了眼的脸不随鼠标或主角的移动而变（它们的 `gazeFollow` 是 0，`gazeTarget` 统一给零向量）。
5. **引擎没有做"视线取整"。** 鼠标一动，所有清醒的脸的 `gazeTarget` 每帧都在变——"全员每帧重画"仍然是最常见的活跃状态，
   和总览之前掌握的一样。总览计划在流水线里做的限频和取整仍然需要。给一个取整时可以用的量（比直接比较 `gazeTarget` 合理——
   目标在远处挪几百点，瞳孔其实纹丝不动）：

   ```
   画面上视线偏到哪里 ≈ gazeFollow × gazeTarget ÷ (|gazeTarget| + 0.12 × 图标宽)      // 一个长度不超过 1 的二维向量
   ```

   这个向量变化不到 0.02～0.03（瞳孔移动不到十分之一点）就可以不重画。0.12 是表情模块里的常数。
6. **转向途中的 `gazeTarget` 是换算出来的"等效目标"**，不是屏幕上某个东西的位置（§3.6）。它的数值可以很大（上限约 1 万点），
   也可以一帧之内变化几百点而画面是连续的。不要拿它做"图标在看谁"之类的判断。
7. **主角的脸什么时候在拖拽层**：正被拖着的时候；松手后、结局出来前，最多 0.3 秒（停在松手处）；
   之后如果要飘回原位，飘的途中（不到半秒）。其余时候所有的脸都在桌面层。同一个图标任何时刻只有一张脸。
8. **松手之后脸画在哪**（接口约定没有明说，我的做法见 §3.4）。和 input-sense 的建议一致的部分：松手到结局之间画在
   `ReleasedDrag.imageRectAtRelease`。不同的部分：只画 0.3 秒，结局还不来就飘回原位——因为"取消"要等 0.4～1.1 秒才确认，
   而那时图标早已弹回去了，脸不能一直悬在半空。
9. **真人实测"松手后图标的位移比鼠标的位移小 2～4 点"**：结局为"挪了位置"的那一帧，脸从松手处直接落到快照里的新矩形，
   所以会有一次 2～4 点的小跳动（一帧）。引擎没有为它做过渡——图标本身就是那一刻到位的，脸晚到反而会脱开。
   肉眼看着别扭的话，可以让脸用 0.1 秒滑过去，改动很小，告诉我即可。
10. **引擎不看这些字段**：`DeletionEvent.wasDragged`、`DeletionEvent.trashed`、`isMouseOverDesktop`、`TrashInfo.closingSpeed`、
    `DragState.velocity`、`MouseState.velocity`。所以 input-sense 那个待裁定的问题（`wasDragged` 的含义）怎么定都不影响本模块：
    见到删除事件就在 `lastImageRect` 放幽灵，仅此而已。鼠标在别的窗口上时，图标照样看着鼠标。
11. **多选拖拽**：只有被抓住的那个是主角。其余一起被拖走的图标在快照里还在原位，所以它们的脸留在原位当围观者；
    真被删了之后各自收到删除事件，幽灵一个不少（错开出现）。
12. **废纸篓估算不出来**（`facts.trash == nil`）时：主角不害怕、没有围观；真被删了照样出幽灵。
13. **"立即删除"（不经废纸篓）没有幽灵**：图标桥报的是"消失、没进废纸篓"，交互感知不发删除事件，脸随图标一起消失。按现有约定如此。
14. **整体重载**（`isReset`）：还在的图标保留身上的情绪（不无故跳一下），新出现的悄悄建好（不算"新来的"），
    不见了的直接撤掉（不放幽灵），正在飘的幽灵清掉（位置多半已经不对了）。同一帧里的删除事件照样放幽灵。
15. **线程**：不绑定线程；`EmotionDirector` 是值类型，里面没有任何共享的可变状态。
16. **调参表在运行中也可以改**（`director.tuning.xxx = …`，下一帧生效），但流水线里它是以协议类型存着的，
    实际上只能在构造时给。想做"边跑边调"的调试界面的话，需要总览在流水线里留个口子。

## 3. 状态与优先级

### 3.1 没有"状态开关"，只有一组连续的通道

每个图标对应一个"演员"，身上是 9 条通道，每条各自朝自己的目标值渐入渐出：

| 通道 | 谁来驱动 | 变成表情里的什么 |
|---|---|---|
| 惊恐 | 主角面临的威胁 | `fear` |
| 汗、发抖、泪 | 主角面临的威胁 | `sweat` `tremble` `tears` |
| 头晕 | 甩动强度 | `dizziness` |
| 脸红 | 悬停 | `blush`，以及视线躲开鼠标 |
| 围观反应 | 围观的波纹传到了没有、主角有多怕 | 按性格：胆小 → `cover`；好奇 → `cover` + `peek`；胆大 → `fear`。三种都带一点 `fear` |
| 困意 | 在不在"该打瞌睡"的名单上、有没有人理 | `sleepiness`，以及眼睛不再跟随 |
| 视线 | 这一帧想看哪里 | `gazeTarget` `gazeFollow` |

外加按时间表走的眨眼（`blink`）。**这一帧的表情就是把各条通道的当前值拼起来。**
没有"现在处于哪个状态"的开关，所以几种情绪可以同时存在、此消彼长（害怕 0.3 + 困意 0.6 也成立），任何时刻画面都是连续的；
也因此不存在"卡在某个状态里出不来"——通道的目标一变，它就往新目标走。

`FaceState.mood` 只是个标签（表情模块只用它区分是不是幽灵），由最后的参数按优先级推出：
`tears > 0.4` → 哭；否则 `cover > 0.5` → 捂眼；否则 `fear > 0.2` → 害怕；否则 `dizziness > 0.25` → 头晕；
否则 `blush > 0.3` → 害羞；否则 `sleepiness > 0.5` → 打瞌睡；否则平静。

### 3.2 优先级：多种情况同时成立时谁压过谁

**幽灵 ＞ 哭 ＞ 害怕（含围观的捂眼、偷看、瞪眼）＞ 头晕 ＞ 害羞 ＞ 平静 ＞ 打瞌睡**；两个彩蛋排在最后，只在"什么事都没有"时出现。
"压过"不是一刀切，而是高优先级的情绪越强、低优先级的目标值被压得越低，所以交接也是平滑的。

| 同时成立的情况 | 表现 | 怎么实现的 |
|---|---|---|
| 被删 vs 任何情绪 | 只剩幽灵 | 图标从快照里消失，演员撤掉；幽灵是单独的一张脸 |
| 哭 vs 害怕 | 是同一件事的两个程度：威胁越大，惊恐、汗、发抖依次到顶，最后才是泪 | 四条通道都由"威胁"一个数决定 |
| 主角害怕 vs 头晕（边甩边拖向废纸篓） | 威胁 0.3 以下照常头晕；0.3～0.8 之间头晕逐渐让位；0.8 以上只剩害怕。虚惊一场之后，如果还在"再晕一阵"的时间里，头晕会回来 | 头晕的目标 ×（1 − 威胁的折算） |
| 害怕 / 头晕 / 围观 vs 害羞（刚被吓过的图标被鼠标停在上面） | 顾不上害羞；缓过来之后才慢慢脸红 | 脸红的目标 = 1 − 2 × max(惊恐, 头晕, 围观反应)，不小于 0 |
| 围观 vs 打瞌睡 | 波纹传到时被吵醒，然后按性格反应；醒到一半时反应打折 | 波纹到达即算"有人理"；围观反应 ×（1 − 困意） |
| 悬停 / 被拖 vs 打瞌睡 | 醒，然后害羞 / 当主角 | 悬停、被拖都算"有人理" |
| 平静 vs 打瞌睡（鼠标在旁边动） | 醒着，跟着鼠标看 | 见 §3.3 第 8 条 |
| 无聊 vs 其它任何事 | 有拖拽、等结局、幽灵、围观、新来的图标时，谁都不张望；被悬停的、睡着的、身上有任何情绪的图标不会被挑去张望 | 张望只挑"完全闲着"的图标 |
| 大家该看哪（视线） | 幽灵 ＞ 被拖的主角 ＞ 新来的图标 ＞（无聊时）自己张望的地方 ＞ 鼠标 | §3.5 |
| 眨眼 vs 情绪 | 睡着、捂着眼、惊恐 ≥ 0.5、泪 ≥ 0.2、头晕 ≥ 0.2 时不眨眼（眼睛看不见，或者正瞪着） | 到点时不满足条件就重新排，不为它叫醒应用 |

### 3.3 十条剧本各是怎么演的

时间都是默认调参表下实测的（`swift run EmotionDemo` 每条剧本末尾的小结）。

1. **平时**。视线目标 = 鼠标位置 − 图标中心，`gazeFollow = 1`。每个图标有自己的一路随机数：两次眨眼之间隔 2.5～7 秒随机，
   一次眨眼 0.17 秒（`blink` 走 0 → 1 → 0），偶尔连眨两下（15%）。第一次眨眼在 7 秒之内随机，所以一开始就不同步。
   眨眼从"已经合了一小步"开始，所以应用专门为它醒来的那一帧画面就有变化，不白醒一次。
2. **悬停**。脸红 0.5 秒左右到顶；视线从"看鼠标"转成"看鼠标的反方向、偏下"（鼠标在图标右半边就往左下看，在左半边就往右下看，
   在正中就往正下方看），脸越红躲得越彻底。鼠标移开后约 2.5 秒脸红退尽，视线随之回到鼠标上。
3. **被拖着走**。主角的脸画在 `drag.currentImageRect`、拖拽层，原位置不画；它平视前方（`gazeFollow` 渐变到 0，看着屏幕外的用户）。
   其它图标的视线目标换成主角的脸所在的位置。
4. **猛甩**。`drag.shake ≥ 0.5` 开始头晕：刚到阈值时 0.6，甩得更猛按比例到 1。晕的程度取这一阵里甩得最猛时的值（甩得轻一点了但还在甩，不会因此清醒一些）。不甩之后（包括松手之后）头晕原样保持 1.6 秒再消退：
   实测松手后 2.2 秒退到 0.25 以下（眼睛不再是漩涡），3.2 秒清零。只是不甩了、还拖着，也一样再晕一阵。
5. **被拖向废纸篓**。
   - **威胁**（0…1）= 接近程度 ×（0.3 + 0.7 × max(正朝它去的程度, 接近程度)）；到了废纸篓上方（`isOver`）恒为 1。
     接近程度 = 1 −（鼠标到估算区域的距离 − 宽容量）÷ 450，夹在 0…1；宽容量 =（1 − 可信度）× 80 点。
     "正朝它去的程度"是把 `isApproaching || isOver` 这个是 / 否用 0.2 秒（变成是）/ 0.6 秒（变成否）平滑出来的。
   - **对位置偏差不敏感**靠三点：起作用的范围很宽（450 点），差几十点只是程度略有不同；估算越不可信，"已经到了"的范围放得越宽
     （只靠公式、可信度 0.45 时，离估算区域 44 点以内就算到了）；离得越近，"是否正朝它去"越不起作用（到跟前时停住不动也一样怕）。
     真删没删不靠位置，只看删除事件。
   - **冒汗 → 发抖 → 大哭**：惊恐从威胁 0 起、0.8 到顶；汗 0.08 起、0.5 到顶；发抖 0.35 起、0.85 到顶（幅度上限 0.85）；
     泪 0.7 起、0.98 到顶。可信度 0.75 时各距离上稳定下来的样子：

     | 鼠标离估算区域 | 威胁（正朝它去） | 惊恐 | 汗 | 发抖 | 泪 | 威胁（没朝它去） | 惊恐 | 汗 |
     |---|---|---|---|---|---|---|---|---|
     | 450 点 | 0.04 | 0.06 | 0 | 0 | 0 | 0.01 | 0.02 | 0 |
     | 350 点 | 0.27 | 0.33 | 0.44 | 0 | 0 | 0.13 | 0.16 | 0.12 |
     | 250 点 | 0.49 | 0.61 | 0.97 | 0.24 | 0 | 0.31 | 0.39 | 0.56 |

     否则"盯着自己所在的位置"在表情模块里会画成对眼。
   - **全体围观**：威胁升到 0.4 时开始（正朝废纸篓去的话大约是离它 290 点时），降到 0.2 以下结束。
     一圈波纹以主角**当时的位置**为中心、每秒 900 点传开（全局坐标里的直线距离，跨屏照算；最晚 1.8 秒传到）；
     传到谁，谁才开始反应。反应的强度随主角的威胁变化（威胁 0.2 → 0，0.8 → 1）。
   - **性格**：由长相种子派生的第 1 路随机数决定（表情模块用第 0 路定五官，互不相关），同一个图标永远相同。
     胆小 35%：捂眼（反应 0.6 时手已捂严），不看。好奇 35%：捂眼（0.65 时捂严），反应 0.6～0.95 之间指缝逐渐张开到 0.9。
     胆大 30%：不捂，瞪眼看（`fear` 到 0.75），视线一直跟着主角。三种都是**静止画面**（只给 `fear`，不给 `tremble`、`sweat`）。
6. **虚惊一场**（松手后结局是挪了位置、取消、去了别处、判断不出）。松手到结局之间，主角"屏住呼吸"：威胁保持松手时的值。
   结局一出，威胁归零，各通道各自消退——实测发抖 1.35 秒、泪 1.9 秒、惊恐 2.1 秒、**汗 4.2 秒**后消失（汗是故意最慢的）。
   围观在结局出来的那一帧结束，围观者约 1.1 秒后全部放下手。"去了别处"时图标从桌面消失，脸跟着消失，不放幽灵。
7. **真的被删**。见到 `DeletionEvent` 就在 `lastImageRect`（图标原位置，不是松手处）放一个幽灵：桌面层、排在所有脸的最后（画在最上面）、
   沿用被删图标的编号和长相种子。`ghost` 从 0 匀速走到 1，用 2.6 秒，然后撤掉。没有拖拽过程的删除完全一样。
   一次删多个：按删除事件的顺序，相邻两个错开 0.15 秒出场；个数多时排密一些，从第一个到最后一个不超过 1 秒。
   围观者放下手（约 1 秒），所有清醒的图标**目送**：视线目标是最后出场的那个幽灵此刻的位置（按约定，比原位置高出"进度 × 一个图标高"），
   幽灵散了再看回鼠标。睡着的图标不看。被删的图标如果又回到了桌面（撤销了删除），幽灵立即让位。
8. **打瞌睡**。最近修改时间距今超过 182.5 天的图标是候选；按修改时间从早到晚排，取前 ⌊图标总数 ÷ 3⌋ 个上名单
   （修改时间相同按编号排，保证确定）。没有修改时间的不参与。所以 2 个图标时谁都不睡，9 个图标最多睡 3 个。
   名单在图标有变化时重排，平时每 10 分钟重排一次。启动时（或整体重载时）名单上的图标直接是睡着的样子，不演一遍"慢慢睡着"。
   **惊醒**：鼠标到图标图像矩形的距离小于 90 点、而且鼠标正在动（静止不到 0.6 秒），或者被悬停、被拖、被围观的波纹扫到——
   约 0.35 秒完全清醒，跟着鼠标看。**没人理了**（鼠标走了，或者只是停在旁边不动）之后再醒 4 秒，然后用 5.6 秒慢慢睡熟
   （合计：鼠标停住后约 10 秒重新睡熟）。睡着时 `sleepiness = 1`、`gazeFollow = 0`，表情状态完全不变。
9. **彩蛋·无聊**。鼠标静止满 12 秒、而且没有别的事（没有拖拽、等结局、幽灵、围观、新来的图标）时开始。
   张望由导演统一安排：每隔 0.7～2.2 秒挑一个完全闲着的图标，让它看一眼邻居（60%，最近的 3 个里随机挑）或者别处
   （40%，400 点外的一个随机方向），看 1.2～3 秒再看回鼠标。所以不管桌面上有多少图标，同一时间在张望的只有一两个。
   鼠标一动（`idleDuration` 归零），所有张望当帧取消，视线约 0.3 秒转回鼠标。
10. **彩蛋·新来的**。只有图标桥明确报告"新增"的图标才算（整体重载、快照里直接多出来的都不算）。
    其它清醒的图标转头看它 1.6 秒；新图标自己照常看鼠标，0.3 秒后连眨三下。很久没动过的文件被拖到桌面上，也是先醒着打个招呼再睡。

**另外加的一项（剧本里没有，为省电）：安静。** 鼠标静止超过 20 秒，眨眼和张望的间隔开始拉长，40 秒后是平时的 3 倍。
理由：鼠标在动的时候应用本来就在连续出帧，眨眼不额外费电；鼠标不动时每一次眨眼都要专门把应用叫醒。
鼠标一动立刻恢复（排到很远以后的眨眼会被重新排到 7 秒之内）。不想要：`tuning.quietStretch = 1`。

### 3.4 脸画在哪、哪一层

| 情形 | 矩形 | 层 |
|---|---|---|
| 平时 | 快照里的 `imageRect` | 桌面层 |
| 正被拖着 | `drag.currentImageRect`（鼠标位置 − 抓取偏移） | 拖拽层 |
| 已松手、结局未定，松手后 0.3 秒以内 | `ReleasedDrag.imageRectAtRelease` | 拖拽层 |
| 已松手、结局未定，超过 0.3 秒 | 从松手处飘回快照里的位置（约 0.2～0.4 秒），到了就留在那里等结局 | 途中拖拽层，到了之后桌面层 |
| 结局：挪了位置 | 立刻落到快照里的新 `imageRect`，不飘 | 桌面层 |
| 结局：取消 / 判断不出，或拖拽被打断 | 如果脸还不在原位，飘回去 | 途中拖拽层 |
| 结局：进了废纸篓 / 去了别处 | 图标已不在快照里：脸消失（前者另有幽灵） | — |
| 幽灵 | `DeletionEvent.lastImageRect` | 桌面层，排在最后 |

为什么松手后只在松手处停 0.3 秒：最常见的两种结局（挪了位置、进了废纸篓）通常 0.1～0.2 秒就确认，脸不动最自然；
"取消"要 0.4～1.1 秒才确认，而访达的图标早就弹回原位了，脸不能一直悬在空处。飘回原位之后如果才确认"进了废纸篓"
（访达慢了半拍），幽灵从原位冒出来，也说得通。

数组顺序（叠放次序）：桌面层的脸按快照里的图标顺序 → 拖拽层的脸 → 幽灵。

### 3.5 大家看哪

每个图标每帧先定"想看哪里"，再平滑地转过去：

- **主角**（被拖着，或等结局）：看着用户，或盯着废纸篓（看威胁）。
- **其它图标**：有幽灵 → 最后出场的那个幽灵；否则有主角 → 主角的脸；否则有新来的图标 → 它；否则自己正在张望 → 张望的地方；否则 → 鼠标。
- 脸红的时候，在上面的基础上按脸红程度混入"躲开鼠标"。
- 困意和捂眼会把 `gazeFollow` 压下去：`gazeFollow` = 平滑后的跟随程度 ×（1 − 困意）×（1 − 捂眼）。睡熟或捂严了时是 0，`gazeTarget` 统一为零向量。

### 3.6 平滑是怎么保证的

- **强度参数**：每条通道朝目标"先按指数规律靠近，快到时匀速走完"。变大和变小的快慢分开给（例如汗 0.2 秒出、1.2 秒收）。
  匀速收尾保证在有限时间内**正好**到达目标——到了之后数值不再变，应用才能休息；也保证不会无限逼近却永远差一点。
- **隔了很久才来的一帧**：平滑只按不超过 1/30 秒的一小步算。应用休息 5 秒后醒来的第一帧，脸红不会一步跳到位（实测第一帧不到 0.25）。
  眨眼、幽灵的进度、各种计时用的是绝对时间，不受影响。
- **视线**：不直接对"目标点"做平滑——目标离脸很远时瞳孔早就转到头了，目标点在远处滑动几百点眼睛纹丝不动，滑到脸附近的那一两帧里
  瞳孔却会从一头甩到另一头。做法是把（目标点，跟随程度）换算成一个三维的量再做平滑：前两维大致是"瞳孔偏到哪里"，
  第三维是"对眼的程度"（目标就在脸上时最大）。在这个量上走直线，画面上就是瞳孔匀称地扫过去：从左边的远处转到右边的远处，
  途中经过的是"平视前方"，而不是"对眼"（有测试）；"看着用户"就是原点。转到位之后输出的就是目标点本身。
- **允许突变的只有**：幽灵的出现；脸随图标的出现和消失；主角的脸在松手 / 结局时换位置和层。

| `ghostDuration` | 2.6 | 幽灵从冒出来到完全消散用多久。 |

| `glanceGapMin` | 0.7 | 整个桌面上，相邻两次"有谁张望一下"之间最短隔多久。 |
| `glanceGapMax` | 2.2 | ……最长隔多久。 |
| `glanceHoldMin` | 1.2 | 一次张望最短看多久。 |
| `glanceHoldMax` | 3.0 | 一次张望最长看多久。 |

`blinkIntervalMin/Max`、`quietAfter`。

## 5. 省电

### 5.1 引擎这边做了什么

- 没事的时候如实说没事（§2 第 2 条）。静止画面的表情状态逐比特不变（§2 第 4 条）。
- 围观者只给 `fear`、`cover`、`peek`，不给 `tremble`、`sweat`、`tears`——按表情模块的说明，这些都是静止画面，不需要每帧重画。
- 睡着的、捂严了眼的脸不跟随视线，鼠标和主角怎么动它们都不重画。
- 不该眨眼的脸（睡着、捂着、瞪着）不为眨眼叫醒应用。
- 眨眼按每秒 30 次出帧，而且从"已经合了一小步"开始（不白醒一帧）；只剩慢慢消退的参数时也按每秒 30 次出帧。
- 鼠标久不动进入"安静"，眨眼和张望放慢到三分之一。
- 无聊时的张望由导演统一安排，同时只有一两个图标在动，与图标数量无关。

### 5.2 鼠标不动时引擎要求的出帧量

`swift run -c release EmotionDemo --bench` 里模拟一个严格按需求出帧的应用（要连续就每 1/60 秒一帧，否则睡到引擎说的时刻；
另按交互感知的节奏，最多睡 0.1 秒——所以每秒 10 帧是底数）。"重画"指表情与上一帧不同的脸的张数，不含表情模块自己的循环小动画。

| 图标数 | 刚停下（1～12 秒） | 无聊（12～60 秒） | 安静后（2 分钟以上） |
|---|---|---|---|
| 10 | 每秒 17.1 帧，重画 12.7 张 | 24.6 帧，23.3 张 | 18.6 帧，12.8 张 |
| 30 | 25.5 帧，37.5 张 | 30.6 帧，44.1 张 | 22.3 帧，22.7 张 |
| 100 | 36.6 帧，144.6 张 | 38.5 帧，121.1 张 | 31.9 帧，61.7 张 |

这些帧几乎全是眨眼带来的（30 个图标平均每秒有 6 个在眨），每帧只重画一两张平静的脸（表情模块实测约 0.02～0.03 毫秒一张）。
"各自随机眨眼"这个设定决定了它不会是零。改之前（眨眼每帧都算、60 秒才开始安静）30 个图标是每秒 46 帧，现在是 25.5 帧。
还想更省：把 `blinkIntervalMin/Max` 调大，或者把 `quietAfter` 调小、`quietStretch` 调大。**整合后请用实测的处理器占用说话**——
按叠加层的数据（每秒十几帧加偶尔眨眼约 1.5%）估计在 2% 上下，但这是估计。

### 5.3 围观高峰时有多少张脸在重画

"每帧必画"指按表情模块的规则（幽灵、`tremble > 0`、`dizziness > 0`、`tears > 0.4`）每个显示刷新都要重画的脸；
"合计"再加上表情状态这一帧变了的脸。每帧平均张数：

| 图标数 | 拖过去的途中（合计 / 每帧必画） | 悬在废纸篓上方不动 | 在上方晃动 |
|---|---|---|---|
| 30 | 29.2 / 0.2 | **1.0 / 1.0** | 9.0 / 1.0 |
| 100 | 98.8 / 0.2 | **1.0 / 1.0** | 25.0 / 1.0 |

- **高峰（主角悬在上方大哭）：每帧重画的只有主角 1 张**（每张约 0.17 毫秒）。围观者全是静止画面。
- 主角在上方晃动时，胆大的那三成（瞪眼看的）视线跟着它转，所以会重画；捂着眼的七成不动。它们画的是"只有 `fear` 的害怕"，没有循环动画。
- 拖过去的途中几乎全员重画——大家的视线都在跟着主角，和"鼠标一动全员重画"是同一件事，靠总览的限频和取整来压（§2 第 5 条）。
  途中主角自己多数时候只是冒汗（每秒 30 次），开始发抖之后才每帧必画。
- 幽灵飘着的 2.6 秒里：幽灵每帧必画（约 0.02 毫秒一张），目送的图标视线缓慢上移，也在重画。

## 6. 耗时

`swift run -c release EmotionDemo --bench`。100 个编造的图标（两块屏各一半，四分之一超过半年没动），每种情形 5700 帧，
只量 `update` 本身。机器：Apple M5，macOS 27.0.1，发布版。量了三遍，取每格里最慢的一遍。

| 情形 | 平均 | 最慢的一帧 |
|---|---|---|
| 鼠标不动（只有眨眼） | 0.0062 毫秒 | 0.062 毫秒 |
| 鼠标一直在动（全员跟随） | 0.0051 | 0.020 |
| 鼠标在图标之间悬停 | 0.0045 | 0.022 |
| 拖向废纸篓，全体围观 | 0.0044 | 0.024 |
| 一次删 10 个（幽灵 + 目送） | 0.0042 | 0.021 |
| 鼠标久不动（无聊，东张西望） | 0.0036 | 0.020 |

目标是不超过约 0.2 毫秒，实际平均低一个半数量级，三遍里最慢的一帧（0.062 毫秒，只出现过一次，其余都在 0.025 以下）也只有目标的三分之一。调试版慢一个数量级以上（单元测试里量到 0.06～0.08 毫秒 / 帧，含测试舞台自己的开销），仍在目标之内。
量的时候用户正在用这台电脑，数字有浮动，请当量级看。

为什么快：图标没变的帧只逐个核对编号，不重建任何东西；每帧的指数只算一遍（20 个时间常数），所有图标共用；
每个图标每帧的工作是十来次加减乘和至多三次开方；到位了的通道直接跳过；视线目标没变、又已经转到位时什么都不算。
每帧只分配一个数组（输出的脸）。

## 7. 结构

```
EmotionDirector                入口：每一帧的流程；公开的只有它、EmotionTuning、EmotionPersonality
├── EmotionDirector+Cast       演员表：跟着快照增减演员、排"谁该打瞌睡"
├── EmotionDirector+Scene      场景：主角（脸在哪、威胁多大、甩没甩晕）、围观的开始与结束、幽灵、大家看哪、无聊时挑谁张望
├── Performer                  演员：一个图标的各条通道、眨眼时间表、这一帧的表情怎么拼
├── Gaze                       视线的平滑
├── Easing                     渐入渐出（Ease、approach）、省电信号的累加（Pulse）
└── EmotionTuning              调参表
```

一帧的流程：算时间 → 演员表跟上快照 → 排打瞌睡名单（需要时）→ 幽灵（出场、退场）→ 主角 → 围观 → 大家看哪 → 无聊 →
每个演员走一帧并给出自己的脸 → 追加幽灵 → 汇总省电信号。

## 9. 已知限制

1. **没有在真实桌面上、由真人操作验证过。** 所有阈值和时长都是对着编造的轨迹定的；多远开始怕、多猛算猛甩、波纹多快，要看过实际效果才知道顺不顺。
2. **多选拖拽只有被抓住的那个是主角**（交互感知的限制）。其余被一起拖走的图标在原位当围观者，被删后各自出幽灵。
3. **按 Esc 取消拖拽发现不了**（交互感知不读键盘）：主角的脸会继续跟着鼠标，直到松开鼠标。
4. **松手后结局超过 0.3 秒才来**：脸先飘回原位。之后如果判定"进了废纸篓"，幽灵从原位冒出；
   如果松在了窗口或程序坞上而最后是"取消"，脸会在松手处悬 0.3 秒再回去。
5. **"挪了位置"的那一帧脸有 2～4 点的小跳动**（§2 第 9 条）。
6. **波纹的中心固定在围观开始时主角所在的位置**，之后主角再移动，各图标的先后次序不变。距离按全局坐标里的直线算，不管中间是否隔着屏缝或没有屏幕的区域。
7. **性格是按概率分的**：图标少的桌面可能全是同一种性格（比如三个都胆小），看不全三种反应。
8. **打瞌睡的名额是 ⌊总数 ÷ 3⌋**：不足 3 个图标时谁都不睡。图标增减时名额跟着变，可能有瞌睡虫因此醒来或睡下。
   只有修改时间变了（图标没有增减）时，要靠快照的版本号变化、或最多 10 分钟后的例行重排才会注意到。
9. **"看别处"可能看向屏幕外**（400 点外的随机方向，引擎不知道屏幕的范围）。
10. **幽灵和 Zzz 画到上方相邻图标的位置上**（表情模块的已知限制）；幽灵升到屏幕外会被裁掉。引擎不知道也不处理遮挡。
11. **快捷键删除没有预兆**：没有"害怕"的过程，直接出幽灵。发现的早晚取决于图标桥的轮询（活跃时约 1 秒）。
12. **废纸篓估算不出来时没有害怕和围观**（只有幽灵）。
13. **整体重载恰好发生在拖拽途中**：演员保留情绪，没有问题；但如果重载是清空（访达很久不回应），主角的演员被撤掉，
    访达恢复后它重新出现时是从平静开始往上涨的。
14. **眨眼按每秒 30 次出帧**时，一次眨眼只有 5～6 个不同的画面。应用在连续出帧时不受影响。
15. **输入的时间倒流或不是数字**：当作时间没有流逝——所有的脸停在原地，等时间追上来再接着走（接口约定保证单调，这只是兜底）。
16. **同一个图标编号在快照里出现两次**：只给第一个画脸（接口约定不会出现，只是兜底）。
    同样是兜底：坐标绝对值超过十亿点、宽高不是正数或超过一百万点的矩形当作不合法——这样的图标不画脸，这样的鼠标位置、拖影、废纸篓、删除位置被忽略。
17. **没有为"减弱动态效果"等辅助功能设置做适配**（需要的话可以让应用换一份更安静的调参表）。
18. **调参表不做合法性检查。** 会导致崩溃或卡死的几处有防护（名额、幽灵时长、波纹速度、害怕半径、眨眼时长等填了非数字或非正数不出事），
    但填了不合理的数（比如开始的门槛比到顶的门槛还高）得到的就是不合理的表现。
19. **打瞌睡名单的 10 分钟例行重排没有登记进省电信号**：桌面上只要有图标就总有下一次眨眼要等，应用不会睡过头；真睡过头了也只是晚一点重排。

## 10. 待用户配合 / 待决问题

**待用户配合**（都要等总览整合之后，在真实桌面上看）：

1. 把一个图标慢慢拖向废纸篓：从多远开始冒汗、发抖、大哭是否合适；围观的波纹是否看得出"由近到远"；松手被删后幽灵和目送的节奏。
2. 拖到废纸篓旁边再放回桌面：主角的汗是否"慢慢收"、围观者放下手是否自然；脸落回图标时有没有肉眼可见的跳动。
3. 抓着图标猛甩：多猛才晕、晕多久是否合适（同时也是在校准交互感知的甩动强度）。
4. 鼠标停在图标上、移开：脸红和躲闪的幅度、恢复的快慢。
5. 桌面上放几个半年没动过的文件：打瞌睡的比例、鼠标多近才惊醒、多久重新睡着。
6. 鼠标不动十几秒：东张西望是否太频繁或太少；放一个新文件到桌面上：大家是否看它、它是否眨眼。
7. 整体的处理器占用（空闲时、鼠标移动时、围观高峰时）。

**待决问题**（都不卡事）：

1. **松手之后脸画在哪**是我定的（§3.4）。接口约定 §5.1 / §7.1 写的是拖拽层"只画正被拖着的那个图标的脸"，
   而我还用它画松手后停留（最多 0.3 秒）和飘回原位途中（不到半秒）的脸——在松手处，脸可能压在程序坞或别的窗口上方，
   只有拖拽层看得见。建议总览在接口约定里补一句，免得以后有人按别的理解改。
2. **三项剧本之外的省电措施**，请总览定是否保留，关掉各只需改调参表里的一个数：
   "安静"状态（§3.3 末尾，`quietStretch = 1`）；眨眼按每秒 30 次出帧（`blinkFrameInterval = 0`）；
   只剩慢慢消退的参数时按每秒 30 次出帧（`slowFrameInterval = 0`）。后两项在动画途中给的是 `.by(现在 + 1/30 秒)`，
   与接口约定 §10.2"`.by` = 当前没有动画"的字面意思不完全一致（§2 第 3 条）——保留的话建议在约定里补一句。
   另外要留意叠加层的定时唤醒够不够准：醒得太稀，0.17 秒的眨眼可能只剩两三帧（不会出错，只是眨得粗）。
3. **目送幽灵时围观者只是看着**，没有加"含泪"之类的额外表情（剧本没要求，而且泪汪汪要每秒 20 次重画）。想加的话是几行的事。
4. **性格的比例**（35% / 35% / 30%）和三种性格各自的表现是我定的，用户看过效果后可以调。
5. **视线取整**没有放在引擎里做（需要知道表情模块的画法，属于跨模块的知识；总览已计划在流水线里做）。如果总览希望由引擎来做，可以加。
6. **`reset()` 之后眨眼时刻表从头重演**（§2 第 1 条）。符合接口约定，但流水线每次"桌面重新可见"都调它。要不要改成换种子重建，由总览定。

## 11. 独立审阅

交付前请了一位没参与实现的审阅者（只读）对照接口约定和任务书通读全部代码和本文档，并自己写了随机序列和离谱输入的验证脚本
（都在草稿目录里，没有动工程）。结论：没有发现会在真实使用中演错剧本、崩溃或卡死的缺陷；确定性、健壮性、收敛性都没有问题。

它指出并已改掉的（各补了单元测试）：

| 问题 | 怎么改的 |
|---|---|
| 主角的脸飘回原位、落地的那一帧，引擎可能报"静止"，而看着它的图标下一帧视线还要再挪最后一步（每 5 万帧出现几次，肉眼看不出，但违反"说了静止就真的静止"） | 落地的那一帧多要一帧。新增针对性的测试（修复前失败）和"说了静止就真的静止"的随机性质测试 |
| 坐标大到 1e154 以上、又恰好遇到时间原地踏步的一帧时，飘回原位的计算会得到非数字，脸的矩形卡死（真实坐标到不了这个量级） | 输入统一把关（坐标绝对值小于十亿点、宽高是正数且小于一百万点），判断也改成对非数字安全的写法。顺带堵住了"原始宽高为负的矩形能通过检查"和极大图标宽度下视线目标溢出 |
| 时间倒流时没有"当作没有流逝"：幽灵会消失后重演，眨眼途中会连续要帧 | 时间取"不早于上一帧"的值：所有的脸停在原地，追上来后接着走 |
| 无聊时会挑中身上还有汗（或还在发抖）的图标去张望 | "闲着"的条件补上汗和发抖 |
| 调参表里填非数字：打瞌睡的名额会崩溃，幽灵的时长会让幽灵永不消失 | 这两处加了防护 |
| 文档：平滑的数字只是综合剧本下的实测，不是上限；"少了四成"和"少了一半"两处说法不一 | 改成随机序列里也核对过的数字并在测试里卡上限；统一为"四成左右" |
| 还拖着、甩得轻一点了的时候，头晕会跟着回落到阈值档，而文档说"原样保持" | 改成保持这一阵里最猛时的程度（代码和文档一致了） |
| `newcomerBlinks = 0` 时新图标仍会眨一下 | 调成 0 就不专门眨眼 |

它的建议里采纳的：只剩慢的渐变时不必每帧都算（§2 第 3 条）；眨眼从"已经合了一小步"开始，不白醒一帧。
没有改、写进了已知限制或待决问题的：`.by` 在动画途中的用法与接口字面不一致；拖拽层的用途比接口写的宽；`reset()` 后眨眼时刻表重演；
打瞌睡名单的例行重排没有登记进省电信号。
