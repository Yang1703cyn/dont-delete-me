# 图标桥（IconBridge）模块说明

> **归属** icon-bridge · **代码** `Sources/IconBridge/` · **测试** `Tests/IconBridgeTests/` · **演示** `Demos/IconBridgeDemo/`
>
> 图标桥让应用知道"桌面上每个图标在哪、是什么"：通过访达读出所有桌面图标，持续发现新增、消失、移动，
> 换算成全工程统一的全局坐标。接口定义见 [接口约定.md](../接口约定.md) 第 2 节，这里只讲本模块自己的结论、做法和限制。
>
> **它接触的东西只有两样**：向访达询问（需要"控制访达"一项授权）；读取访达自己的一项桌面显示设置（分组方式，用来识别"叠放"，不需要授权）。
> 不直接读取桌面文件夹，不读取任何用户文件；唯一写入的是应用自己偏好设置里的一份随机盐（让图标编号跨启动不变）。
>
> 文中所有实测都在 macOS 27.0.1（Apple Silicon）、内屏 1512×982 @2x + 左侧外接屏 1920×1080 @1x、桌面 19 个图标的机器上完成，
> 运行方式是 `swift run` 出来的命令行程序（授权算在启动它的程序头上）。没有在别的系统版本上跑过。

## 1. 结论一览

| 问题 | 结论 | 把握 |
|---|---|---|
| a. 锚点 | 访达的 desktop position 是**图标图像的中心**；图像矩形 = 以它为中心、边长为"图标大小"的方块 | **已用截图校准**：实测与推算相差 0 点（§3） |
| b. 手动拖动后是否同步 | **会同步**：真人拖动 3 次，松手后访达都报出了新位置；经图标桥在松手后 65、76 毫秒上报"移动" | 真人实测（§4） |
| 拖动期间访达的表现 | **访达一旦把图标拖起来，就不再回应请求，一直卡到松手那一刻**；拖动途中位置不变 | 真人实测；图标桥的应对见 §4.3 |
| c. 两块屏 | 两块屏共用同一套全局坐标，访达原样接受和报告；"所在显示器"和各种换算都正确 | 数值上已验证（§5） |
| d. 读取开销 | 一次完整读取约 0.1 秒、访达花约 0.14 秒 CPU；建议节奏：活跃时每 1 秒数个数、每 8 秒完整读取；空闲时 5 秒 / 30 秒 | 已实测（§6） |
| 新增 / 移动 / 消失 / 进废纸篓 | 用自己的临时文件实测全部通过 | 已实测（§7） |
| 开启"叠放" | 已实现识别：读访达的一项桌面显示设置为主、"多个图标位置完全相同"兜底（总览定的方案）；**"开了叠放"的那一面待用户配合验证** | 没开叠放的一面已实测；见 §9.1 |

## 2. 怎么用（给总览的集成注意事项）

```swift
let provider = DesktopIconProvider()          // 应用里就这样构造
provider.onUpdate = { update in … }           // 主线程回调
provider.start()
provider.setPollingPace(.active)              // .active / .idle / .suspended
provider.refreshNow()                         // 鼠标松开时调用；连续多帧调用也没问题
```

1. **首次启动会弹"是否允许控制访达"。** `start()` 之后的第一次读取会触发它（打包成 .app 之后才是应用自己的名义）。
   等用户回答期间状态是 `starting`、快照为空；拒绝后是 `permissionDenied`，图标桥每隔 1 秒（活跃）/ 5 秒（空闲）不弹窗地复查一次，
   用户在"系统设置 → 隐私与安全性 → 自动化"里打开开关后自动恢复，并以整体重载上报。**这一段没有真机验证过**（本机早已授权，
   没有人能去点弹窗），只有单元测试；请在整合阶段用打包后的 .app 验证。
   **发布时注意**：现在的打包脚本是本机临时签名，没有开"强化运行时"。将来为了公证而开启强化运行时的话，必须同时给应用加上
   "允许发送 Apple 事件"的权利项（`com.apple.security.automation.apple-events`），否则系统不弹窗、直接拒绝，图标桥会一直报 `permissionDenied`。
2. **节奏提示要给准，它直接决定访达的 CPU 占用**（§6）。桌面看不见或应用暂停时务必 `setPollingPace(.suspended)`；
   用户没在操作时给 `.idle`。图标桥也自己观察全局暂停开关：暂停期间不读，恢复后第一次上报是整体重载。
3. **`refreshNow()` 可以放心地每帧调用。** 图标桥会合并：第一次立即开始读；读取进行中再来的调用合并成"读完之后再读一次"；
   连续调用时各次读取的开始时刻至少相隔 0.15 秒（免得访达连轴转，实测连轴转时访达占到 60% 的 CPU）。
   每一次这样的读取结束都会回调一次 `onUpdate`，哪怕没有变化；回调里快照的 `capturedAt` 不早于调用的时刻。
   `suspended` 期间调用无效（不读、不回调）。
4. **同一个进程里不要有别的线程也向访达发 Apple 事件。** 实测两个线程同时发，会偶发约半秒的卡顿。应用里只有图标桥在发，没有这个问题；
   其它模块如果将来也想问访达，请经由图标桥，不要自己发。
5. ~~显示器全都睡着时，"所在显示器"全是 nil。~~ **（总览批注，2026-11-13：已在公共部分修好。）**
   `DisplayLayout.current()` 现在在显示器全部睡着时给出和醒着时相同的布局，所以睡眠期间"所在显示器"照常给出，
   睡眠、唤醒本身也不再引起整体重载。见 §9.4。
6. **快照里图标的顺序是按编号排的**（稳定，但没有别的含义）。所以 `icon(at:)` 在两个图标重叠时取到哪一个是固定的，但不代表谁在上面。
7. **编号跨启动不变**，靠的是存在应用自己偏好设置里的一份随机盐（键名 `IconBridge.identitySalt`，32 字节）。
   删掉偏好设置后所有图标会换一副长相。编号只由"名字 + 是否磁盘"决定：改名 = 旧的消失（进废纸篓：否）+ 新的出现。
8. **各种变化多久能发现**（19 个图标时）：

   | 变化 | 活跃 | 空闲 |
   |---|---|---|
   | 新增、消失（个数变了） | 约 1 秒内 | 约 5 秒内 |
   | 移动、改名（个数没变），且没有调用 `refreshNow()` | 最迟约 8 秒 | 最迟约 30 秒 |
   | 调用了 `refreshNow()` | 约 0.1 秒 | 约 0.1 秒 |
   | 修改时间、种类的变化（不发事件，只更新快照） | 约 1 分钟 | 最迟约 1 分半 |
   | 显示器插拔、改分辨率、改排列；开关叠放 | 约 1 秒内 | 约 5 秒内 |

   用键盘删除图标（没有鼠标松开）靠的是第一行，所以幽灵最多会晚 1 秒出现。发现变化后图标桥会在 0.4 秒和 1 秒后各追加一次完整读取。
   "消失"事件里，确认进了废纸篓的立即上报；其余的（挪进文件夹、改名、直接删除）会为了再查一次废纸篓而晚约 0.3 秒（§8.3）。
9. **访达一时没空回答，不等于访达不可用**（§4.3）。用户拖着图标（或开着访达的菜单）期间访达不回应请求，图标桥此时
   **保留上一份快照和状态、不上报任何东西**，只让一个最便宜的请求排队等着；访达一回答就马上完整读一遍。
   连续 5 分钟一个请求都不回答，才报 `finderUnavailable`、清空快照。访达进程没了、连接断了仍然立刻报 `finderUnavailable`。
   所以应用**不需要**在拖拽期间把节奏设为 `suspended`——而且最好不要：按接口约定，从 `suspended` 恢复后的第一次上报是整体重载、
   不带变化事件，那样松手后就拿不到"移动"和"消失 + 进了废纸篓"了（详见 §4.4）。
10. **`labelRect` 是估算**（§3.3）：标签在下方的情形已用截图校准，文字笔画都落在矩形之内（四边各留 2.5～6.5 点）；标签在右侧和别的字号仍是推算。
11. **隐私说明要如实写。** 图标桥除了向访达询问，还会读取访达的一项桌面显示设置（§9.1）。README 的隐私说明请写成：
    "向访达询问图标位置，并读取访达的一项桌面显示设置"。打包后的 .app 身份下读这项设置是否确实不弹任何授权窗口，请在整合阶段再确认一次
    （命令行身份下已实测不弹、不卡）。
12. **开了叠放时**状态是 `stacksEnabled`、快照为空，应用什么都不画。开关叠放后最迟约 1 秒（活跃）/ 5 秒（空闲）跟上。

## 3. 锚点（问题 a）

### 3.1 结论与公式

desktop position 指**图标图像（边长为"图标大小"的那个方块）的中心**，与文字标签无关：

```
imageRect = (x − size/2,  y − size/2,  size,  size)        // (x, y) = desktop position，size = 图标大小
```

代码：`IconGeometry.imageRect(position:iconSize:)`。标签位置改成"在右"时，按同一个公式处理（图像中心不变，标签挪到右边）——这一点没有验证。

### 3.2 证据

1. **访达自己的说法。** 访达给每个项目同时提供 `position`（在文件夹窗口里的位置）和 `bounds`（外接矩形）两个属性。
   实测桌面上全部 21 个项目（当时含 2 个临时文件）：`bounds` 都是一个 64×64 的方块，`position` 恰好是它的中心（21/21）。
   也就是说，在访达的概念里，"项目的位置"就是图标图像方块的中心。`desktop position` 是同一个概念在屏幕坐标下的版本。
   （`position` 和 `desktop position` 的数值本身没有固定关系——前者是"把桌面文件夹当普通窗口打开时"的位置。）
2. **用户桌面的实际排布。** 图标最右一列的 desktop position 是 x = 1446，主屏宽 1512。如果它指的是左上角，图标图像会占到 x = 1510，
   离屏幕右边只剩 2 点，比图标还宽的标签必然画出屏幕——不可能。按中心算，图像占 1414…1478，右边留 34 点，合理。
3. **业界的一致用法。** 做安装镜像的工具（create-dmg、appdmg 等）都是用访达的这个位置属性摆图标，文档写明坐标是"图标的中心点"。

4. **像素级的直接证据（2026-11-13 下午，屏幕解锁后补做）。** `swift run IconBridgeDemo --calibrate`：在主屏空白处放两个自己的临时文件，
   设成洋红色纯色方块图标，只截取访达桌面窗口里它们各自周围的一小块，量出方块实际画在哪：

   ```
   【短名字】访达报告的 desktop position (160,220)
     图标图像：推算 (128,188 64×64)；实测 (128.0,188.0 64.0×64.0)；实测中心 (160.0,220.0)，与 desktop position 相差 (0.0,0.0)
   【长名字】访达报告的 desktop position (400,220)
     图标图像：推算 (368,188 64×64)；实测 (368.0,188.0 64.0×64.0)；实测中心 (400.0,220.0)，与 desktop position 相差 (0.0,0.0)
   校准结论：锚点与图像矩形的推算公式得到验证。
   ```

   （上一轮没做成，是因为当时屏幕锁着：锁屏状态下系统不给访达桌面窗口的画面，截出来是一张全透明的空图。）

### 3.3 标签矩形的校准

**标签矩形**是估算的，访达不提供标签尺寸。算法：用系统字体按桌面的文字大小量出名字的宽度；一行放不下就按两行算（访达最多显示两行）；
位置在图像正下方居中（或右侧垂直居中）。常数都在 `IconGeometry.swift` 的 `LabelMetrics` 里。

同一次截图校准也量了文字的实际笔画（图标 64 点、文字 12 点、标签在下）：

| | 推算的标签矩形 | 实测的文字笔画 | 矩形比笔画多出（左 / 上 / 右 / 下） |
|---|---|---|---|
| 短名字（一行） | (119.8, 259.0, 80.3 × 16.0) | (123.0, 261.5, 71.5 × 11.0) | 3.2 / 2.5 / 5.7 / 2.5 点 |
| 长名字（折成两行） | (341.0, 259.0, 118.0 × 32.0) | (346.0, 261.5, 106.5 × 27.0) | 5.0 / 2.5 / 6.5 / 2.5 点 |

据此定下的常数：图像下沿到标签上沿的间隙 7 点（校准前凭经验定的是 4 点，偏高了 3 点，已改）；一行 16 点高（实测两行字的行距正是 16 点）；
一行文字最宽 = 图标大小 + 46 点（实测折行后的字宽 106.5 点，在 110 点之内）；文字左右各留 4 点。文字宽度是用系统字体量的，和实测只差 0.8 点。

**没有校准的**：标签在右侧；别的图标大小、文字大小；"显示项目简介"多出的那一行。已知的偏差来源：访达隐藏扩展名时显示的名字比真实名字短；
网格间距不是默认值时一行的最大宽度不同（网格间距访达不提供）。换了显示选项想重新校准，再运行一次 `--calibrate` 即可（约 15 秒，结束后自动清理）。

**肉眼核对**（整合后）：让叠加层在每个图标的 `imageRect` 上画一个半透明方块、在 `labelRect` 上画一个描边框，
看方块是否正好盖住图标图像、描边框是否大致框住名字；换一种图标大小、把标签位置改成"在右"再各看一遍。

## 4. 手动拖动：位置是否同步、访达拖动期间的表现（问题 b）

### 4.1 结论（真人实测，2026-11-13 下午）

用户亲手拖了两轮（原始输出在共享笔记的"总览-真人拖动检查结果.md"）：

- **松手后访达会更新位置。** 3 次拖动，松手后访达都报出了新位置。经图标桥：松手后 **65、76 毫秒**上报"移动"。
- **访达一旦把图标拖起来，就不再回应 Apple 事件，一直卡到松手。** 只是按着鼠标、图标还没被拖起来时照常回答（约 30 毫秒）；
  拖起来之后发出的请求要么等到超时（-1712），要么在松手的那一刻才答回来——答的已经是新位置。
- **拖动途中访达报告的位置不变**（卡住期间问不到；松手那一刻答回来的就是落点）。
- **图标位移比鼠标位移小 2～4 点**（沿拖动方向；3 次分别相差 4、2.2、2.4 点）。交互感知用"鼠标位置 − 抓取偏移"推算拖影位置时，
  松手后以图标桥报的新位置为准即可。

### 4.2 检查脚本和它出过的误报

```bash
swift run IconBridgeDemo --drag-check
```

一条命令完成"新建临时图标 → 等待拖动 → 报告结果 → 清理"；按提示把名叫「别删我-测试-请拖动我」的图标拖 4 次。
阶段一（前 2 次）图标桥不工作，脚本不停地直接问访达，量"松手后多久访达答出新位置"；阶段二（后 2 次）像应用那样松手后连续调用
`refreshNow()`，量"图标桥在松手后多久上报移动"，并报告这期间图标桥有没有清空过快照、请求被访达卡了多久。

**上一版脚本有一个误报，已修。** 它在主线程上问访达，而这一问在拖动期间被卡住，直到松手才回来——回来时脚本手里的"鼠标还按着"是卡住之前读的旧状态，
于是把"松手那一刻答回来的新位置"记成"拖动途中位置变了"、还算成一次拖动，下一轮又以新位置为起点空等 3 秒，报"没有更新 / 全项目的阻塞问题"。
现在：鼠标的按下和松开由后台线程记录（带精确时刻，主线程被卡住也不漏记）；位置变化先和松手记录对账再下结论，
被卡到松手才回答的那一问算作这次松手的结果，并报告它被卡了多久；结论那句话按"几次松手里有几次没有更新"如实写。
对账逻辑（`Demos/IconBridgeDemo/DragLedger.swift`）自带 10 个情形的自检，第一个就是出过误报的那个；
拖动超过 10 秒时脚本自己的那一问会等到超时，现在也不会再被当成"图标不在桌面上了"。
`--drag-check --rehearse` 先跑自检，再经访达直接改位置走一遍流程：

```
记账自检：10 个情形全部符合预期（含"拖动途中的询问被访达卡到松手才回答"）。
阶段一：第 1 次：位置 (160,220) → (400,220)（位移 240,0）；（演练：位置是经访达设置的）设置后 10 毫秒看到新位置
阶段二：第 1 次：位置 (400,220) → (640,220)（位移 240,0）；（演练：位置是经访达设置的）设置后 88 毫秒看到新位置
演练结论：脚本流程正常（记账自检 → 新建 → 两个阶段各观察一次位置变化 → 汇总 → 清理）。
```

真人那一面要请用户再拖一次才能确认（待用户配合，见 §9.5）。

### 4.3 访达没空回答时图标桥怎么办

以前：一个请求 5 秒没有回答就当作"访达不可用"——清空快照、状态变 `finderUnavailable`、整体重载。
后果是把图标慢慢拖向废纸篓超过 5 秒，所有的脸都消失。现在：

| 情形 | 图标桥怎么做 |
|---|---|
| 请求发出去，访达一时没回答（用户刚把图标拖起来） | 就等着。单个请求最多等 15 秒；这期间快照和状态原样保留，什么都不上报 |
| 松手，访达在那一刻回答了 | 如果这一问等了 1 秒以上，不管问到的个数变没变，**马上完整读一遍**并上报结果；这份快照的 `capturedAt` 是访达回答之后的时刻 |
| 15 秒还没回答（长时间的拖动） | 这一轮作废（什么都不记），快照和状态仍然原样保留、不上报。0.2 秒后再去等——**只发一个最便宜的请求**（数个数），等到它回答，马上完整读一遍 |
| 连续 5 分钟一个请求都不回答 | 报 `finderUnavailable`、清空快照（整体重载）。之后继续等，访达回答了就恢复 |
| 访达进程没了（-600）、连接断了（-609） | 和以前一样，立刻报 `finderUnavailable` |
| 启动后第一次读取就没等到回答 | 没有上一份快照可留：状态停在 `starting`、快照为空、不上报；访达回答后照常以整体重载开始 |
| 读到一半访达没空了（包括正在查废纸篓的时候） | 这一轮整个作废、什么都不记，不草率地报半截结果，也不再接着发别的问题去排队；有空之后重新读、重新比对、重新查 |
| 完整读取读到一半被卡了一阵、又答回来了（位置刚问完，用户正好拖了一下图标） | 刚读到的东西可能一半是卡住之前的、一半是之后的：趁访达现在有空，从头再读一遍，`capturedAt` 以重读开始的时刻为准 |
| 数个数能答、别的问题却一直超时 | 不算"访达恢复了"：5 分钟的界线照样生效，到点报 `finderUnavailable` |
| 访达别的问题照常回答，只有废纸篓问不动（废纸篓里东西极多、或在连不上的卷上） | 不拖累读取：图标照常提供，消失的图标给"不确定"；之后 2 分钟内不再问废纸篓，免得每次读取都白等 15 秒 |

几个要点：

- **为什么等的时候只发一个最便宜的请求。** 访达忙完之后，会把排着队的请求挨个处理掉，包括我们早已放弃等待的那些。
  如果每隔几秒就发一轮完整读取去试，一次长拖动之后访达要先花上几百毫秒回答一堆没人要的问题，松手后的上报就晚了。
  现在一次拖动里最多每 15 秒留下一个作废的"数个数"请求（访达处理它约 10～20 毫秒）。
- **"卡过一阵"的门槛是 1 秒，但随图标数放宽**（每个图标多给 10 毫秒）：图标很多的桌面访达回答一次本来就慢，不能把"图标多"当成"卡住"。
- **为什么是 5 分钟。** 访达不回答最常见的原因是用户正拖着图标或开着访达的菜单，这种状态持续几分钟的极少；
  而访达不回答的时候它自己也动不了桌面上的图标，所以上一份快照多半仍然是对的——宁可多留一会儿，也不要在用户拖着图标往废纸篓走的时候让所有的脸消失。
  真的坏了（进程没了、连接断了）会立刻得到明确的错误，不走这条路。常数是 `BridgeCore.Tuning.unresponsiveLimit`。
- **松手时的 `refreshNow()` 不会让上报晚到。** 松手那一刻如果有请求还卡着：它一回答，图标桥就在同一个周期里完整读一遍并上报；
  这次读取是在 `refreshNow()` 之后才开始的，所以直接算作那次"立即刷新"的结果（`capturedAt` 不早于调用时刻），不再多读一遍。
  如果松手时没有请求在路上（正好在两次等待之间的 0.2 秒空档），`refreshNow()` 就和平时一样立刻开始读。
- **废纸篓的判断不受长拖动影响。** 判断"废纸篓有没有变多"要用拖动之前读到的项目数作基准，而基准超过 20 秒就作废（§8.3）。
  访达不回答的那段时间现在**不计入**基准的年龄——那段时间我们读不了废纸篓，但访达自己也忙着，不会有别的东西经它进废纸篓。
  所以拖着图标犹豫半分钟再扔进废纸篓，仍然给出"进了废纸篓"。只是隔得久、访达并没有卡住的情形，基准照样过期。

这一切都用假的数据源在单元测试里模拟过（`FinderBusyTests.swift`、`ProviderTests.swift`：每个请求等满 15 秒超时、某个请求卡了 7 秒后在"松手"时答回新位置、
拖了四十多秒才进废纸篓、连续 5 分钟不回答、只有废纸篓问不动，等等）。**真的拖着图标时是否如此，需要真人再验证一次**（§9.5）。

### 4.4 给总览：拖拽期间不要把节奏设为 `suspended`

总览打算"拖拽进行中把节奏设为停止，松手那一帧恢复并立即重读"。按现在的接口约定，这样做会丢事件：
**从 `suspended` 恢复后的第一次上报是整体重载，`changes` 恒为空**——交互感知等的"移动"、"消失 + 进了废纸篓"就不会出现，只能自己拿两份快照去比。
（图标桥在恢复时还会把废纸篓计数的基准作废，因为不知道停读期间发生过什么。）

建议二选一：

1. **不停**（推荐，不用改任何接口）。图标桥自己扛得住：拖拽期间最多有一个请求卡在路上，不会堆积；松手后由那个请求的回答直接带出完整读取。
2. 如果一定想让应用认出的拖拽期间一个请求都不发：需要一个"只是先别读、恢复时不算整体重载"的新节奏（例如 `IconPollingPace.held`）。
   这要改公共部分，我没有动；总览定了之后，图标桥这边的改动很小（恢复时发一次带"必须回调"的完整读取，照常比对出变化事件）。

## 5. 两块屏（问题 c）

`swift run IconBridgeDemo --displays` 用一个临时文件依次放到每块显示器的中部和两个角附近，核对四件事：
访达原样接受并报告这个全局坐标；图标桥的图像矩形以它为中心；"所在显示器"是这块屏；换成屏内坐标、AppKit 坐标后都落在这块屏的范围内
（AppKit 那一条是和系统的 `NSScreen.frame` 比的）。实测输出（节选）：


（此前的探针已确认图标可以出现在任一块屏上）。外接屏在主屏右侧、上方、下方的排列没有试过，但公式不依赖排列方向，单元测试里用的就是坐标为负的屏。

## 6. 读取开销与轮询节奏（问题 d）

### 6.1 怎么读

在本进程内直接构造并发送 Apple 事件（`FinderAppleEvents.swift`），不启动 osascript，也不编译 AppleScript。
所有请求都在图标桥自己的一条后台队列上同步发出（`BridgeEngine`），主线程只做调度，从不等待。
实测主线程在读取期间的最长停顿是 3–7 毫秒（测量循环本身的粒度），而一次完整读取要 100 毫秒左右——读取没有卡住主线程。

### 6.2 单个请求的开销（19 个图标）

| 请求 | 连着问（紧接上一个请求） | 隔一阵才问（间隔 ≥ 0.5 秒，轮询的真实情形） |
|---|---|---|
| 桌面上有几个图标 | 墙上 8.5 毫秒，访达 CPU 6 毫秒 | 墙上 20–24 毫秒，访达 CPU **20 毫秒** |
| 每个图标的位置（或名字、类、修改时间，各算一个请求） | 墙上 17 毫秒，访达 CPU 25 毫秒 | 墙上 53 毫秒，访达 CPU **78 毫秒** |
| 位置 + 名字（连着两个请求） | 墙上 33 毫秒，访达 CPU 50 毫秒 | 墙上 80 毫秒，访达 CPU **120 毫秒** |
| 桌面显示选项（整组） | 墙上 15 毫秒 | 墙上 11.5 毫秒，访达 CPU 11 毫秒 |
| 废纸篓里有几项 | 墙上 8 毫秒，访达 CPU 3 毫秒 | 墙上 9 毫秒，访达 CPU 9 毫秒 |
| 每个图标的全部属性（一次取回） | 墙上 107–116 毫秒，访达 CPU 118 毫秒 | 没测（太慢，没有采用） |

要点：

- **访达隔一阵被问一次，比连着被问贵三倍左右**，所以按"连着问"估出来的开销会严重偏低。间隔是 0.5 秒还是 2 秒没有差别。
- **开销随图标数量线性增长**：在临时目录里用 5 / 20 / 50 / 100 / 200 个空文件实测，一个"每个项目的某属性"请求让访达花
  12 / 18 / 41 / 81 / 162 毫秒 CPU，约为 10 毫秒 + 每个项目 0.8 毫秒（这是"连着问"的数字）。100 个图标的桌面，一次完整读取大约是 19 个图标时的 3 倍。
- 本进程自己的开销很小：每次完整读取约 7 毫秒 CPU。
- 探针报告的"约 0.27 秒 / 19 个图标（含 osascript 启动）"对应到这里：进程内一次完整读取约 0.1 秒；第一次读取（要多问几轮，共 8 个请求）约 0.26 秒。

### 6.3 一次读取发哪些请求

- **快速检查**：只问"桌面上有几个图标"（1 个请求）。个数没变就结束；变了当场升级为完整读取。
- **完整读取**：位置 → 名字 → 显示选项 → 废纸篓计数（4 个请求，墙上约 0.1 秒，访达 CPU 约 0.14 秒）。
  名字列表有变化、或到了每 60 秒一次重读修改时间的时候，再追加"类 → 修改时间 → 位置 → 名字"一轮（共 8 个请求）。
  有图标消失时，再为每个消失的图标问一次"废纸篓里有没有叫这个名字的"；第一次没查出"是"的，稍等 0.25 秒后把废纸篓计数和这个问题各再问一次（§8.3）。

为什么是"先位置、后名字"、为什么名字变了要再问一轮：访达不能一次把名字和位置原子地交出来（实测：把多个属性放进一个请求，访达不回答；
取"全部属性"又慢了近十倍），而两个请求之间桌面可能变化。访达的列表是**按名字排序**的（实测：改名后项目在列表里立刻换位），
所以"长度没变但次序变了"会让位置张冠李戴。做法见 `ConsistentDesktopRead.swift` 开头的说明，单元测试里重现了这几种情形。

### 6.4 不同轮询频率下的 CPU 占用（19 个图标，实测）

`swift run IconBridgeDemo --bench`（只读，约 3 分钟）。CPU 占用 = 这段时间里用掉的 CPU 时间 ÷ 时长，100% = 占满一个核。
"本进程"一栏已减去测量循环自身的 3.0%。

| 情形 | 访达 CPU | 本进程 CPU | 实际发生的读取 |
|---|---|---|---|
| 基线（图标桥没启动） | 0.05% | — | — |
| **活跃节奏** | **3.4%** | 0.2% | 32 秒里完整读取 4 次（平均 98 毫秒）、快速检查 29 次（平均 20 毫秒） |
| **空闲节奏** | **0.9%** | 0.04% | 65 秒里完整读取 2 次、快速检查 11 次 |
| 停止读取（suspended） | 0.02% | 0% | 无 |
| 每秒 1 次完整读取 | 12.4% | 0.7% | 平均 101 毫秒 / 次 |
| 每秒 2 次完整读取 | 25.5% | 1.3% | 平均 96 毫秒 / 次 |
| 每秒 5 次完整读取 | 56.9% | 3.1% | 平均 88 毫秒 / 次 |
| 连续不断地调用 `refreshNow()` | 62.0% | 4.4% | 4 秒里 26 次（间隔被限制在 0.15 秒） |

### 6.5 建议的节奏（已经是默认值，`PollSchedule.swift` 的 `PollingPolicy`）

| | 快速检查 | 完整读取 | 访达 CPU（19 个图标） |
|---|---|---|---|
| 活跃（刚有操作时） | 每 1 秒 | 每 8 秒 | 约 3.4% |
| 空闲 | 每 5 秒 | 每 30 秒 | 约 0.9% |
| 停止读取 | 不读 | 不读 | 0 |

- 用户用鼠标造成的变化（拖动图标、拖进废纸篓）不靠轮询，靠应用在松开鼠标时调用 `refreshNow()`：约 0.1 秒后上报。
- 两档间隔都会**按实测耗时自动拉长**（读取占用的时间比例有上限：活跃时快速检查 ≤ 1/50、完整读取 ≤ 1/80），
  所以图标很多的桌面自然读得更稀，访达的占用大致保持在上表的水平。"耗时"取最近三次里最快的一次，而且最多拉长到下限的 4 倍——
  访达偶尔慢一次（例如正忙着拷贝文件）不会让轮询停上几分钟。
- 原先想的是"活跃时每半秒数一次、每 2 秒完整读一次"，实测访达占到 7.3%，所以放慢到现在的数字。
  想让键盘删除的反应更快，可以把活跃档的快速检查改回 0.5 秒，代价是访达多占约 2%。

## 8. 工作原理摘要

### 8.1 文件

| 文件 | 内容 |
|---|---|
| `DesktopIconProvider.swift` | 模块入口。主线程上的调度：什么时候读、读哪一种、怎么上报、暂停与恢复 |
| `BridgeEngine.swift` | 把核心放到自己的后台队列上（一个用串行队列当执行器的 actor） |
| `BridgeCore.swift` | 核心：一个读取周期里的全部事情（读、比对、查废纸篓、定状态、出快照） |
| `ConsistentDesktopRead.swift` | 把几次独立的请求拼成一份前后一致的读数 |
| `DesktopQuerying.swift` | "向访达问桌面"的接口，和它的真实实现 |
| `FinderAppleEvents.swift` | 最底层：构造、发送 Apple 事件，解析回复 |
| `IconGeometry.swift` | 由位置推算图像矩形、标签矩形、所在显示器 |
| `IconIdentity.swift` | 种类判断；名字 → 不可读的编号 |
| `SnapshotDiff.swift` | 快照比对、废纸篓线索的判断、访达报错到状态的映射 |
| `PollSchedule.swift` | 轮询节奏 |
| `StacksProbe.swift` | 识别"叠放"：读访达的一项桌面显示设置（办法 B），位置完全相同的启发式（办法 A） |
| `IconIdentity.swift`（盐的存取） | 盐经一个小接口存取：应用里是本应用的偏好设置；单元测试用内存里的字典顶替，不落盘 |
| `AnchorCalibration.swift` | 校准用的像素分析 |

`BridgeCore` 对访达的一切访问都经过 `DesktopQuerying` 这个接口，所以单元测试用一个内存里的假桌面驱动它，不碰真实桌面。

### 8.2 读到了什么

- **哪些算桌面图标**：访达的 `every item of desktop`。实测它包含桌面文件夹里的可见项目，以及**确实显示在桌面上的磁盘**
  （访达设置里没勾选"硬盘"时，启动盘不在其中）；不包含隐藏文件（实测：桌面文件夹里有 2 个以点开头的项目，访达的列表里没有它们；
  给临时文件设上隐藏属性后它立刻从列表里消失，取消后又回来）。
- **种类**：由访达报告的"类"判断——文件夹、应用程序、磁盘各自对应；文稿、替身、网址快捷方式、剪报、文稿包都算"文件"；认不出的算"其它"。
- **编号**：由"名字 + 是否磁盘"加盐算出。桌面文件夹里不会有重名；两个磁盘可以同名，第二个起带上序号，各得一个编号。
- **修改时间**：第一次读取、名字列表有变化、以及每 60 秒读一次；种类也在这时一并重读。
- **显示选项**：图标大小、文字大小、标签位置、是否显示项目简介，每次完整读取都读。前三项任何一项变了，就以整体重载上报。

### 8.3 消失的图标是不是进了废纸篓

图标消失时，趁旧名字还在手里，问访达两件事：废纸篓里有没有同名的项目；废纸篓里的项目数比"之前"多了没有。

| 废纸篓变多了？ | 里面有同名项目？ | 结论 |
|---|---|---|
| 是 | 有 | **是** |
| 是 | 没有 | 不确定 |
| 否 | 有 / 没有 | **否**（同名的那个是以前就在的旧物） |
| 没有基准 | 有 | 不确定 |
| 没有基准 | 没有 | 否 |
| 查询失败 | | 不确定 |

只凭"废纸篓里有同名项目"不够——用户完全可能上周删过一个同名文件，这次只是把文件挪进了文件夹。磁盘从桌面消失是被推出，直接给"否"。

访达把一个文件移进废纸篓，在它的两个列表里（桌面少一项、废纸篓多一项）不一定同时生效，所以有两处防备：

- **"之前"的计数**不是上一次读取时的数，而是最近 3 秒内各次完整读取里**最小**的那个（外加再往前最近的一次）。
  这样即使访达先登记了废纸篓、稍后才从桌面的列表里去掉，而中间恰好有一次读取，也还看得出"变多了"。
  但超过 20 秒的旧计数不当基准（隔得越久，"变多了"越可能是别的东西进了废纸篓），从停止读取恢复时之前的计数也作废——
  没有基准时，废纸篓里有同名项目只能给"不确定"。
  这里的"20 秒""3 秒"量的都是**访达在回答的时间**：访达不回答的时间（典型情形是用户正拖着图标）不算——
  否则拖着图标犹豫二十几秒再扔进废纸篓，拖动之前读到的计数就过期了，给不出"进了废纸篓"（§4.3）。
- **第一次没查出"是"的**（而且两个问题都问成功了），统一稍等 0.25 秒再查一次——不管同时消失了几个图标，只等这一回。
  所以"确认进了废纸篓"的消失事件立即上报，其余的消失事件会晚约 0.3 秒。

实测（经访达移入废纸篓）：等访达答复我们的查询时，废纸篓里已经有它了，立即得到"是"。真人用鼠标拖进废纸篓时两个列表的先后还没有实测过，
上面两处防备就是为它准备的；`--slow-drag-check` 的第二步会验证（§9.5）。

已知会判错的罕见情形：废纸篓里本来就有同名旧物，这次文件被挪去了别处，而**恰好在上一次完整读取之后的这几秒到十几秒内**别的东西进了废纸篓——会误判成"是"。
（典型的例子：以前删过一个"未命名文件夹"，这次整理桌面时一边删别的文件、一边把新的"未命名文件夹"拖进了别的文件夹。）

### 8.4 状态

| 情形 | 状态 | 之后 |
|---|---|---|
| 还没读完第一次，或授权窗口等着用户回答 | `starting` | — |
| 用户拒绝了"控制访达"（预检结果为拒绝，或请求返回 -1743） | `permissionDenied` | 每 1 / 5 秒不弹窗地复查 |
| 访达没运行（-600）、连接断了（-609）、刚重启对象还没就绪（-1728）、其它任何失败 | `finderUnavailable` | 每 1 / 5 秒重试 |
| 等访达回复超时（-1712）：访达一时没空，典型情形是用户正拖着图标 | **状态不变**，快照原样保留，不上报 | 0.2 秒后再去等（只发一个最便宜的请求）；访达一回答就完整读一遍（§4.3） |
| 连续 5 分钟一个请求都不回答 | `finderUnavailable` | 继续等；访达回答了就恢复 |
| 桌面开启了叠放（§9.1） | `stacksEnabled` | 靠设置认出来的：每 1 / 5 秒复查（不惊动访达）；靠位置认出来的：每 8 / 30 秒复查 |

状态不是 `ok` 时快照的图标一律为空；状态每变一次，都以整体重载上报一次，不发任何"消失"事件。
版本号只在图标、外观或状态真的变了时加一：整体重载（例如从停止读取恢复）读到的内容如果和之前一模一样，照样上报，但版本号不变。
`stop()` 之后再 `start()`，版本号接着往上数，不从头再来。
桌面正在连续变化、一次读取试了三轮都拼不出一致的读数时，**不改状态**，保留旧快照，0.2 秒后重读。

## 9. 已知限制与待决问题

### 9.1 "叠放"的识别（已实现；"开了叠放"的那一面待用户配合验证）

开了叠放之后，访达报告的图标位置对不上屏幕上的样子（多半仍是叠放前的旧位置），脸会画在过期的位置上。所以要认出来，报告 `stacksEnabled`，什么都不画。

访达的脚本接口里**没有**"叠放"开关：桌面窗口的显示选项只有排列方式、图标大小、文字大小、标签位置、是否显示项目简介和预览这几项。
总览定的方案是两条办法一起用（代码在 `StacksProbe.swift`）：

**办法 B（主要依据）：读访达自己的一项桌面显示设置。** 偏好设置域 `com.apple.finder` 里 `DesktopViewSettings` 这一组设置中的 `GroupBy`（桌面按什么分组）。

| 读到的样子 | 判断 |
|---|---|
| 那一组设置里没有 `GroupBy`（本机没开叠放时就是这样） | 没开 |
| `GroupBy` 是"None"（不分大小写） | 没开 |
| `GroupBy` 是别的文字（例如 Kind） | **开了** |
| 那一组设置读不到；`GroupBy` 不是文字；是空的 | 无法判断 → 交给办法 A |

这一步偏离了提示词"只向访达询问"的字面要求，是总览代用户做的决定（用户回来后可改）。理由：它和图标桥本来就要读的图标大小、文字大小、标签位置是同一类信息；
不是用户的文件，不含文件名，读它不需要任何授权——符合那条硬性设计的本意（不碰用户文件、只要一项授权）。限定条件及落实情况：

| 限定条件 | 怎么落实的 |
|---|---|
| 只读、只读这一个值；经系统的偏好设置接口读，不按路径打开偏好文件；绝不写入 | 用系统的偏好设置接口（CFPreferences）按键取值，代码里没有任何写入。接口只能按顶层的键取，取回的是"桌面显示设置"这一组，代码只取其中的 `GroupBy`，其余立即丢弃 |
| 读不到、格式不认识、值不在预期内 → 无法判断，退回办法 A；不报错、不崩溃；不因为读不到就判定"开了叠放" | 见上表；有单元测试 |
| 读它不触发任何授权弹窗 | 命令行身份下实测：连读 200 次，每次中位 2 微秒、最长 4.9 毫秒，从不卡住（等授权会卡住）。**打包后的 .app 身份下请总览在整合阶段再确认一次** |
| 别的进程改了值之后要能读到新值 | 每次读之前先让系统同步这个域的缓存。用我自己的一个测试域实测（没有改访达的设置）：另一个进程写入、改值、删掉这一项之后，本进程都在 1 毫秒内读到新值。测试域已删除 |
| 不打印、不记录这个设置以外的任何偏好内容 | 模块里不打印、不记录任何东西；演示程序的 `--stacks-check` 也只打印这一项的有无和取值 |

**办法 A（兜底）：看访达报告的位置。** 只在办法 B 无法判断时使用：有 3 个或更多图标的位置完全相同，就当作开了叠放。
（正常的桌面上两个图标偶尔会被摆在同一个网格点，三个以上完全重合就很反常了。）它多半认不出真正的叠放，只是聊胜于无。

**多久能跟上**：办法 B 几乎不花时间，每次快速检查都会看一眼，所以打开叠放后最迟约 1 秒（活跃）/ 5 秒（空闲）报告 `stacksEnabled`；
处于这个状态时按同样的间隔复查，关掉叠放后同样快地恢复，并以整体重载上报。靠办法 A 认出来的，每 8 / 30 秒才复查一次（每次都要完整读一遍桌面）。

**没验证过的**：两条办法都没有在"真的开了叠放"的桌面上试过——我不能替用户切换叠放（那会改动用户桌面的显示方式）。
"开了叠放时 `GroupBy` 是分组依据"是推断：访达的程序里这个键名和其它显示设置的键名排在一起，本机没开叠放时没有这一项，除此之外没有直接证据。

**这个推断如果错了，有两种后果，请在用户验证之前心里有数：**

- 开了叠放而这一项没有变：认不出来，脸画在过期的位置上（和没有办法 B 时一样）。
- **关掉叠放之后访达仍保留着上一次的分组值**（而不是改回"None"或删掉）：图标桥会一直以为开着叠放，**什么都不画**。
  这比前一种更糟，而且只会发生在"用过叠放又关掉"的用户身上。下面第三次运行就是专门查这一点的。

**待用户配合**（三次运行，每次约 1 秒，只读）：

1. 没开叠放时运行一次 `swift run IconBridgeDemo --stacks-check`；
2. 桌面空白处点右键 → 使用叠放，再运行一次——第一行应当是"状态「桌面开启了叠放」"；
3. 把叠放关掉，再运行一次——第一行应当回到"状态「正常」"。

把三次输出交给总览即可定案。哪一次不符合预期，输出里的另外两行（那一项的实际取值、访达报告的位置有没有重合）就是改进的依据，改动只在 `StacksProbe.swift` 一个文件里。

没开叠放时的实测输出：

```
图标桥的判断：状态「正常」；提供图标 19 个
访达的桌面分组设置（办法 B 的依据）：没有这一项（没开叠放时就是这样）
访达报告的位置（办法 A 的依据）：共 19 个图标、19 个不同的位置；0 个位置被多个图标共用，最多 1 个图标挤在同一个位置；位置不在任何一块屏上的 0 个
```

### 9.2 其它限制

- **只在一台机器、一个系统版本、一种显示选项（64 点、12 点、标签在下、不排列）下实测过。**
- **标签矩形是估算**。标签在下方（64 点图标、12 点文字）已用截图校准；标签在右侧、别的大小没有校准（§3.3）。
- **访达不回答期间，快照是"访达卡住之前"的样子。** 这期间访达自己也动不了桌面，所以通常没有出入；
  唯一看得见的出入是正被拖着的那个图标（它的拖影跟着鼠标走，快照里它还在原位）——这本来就是交互感知按"鼠标位置 − 抓取偏移"来画的。
- **松手时如果正有请求卡在路上，上报比平时多等这个请求的回答**（估计十几毫秒）；长拖动（超过 15 秒）每 15 秒还会多留一个作废的请求给访达处理。真人数据待补（§9.5）。
- **种类只在名字变化或每 60 秒重读一次**：名字没变而种类变了（例如应用正在被拷贝到桌面，先是文件夹、拷完变成应用）最多晚 60 秒跟上。
- **个数没变的变化靠完整读取发现**：一个图标消失的同时另一个出现（例如改名），活跃时最迟约 8 秒才报。
- **图标被隐藏时**（访达设置成不显示桌面图标、"点按墙纸显示桌面"把图标收起等）访达仍照常报告位置，图标桥不知道它们其实看不见。
  这归叠加层的 `isDesktopVisible` 管。
- **iCloud 桌面、外接卷上的废纸篓**没有试过；废纸篓的两个问题都是问访达的总废纸篓。
- **立即删除**（不经废纸篓）报的是"消失，进了废纸篓：否"——这是接口的定义，但意味着这种删除没有幽灵，除非交互感知另有判断。

### 9.3 接口方面，没有需要改的地方

`IconProviding` 够用。两处自行决定的细节，写在这里备查：

- `refreshNow()` 在 `suspended` 期间被忽略（接口没有明说）。
- `DesktopIconProvider` 多了两个带默认值的构造参数（盐存在哪里、怎样取显示器布局）和一个只用于观察开销的回调 `onCycle`；
  `DesktopIconProvider()` 照常可用，应用入口不用改。
