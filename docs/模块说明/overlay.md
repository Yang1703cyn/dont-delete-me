# 叠加层（Overlay）模块说明

> **归属** overlay · **代码** `Sources/Overlay/` · **测试** `Tests/OverlayTests/` · **演示** `Demos/OverlayDemo/`
>
> 叠加层是"画布"：盖在桌面图标上方的透明窗口，别的模块把脸画在上面。它不知道画的是脸，也不知道图标在哪——
> 只负责在屏幕的正确位置、正确层级，以流畅且省电的方式把别人给的内容显示出来。
> 接口定义见 [接口约定.md](../接口约定.md) 第 7 节，这里只讲本模块自己的结论、做法、实测数据和限制。
>
> **它向系统打听的只有三样**，都是只读、不需要任何授权：当前在屏的窗口列表（只取所属进程、层级、透明度、边界，**不读窗口标题**）、
> 访达的进程号、是否锁屏 / 屏幕是否睡着。不读桌面内容，不读任何用户文件，不写任何东西。
>
> 文中所有实测都在 macOS 27.0.1（Apple Silicon）、内屏 1512×982 @2x（主屏，最高 120 Hz）+ 左侧外接屏 1920×1080 @1x（144 Hz）的机器上完成。
> **整个开发期间这台机器一直锁着屏**（没有人在场），所以每个数字都标了测量时的状态；凡是只有解锁后才作数的，列在 §7 的人工检查清单里。

## 1. 结论一览

| 问题 | 结论 | 把握 |
|---|---|---|
| a. 怎么画最省 | **每张脸一个小图层，自己画位图再贴上去；只重画变了的，位置变了只挪图层。** 整窗一张画布在内屏（2x）上贵 4 倍多 | 已实测（§4） |
| a. 开销 | 空闲 0.1%（完全休息）～约 1.5%（每秒醒 10 次并偶尔眨眼）；30 张脸**每帧全部重画**时 60 帧/秒、本进程约 25%（内屏）/ 26%（外接屏），**超过 15% 的目标**。其中约 20 个百分点是替身脸自己的绘制，叠加层自身约 5 个百分点；只挪位置不重画约 2% | 熄屏、亮屏未解锁两种状态已实测；解锁状态**待用户配合**复测（§4.4） |
| b. 拖拽层层级 | **系统拖影层 +1（501）**：高于普通窗口、程序坞、菜单栏、各种弹出菜单和系统的拖影，低于屏保和锁屏 | 层级与点击穿透已自动验证；"真实拖放不受干扰"**待用户配合**（§5） |
| c. 切换空间 | 桌面层窗口**属于某一个空间**，像普通窗口一样跟着自己的空间滑走；每个去过的空间各留一个窗口 | 机制上不会错位；肉眼效果**待用户配合**（§6.1） |
| c. 全屏空间 | 不显示。判断依据：那块屏上访达的图标层窗口不在"在屏窗口"里 | 已在真实的全屏空间里实测（§6.2） |
| c. 访达隐藏桌面图标 | 脸跟着隐藏。判断依据：系统在图标层、访达窗口的前面放了一块整屏的遮挡窗口 | 开发机正处于这种状态，已观察到；"显示 ↔ 隐藏"的切换过程**待用户配合**（§6.3） |
| c. 显示器变化 | 自动重建全部窗口，下一帧全部重画 | 用假布局模拟已验证；真实插拔**待用户配合**（§6.4） |
| c. 锁屏、屏幕睡眠、被完全挡住、暂停 | 停止帧回调、不作画，`isDesktopVisible` 为 false | 锁屏、睡眠、唤醒、暂停已实测；解锁、被窗口挡住**待用户配合**（§6.5） |
| 点击穿透、不抢焦点 | 窗口在第一次显示之前就已点击穿透；叠加层出现前后，40 个探测点上"鼠标会落到哪个窗口"完全相同 | 已自动验证（§3.1），手感**待用户配合** |

**一个需要用户知道的发现**：开发机的系统设置里，「桌面与程序坞 → 显示项目：在桌面上」是**关着**的（桌面项目平时被系统隐藏）。
按任务书"访达隐藏桌面图标时脸也要隐藏"的要求，在这台机器上脸平时不会出现，只有桌面项目显示出来时才出现。详见 §6.3 和 §10。

## 2. 怎么用（给总览的集成注意事项）

```swift
let overlay = OverlayHost()            // 应用里就这样构造；入口类型名和构造方式没变
overlay.frameSource = pipeline         // 弱引用
overlay.onDesktopVisibilityChange = { visible in … }
overlay.start()
```

1. **`isDesktopVisible` 启动后先是 false**，大约 0.35 秒后（确认图标层真的看得见）才变成 true 并回调 `onDesktopVisibilityChange(true)`。
   现在的 `FramePipeline.start()` 先读它决定图标桥的节奏、再等回调切换，正好对得上，不用改。
2. **桌面看不见时一帧都不出**，这是约定的行为，但它让现在的应用自检失败：
   锁着屏跑 `swift run DontDeleteMe --smoke-test 3`，结果是"运行阶段没有任何帧回调 / 没有收到图标上报 / 继续之后没有恢复帧回调"。
   自检需要区分"桌面不可见所以不出帧"和"坏了"（例如桌面不可见时改为检查 `isDesktopVisible == false` 且帧数为 0）。
   `Sources/DontDeleteMe/` 不归我，没有动。
   > **总览批注（已修）**：自检现在会区分这种情况——桌面看不见时最后一行是 `smoke-test: PASS-LIMITED`，并检查"看不见时确实一帧没出"；
   > 加 `--assume-visible` 可以在锁屏时也跑完整条流水线。见 `docs/开发说明.md` §9.3。
3. **系统通知只在真正的应用事件循环里才送得到。** 实测：只转 `RunLoop.main.run()` 的进程收不到"屏幕睡眠 / 唤醒"通知，
   `NSApplication.run()`（或自己取事件再分发）才收得到。应用入口走的是 `NSApplication.run()`，没有问题；
   演示程序里我用"取事件再分发"的方式转主循环。以后谁写带叠加层的演示或测试程序，请照 `Demos/OverlayDemo/Support.swift` 里的 `spin` 来。
4. **帧时间**用的是帧回调那一刻的 `FrameTime.now()`，不用显示刷新的目标时刻，满足"帧时间不得超前"。
5. **帧率封顶约 60**。跟着内屏（120 Hz）时是每秒 60 帧；跟着 144 Hz 的屏时系统给的是 72（每两个刷新一帧）。
6. **画布大小成档很重要。** 同样像素大小的画布会被反复使用（§4.3）；如果 `outsets` 每帧连续变化，每帧都得新建画布，开销会明显变大。
   接口约定已经要求 `outsets` 成档稳定，这里再强调一次。
7. **绘制回调里"保存 / 恢复绘图状态"必须成对。** 画布是反复使用的：每次交出去之前，坐标系、裁剪、颜色、线宽等都会回到初始状态——
   前提是上一次绘制没有多 `saveGState()` 少 `restoreGState()`。
8. **色彩**：画布和叠加窗口都是 sRGB。绘制时直接给的红绿蓝数值按 sRGB 显示（内屏是广色域，颜色不会因此变艳）。
9. **所有窗口都在本进程名下**（每块屏、每个去过的桌面空间各一个桌面层窗口，外加拖拽期间每块屏一个拖拽层窗口）。
   交互感知按"窗口属于不属于本进程"来排除自家窗口，仍然成立。
10. **桌面图标被系统隐藏时**，`isDesktopVisible` 是 false，应用会让图标桥停止读取——符合"看不见时务必是 false"的要求。
11. **可调选项**（`OverlayOptions`，应用里用默认值）：
    - `maxDesktopWindowsPerDisplay`（默认 6）：每块屏最多保留几个桌面层窗口。设成 1 就是"每块屏只有一个窗口，切换空间后搬过去再淡入"。
    - `treatsDesktopShieldAsHidden`（默认 true）：万一"图标被隐藏"的判断在某个系统版本上有误，这里一行关掉。
    - `assumesAlwaysVisible`（默认 false）：只给演示和测量用，应用里不要开。
12. **可以在帧回调或绘制回调里暂停、停止叠加层。** 那之后这一帧剩下的项不再画（恢复后补上），也不会再建窗或显示窗口。
13. **用完请调用 `stop()`。** 没停止就把它释放掉的话，窗口、显示刷新回调和定时器会自己清理，但对系统通知的登记会留着（无害，只是多余）。
14. **排查问题**：`overlay.diagnostics` 给出一份状态快照（每块屏的图标层状态、窗口数、是否被挡住、帧循环状态、帧数……），不含任何用户数据。
    命令行里 `swift run OverlayDemo --probe` 打印同样的内容外加系统那几层窗口的情况。

## 3. 做法

```
OverlayHost（入口，把下面这些串起来）
├── FrameScheduler   省电信号 → 帧循环该处于什么状态（纯逻辑）
├── FrameClock       显示刷新节拍（封顶 60），不需要时完全停掉
├── SystemEventMonitor / SystemProbe   系统通知；窗口列表、锁屏、睡眠（只读）
├── DesktopVisibility   图标层在不在、有没有被遮住；桌面是否可见（纯逻辑）
└── DisplayStage × 每块屏 ×（桌面层、拖拽层）
    ├── ScenePlanner     每个画布项这一帧：不动 / 只挪 / 重画 / 先欠着（纯逻辑）
    ├── ItemRasterizer   造画布（全局坐标、y 向下、已裁剪、已清空），画完取图
    └── CanvasWindow     透明点击穿透窗口，每个画布项一个小图层
```

### 3.1 窗口：安全线怎么守

- 窗口用"推迟创建"的方式构造，**第一件事就是设成不接收鼠标事件**，此时系统里还没有这个窗口；之后才可能被显示。
- 不能成为键盘焦点窗口、不能成为主窗口；显示时用"不激活应用"的方式；应用隐藏时不跟着隐藏。
- 自动验证（`swift run OverlayDemo --self-check`，不产生任何鼠标键盘事件）：在两块屏上取 40 个点，问系统"鼠标点在这里会落到哪个窗口"，
  叠加层出现前、桌面层出现后、拖拽层出现后、全部关闭后各问一遍，四次答案完全相同，而且从不是叠加窗口；
  全程本进程没有焦点窗口、没有变成前台应用、前台应用没变。

### 3.2 坐标

调用方只说全局坐标。每块屏各自换算：画布矩形 → 屏内坐标 → **向外取整到这块屏的像素格** → 位图。
位图按 1:1 贴在图层上，所以内屏（每点 2 像素）和外接屏（每点 1 像素）都不会因为半个像素的偏移发虚。
交给调用方的画布已经调成全局坐标（y 向下、单位点）、裁剪到画布矩形、清空为全透明。

- **跨两块屏**：画布与哪块屏相交，就在哪块屏上有一个图层、一块按那块屏的缩放画出的位图；窗口裁掉屏外的部分。同一项在这一帧被回调两次。
- **只挪位置不重画**：图层按整数个像素挪，从"上次重画时的位置"算起，误差不累积；与精确位置最多差半个像素（内屏 0.25 点、外接屏 0.5 点）。
- **保护**：矩形含非数字、没有面积、或单边超过 4096 像素（只可能是传错了）的项不画，免得去分配巨大的位图。
- **这块屏看不见时**（被挡住、在别的空间）不回调绘制，先欠着；看得见了补画。另一块屏照常。

### 3.3 帧循环

| 调用方给的需求 | 叠加层怎么做 |
|---|---|
| 连续 | 开着显示刷新回调，每个节拍出一帧 |
| 某个时刻之前（离现在超过 0.05 秒） | 关掉显示刷新回调，用一个定时器到点醒一次；中间没有任何开销 |
| 某个时刻之前（0.05 秒以内） | 守着显示刷新，在**不早于**那个时刻的第一个节拍出帧 |
| 休息 | 什么都不开，直到 `requestFrame()` |

约定的时刻没到就不出帧，哪怕只差一毫秒：调用方是拿帧时间和它约的时刻比的，早到的那一帧它什么都不会做，只会原样再约一次。
时刻值不是一个数（非数字、正无穷）时当作"休息"。

显示刷新回调偶尔会自己停掉（实测：亮屏未解锁时会停几十毫秒；所跟的屏睡着时完全不来）。帧循环不能因此卡死：
超过 0.06 秒没来就让一个每秒 60 次的备用定时器顶上，回调恢复后再退下。实测停顿因此从约 220 毫秒缩短到 80～100 毫秒。

### 3.4 桌面是否可见

`isDesktopVisible` = 会话在线（没锁屏、屏幕没睡、电脑没睡、没切到别的用户）且至少有一块屏满足：
图标层看得见、我们在当前空间里有窗口、窗口没被完全挡住。

- **藏得快、出得慢**："看不见"立刻生效；"看得见"要连续成立 0.35 秒才作数。切换空间、显示桌面这类过渡动画里系统会短暂地撤掉再放回遮挡窗口，这样脸不会在中途闪一下。
- **"被挡住"的报告先验证再采信**：窗口是否被完全挡住由系统报告。因为锁着屏没法验证它对我们这种窗口管不管用，
  叠加层只在亲眼见过它报告"没被挡住"之后才采信"被挡住"。万一它不管用，后果只是多费点电，而不是永远不画。
- **巡检**：系统隐藏 / 显示桌面图标没有任何通知，只能隔一会儿看一眼窗口列表（一次约 0.3～0.5 毫秒）。
  桌面露在外面时每秒一次；被窗口完全挡住或停在全屏空间时每 10 秒一次；锁屏、睡眠期间每 2 秒只读"是否锁屏、屏幕是否睡着"（约 0.06 毫秒）；暂停时完全不巡检。
  其余状态变化（切换空间、锁屏解锁、睡眠唤醒、被挡住、显示器变化、前台应用变化）都由系统通知触发，立即处理。

## 4. a. 绘制方式

### 4.1 四种方式的对比

30 张替身脸、指针每帧都在动、**每张脸每帧都重画**（最坏情形）。发布版。"每帧耗处理器" = 处理器占用 ÷ 帧率。

亮屏未解锁（显示刷新回调驱动），终稿代码：

| 屏 | 方式 | 帧/秒 | 本进程处理器 | 每帧耗处理器 |
|---|---|---|---|---|
| 内屏 @2x | 一、整窗一张画布，每帧整窗重画 | 60.0 | 104.6% | 17.43 毫秒 |
| 内屏 @2x | 二、整窗一张画布，只重画变了的矩形 | 60.0 | 105.4% | 17.57 毫秒 |
| 内屏 @2x | 三、每张脸一个图层，系统管位图、回调我们画 | （见注） | — | 4.13 毫秒 |
| 内屏 @2x | **四、每张脸一个图层，自己画位图再贴（选定）** | 60.0 | 24.4% | **4.06 毫秒** |
| 外接屏 @1x | 一 | 72.0 | 19.3% | 2.68 毫秒 |
| 外接屏 @1x | 二 | 70.7 | 22.8% | 3.23 毫秒 |
| 外接屏 @1x | 三 | 59.9 | 26.4% | 4.40 毫秒 |
| 外接屏 @1x | **四（选定）** | 60.0 | 26.1% | **4.36 毫秒** |

注：方式三在内屏那一轮只拿到每秒 16.7 个节拍（锁屏下显示刷新回调时有时无），所以只有"每帧耗处理器"可比。
熄屏状态下（定时器驱动、每秒 60 帧）量到的是：内屏 一 15.5 / 二 15.8 / 三 4.2 / 四 4.5 毫秒；外接屏 一 4.6 / 二 5.4 / 三 5.2 / 四 5.5 毫秒（那一轮的方式四还没有做 §4.3 的第二项优化）。

**结论：选方式四。**

- 整窗画布在内屏上贵 4 倍多：内屏的整窗位图有 3024×1964 像素（约 24 MB），每帧清空、重画、提交。只重画变了的矩形也救不了——所有的脸都在变。
- 在一倍屏上，"全部都在变"时整窗画布反而略省（位图只有 8 MB，一次画完）。但它在别的情形都输：只有两三张脸在变时照样要提交整窗；
  位置变了必须重画（做不到"只挪不画"）；而且两块屏要用两套做法。
- 方式三和方式四开销相当。选四是因为：一块位图可以同时贴到多个窗口上（每个桌面空间各有一个窗口，§6.1），画一次就够；
  绘制发生在帧回调之内，时机由我们控制（约定要求在本帧之内）；看不见的屏可以先欠着不画；画布可以脱离窗口做逐像素的单元测试。

熄屏（已锁屏；定时器驱动，每秒 60.0 帧，最长帧间隔 18.7 毫秒），终稿代码。
这一轮是在修完独立审阅提出的问题之后量的；上面亮屏那一轮是在那之前量的，两轮之间的改动不涉及作画路径，熄屏数字前后也没有差别。

**对照目标：**

- 空闲时接近 0：**达到**。完全休息 0.1%（这 0.1% 是演示程序自己每秒看 4 次"要不要退出"）；每秒醒 10 次再加偶尔眨眼约 1～1.5%。
- 30 张脸同时动时约 60 帧：**达到**（58.5～60.0）。帧间隔 16.7 毫秒；标着 80～100 毫秒的几行是锁屏下显示刷新回调停了一下、备用定时器接手的那一瞬间。
- 本进程不超过约 15%：**没达到**——"每帧全部重画"这个最坏情形是 25%～33%。

**瓶颈在哪：** 采样器显示时间花在 CoreGraphics 的路径光栅化上，也就是替身脸本身的绘制：每秒 1800 张，每张约 0.11～0.14 毫秒
（一块半透明圆角底色 + 两只带描边的眼睛 + 两个瞳孔，共 8 次填充或描边）。它占了总占用的八成。叠加层自身（造画布、取图、贴图层、提交）约占 5 个百分点。
"不画内容"那一行量到的 8%～11% 比这 5 个百分点高，我的推测是负载轻时处理器降频、同样的活耗时更长——所以这类占用数字本身随负载和电源状态浮动，
锁屏状态下尤其不能当成解锁后的真值。

**这对别的模块意味着什么（请总览留意）：**

- 一帧 15% 的预算是 2.5 毫秒。扣掉叠加层约 0.8 毫秒，30 张脸只剩 1.7 毫秒，也就是**每张脸约 0.05 毫秒**。
  接口约定里表情绘制的目标是"每张不超过约 0.3 毫秒"，按它算 30 张全部重画是 9 毫秒，占一个核心的 54%——这两个目标互相对不上。
- 鼠标一动、所有的脸视线都变，于是"每帧全部重画"不是罕见情形，而是这个产品最常见的活跃状态。要守住 15%，办法在调用方这一侧：
  1. 视线取整：演示程序默认把视线方向取整到 1/64，远处的脸几帧才变一次（见 `StandInFace.gaze`）。
     实测（熄屏，两块屏各 15 张）重画量从每秒约 1860 降到约 1180，占用从 33% 左右降到 26.8%——有用，但光靠它不够；
  2. 视线的重画限到每秒 30 次（位置移动仍然每秒 60 次，"只挪不画"只要 2% 左右）；
  3. 让表情绘制足够便宜。
- 表里各行之间相差几个百分点的地方不要细究（例如"只画两只眼睛"在内屏上反而比画整张脸略高）：负载轻重不同，处理器的频率和所用的核心也不同。
  站得住的结论是量级：整窗画布在内屏上贵 4 倍；空闲接近 0；只挪位置约 2%；全部重画 25%～33%，其中内容绘制占八成。
- 叠加层这一侧还剩一个可做的优化：把贴图换成与系统窗口服务共享的显存表面，省掉每帧把 30 张位图发给系统的那一次传送
  （采样显示它占叠加层自身开销的一半以上，系统那边也省一次上传）。估计能再省 2～5 个百分点。
  没有做的原因：它需要亮着屏、肉眼确认没有撕裂和闪烁，现在做不了。列在 §10。

### 4.3 两个值得记下来的坑

1. **窗口的色彩空间要和位图一致。** 窗口默认跟着屏幕走，内屏是广色域；位图是 sRGB。不设的话，每次换图系统都在**本进程里**用处理器把整张位图转一遍色彩。
   把窗口设成 sRGB 后转换改由系统在合成时用显卡完成，颜色不变。内屏全员跟随从 45.9% 降到 27.5%（熄屏状态实测）。
2. **画布要反复用，不要每次新建。** 每秒 1800 块位图，每块都向系统要内存、用完归还的话，内存映射、首次写入时的缺页、解除映射加起来比真正的活还多。
   现在同样大小的画布（内存连同绑在上面的绘图上下文）留在池子里，清零、恢复绘图状态后再用；取图时不拷贝像素，图被释放时画布自动回池。
   "不画内容"的开销从 15.4% 降到 10.4%（内屏）、13.1% 降到 6.1%（外接屏）。池子有上限（每种大小 96 块、总共 48 MB），停止运行时清空。

## 5. b. 拖拽层的层级

**结论：系统拖影层 +1，也就是 501。**

本机的层级值（`CGWindowLevelForKey`）：桌面图标 −2147483603 · 普通窗口 0 · 浮动 3 · 程序坞 20 · 菜单栏 24 · 状态栏 25 · 弹出菜单 101 · 帮助标签 200 ·
**拖影 500** · 屏保 1000 · 辅助功能最高 1500 · 光标 2147483630。

- **为什么不能更低**：系统拖放时，被拖东西的影子（拖影）画在 500 这一层。脸要画在拖影上，低于 500 就会被拖影盖住；
  而高于 500 自然也就高于普通窗口、程序坞、菜单栏和各种菜单。
- **为什么不取更高**：1000 以上会盖到屏保和锁屏界面上去（锁屏窗口实测在 2001 以上）。501 时锁屏会盖住我们，这是对的。
- **会不会干扰拖放**：窗口不接收鼠标事件，系统寻找"鼠标下面是谁"时会跳过它。自动验证的部分：拖拽层显示期间，
  40 个探测点以及拖拽项正下方那一点上，"鼠标会落到哪个窗口"与没有它时完全相同；它在系统窗口列表里的层级是 501，
  排在所有层级不高于 500 的窗口之前（实测时它后面层级最高的是 24 的菜单栏；前面只有 2001 以上的锁屏窗口）。
  **真实拖放时访达、程序坞、废纸篓的反应是否完全不变，必须真人拖一次**，见 §7 第 6 项。
- **实现上是每块屏一个拖拽层窗口**，用到时才建，只在有拖拽项落在那块屏上时显示，没有就收起。
  为什么不是一个大窗口：系统默认"每块显示器有各自的空间"，一个窗口只会显示在一块屏上；拖着图标跨屏时，骑在接缝上的脸要两边各画一半。
  拖拽层窗口所有空间都有、全屏应用上方也能显示（拖着图标切换空间时脸不丢）。

## 6. c. 各种系统状态下的表现

### 6.1 切换桌面空间

**做法**：桌面层窗口不是"所有空间都有"的那种窗口，而是**属于某一个桌面空间**。切换时它和普通窗口一样跟着自己的空间滑走，与图标同步——
这是系统对所有窗口的一贯行为，不需要我们感知动画什么时候开始、什么时候结束。

- 第一次来到某个空间：那里还没有我们的窗口，新建一个，等 0.45 秒（切换动画结束）后淡入。也就是任务书说的"做不到同步就短暂淡出、切完再出现"。
- 再回到去过的空间：窗口已经在那里，和图标一起滑进来，全程同步。
- 所有窗口显示同样的内容，共用同一批位图。不在当前空间的窗口在帧循环空下来时、以及切换发生时才更新，平时不占开销。
- 每块屏最多留 6 个窗口，超出时关掉最久没用的；某个空间被删掉、它的窗口并进隔壁时，同一空间里多出来的那个会被关掉。
- 切换之后一秒再核对一次：切换那一刻系统对"窗口在不在当前空间"的回答可能还没跟上，用户也可能紧接着又切了一次。
- 不是切换空间引起的例行巡检，最多每 10 秒新建一个窗口——防的是"系统总说我们的窗口不在当前空间"这类意外，那样也只是偶尔多建一个。

**为什么不用"所有空间都有"的窗口**：那种窗口在切换动画中是原地不动的（把某个应用设成"所有桌面"时就是这样），而图标会跟着桌面滑走，
正是任务书要避免的"图标滑走、脸留在原地"。访达自己的图标窗口虽然也是"所有空间都有"，却会跟着滑——那是系统对它的特殊处理（实测它确实属于这块屏的每一个桌面空间），我们的窗口享受不到。
而且切换开始时系统并没有通知（三指滑动时尤其如此），没法做到"先淡出"。

**没法自动验证的**：肉眼看到的同步效果、调度中心里的样子。见 §7 第 7、13 项。如果实际效果不如预期，`maxDesktopWindowsPerDisplay = 1` 是现成的退路。

### 6.2 全屏应用所在的空间

**不显示，也不建窗。** 开发机的内屏在整个开发期间正好停在一个全屏应用的空间里，所以这一条是真实观察到的：

- 那块屏上，访达的图标层窗口**不在**"在屏窗口"里（外接屏停在普通桌面，访达的图标层窗口在）。叠加层据此判断"这块屏上没有图标层"：不建窗、不可见。
- 即使硬要在全屏空间里建一个桌面层窗口，系统也不会让它出现在那里，而是放到这块屏的某个普通桌面空间去
  （"强制可见"时看到的：窗口不在屏上，查它所属的空间是这块屏的第一个桌面）。
- 进出全屏会触发"空间变了"的系统通知，叠加层立即重新判断。

### 6.3 访达隐藏了桌面图标

**怎样判断图标层当前是否可见（任务书要求查清）：**

看当前在屏的窗口列表（从前到后）。对每一块屏：

1. 找访达的、层级为"桌面图标层"、盖住这块屏的窗口。**找不到** → 图标层不在（全屏空间、访达没运行、窗口被收起或调成全透明）。
2. 找到了，再看它**前面**有没有别的进程的、**同一层级**、盖住这块屏九成以上、不是全透明的窗口。**有** → 图标被遮住了。
3. 都没有 → 图标看得见。

**依据**（开发机正好处于"桌面项目被隐藏"的状态）：

- 系统设置里「在桌面上显示项目」是关着的（偏好设置 `com.apple.WindowManager` 的 `StandardHideDesktopIcons` 为真）。
- 此时访达的图标层窗口**照常在屏、透明度是 1**——所以只看访达的窗口是看不出来的。
- 在外接屏当前的桌面空间里，系统的窗口管理程序（WindowManager）有一个整屏窗口，层级正好是桌面图标层，排在访达图标窗口的**前面**；
  它的各项标记与墙纸窗口一模一样，而且只存在于当前这个空间。别的桌面空间和全屏空间里都没有这样的窗口。
- 这个程序的可执行文件里有 `WallpaperShieldWindow`、`desktopIconsHidden`、`prefersDesktopIconsHidden`、`revealDesktopContentForSpaceSwitch` 这些名字。

合起来的解释：**系统隐藏桌面项目的办法，是在图标前面盖一块画着墙纸的窗口**，而不是让访达把图标收起来。
我们的窗口在"图标层 +1"，在这块遮挡窗口的上面，所以必须自己识别、自己把脸藏起来。

**表现**：发现被遮住后脸在 0.12 秒内淡出，`isDesktopVisible` 变 false（如果别的屏也看不见）；遮挡撤掉后，确认 0.35 秒，脸在 0.2 秒内淡入。
发现的时机：有前台应用切换等系统通知时立刻；否则靠每秒一次的巡检，最迟约 1 秒。

**把握与风险**：以上是从一个状态的观察推出来的——我不能替用户改系统设置，所以"显示 ↔ 隐藏"切换时那块窗口是否如预期地出现和消失，还没有亲眼看到。
如果推断错了，会有两种后果之一：脸永远不出现，或者图标隐藏时脸还浮在墙纸上。两种都能在 §7 第 9 项里半分钟查出来；
前一种可以立刻用 `treatsDesktopShieldAsHidden = false` 绕开。

**已知的识别盲区**：只认"同一层级"的遮挡。第三方的"隐藏桌面图标"工具如果用更高层级的窗口去盖，识别不到（脸会浮在它上面，或被它盖住，取决于谁在前）。
故意不把更高层级的整屏窗口也算作遮挡，是因为那样一来本项目的两个进程（比如应用和演示程序同时运行）会互相把对方当成遮挡。

### 6.4 显示器插拔、分辨率或排列变化

收到系统的"屏幕参数变了"通知后重新读布局；布局确实变了，就关掉全部窗口、按新布局重建，下一帧所有画布项重画（位置按新布局换算）。布局没变（例如只是唤醒）则什么都不重建。

自动验证（自检第 8 步）：给叠加层一个假的布局来源，把一块屏"缩小并挪动"，再由演示程序自己发出那条系统通知——
窗口按新位置重建、旧窗口没有残留、全部重画、位置正确；恢复真实布局后窗口回到原处。真实的插拔见 §7 第 12 项。

### 6.5 锁屏、屏幕睡眠、桌面被完全挡住、应用被暂停

| 状态 | 表现 | 验证情况 |
|---|---|---|
| 锁屏 | 不可见、不出帧、不作画 | **实测**：开发期间一直锁着。默认设置的叠加层 1.5 秒内帧数 0、绘制 0；不带参数的演示 20 秒本进程占用 0.2% |
| 屏幕睡眠 / 唤醒 | 不可见；唤醒后立即重新判断 | **实测**：屏幕被点亮和再次睡着的那一刻都收到了系统通知并立即更新（仍在锁屏，所以保持不可见） |
| 解锁 | 立即恢复；窗口在锁屏期间就已备好 | 待用户配合（§7 第 11 项）。万一漏了解锁通知，2 秒一次的巡检也会发现 |
| 桌面被完全挡住 | 那块屏不作画；所有屏都被挡住时 `isDesktopVisible` 为 false | 待用户配合（§7 第 10 项）。依赖系统的"窗口被挡住"报告，采信前先验证（§3.4） |
| 暂停 | 停止帧回调，内容淡出，拖拽层收起；恢复时重新显示并出一帧 | **实测**（自检第 7 步）：暂停 0.5 秒内 0 帧、画面读回全透明、拖拽层收起；恢复后 0.6 秒出了 36 帧，画面和拖拽层都回来 |
| 电脑睡眠 / 快速切换到别的用户 | 不可见 | 只有单元测试 |

暂停时窗口本身留着（只是内容隐藏、不出帧、不巡检），这样恢复时不必重建各个空间里的窗口。从外面看和"隐藏所有窗口"没有区别：屏幕上什么都没有，也不参与合成。

| 6 | 拖放不受干扰 | 同上运行中，真的拖一个桌面文件（或新建的空文件夹）：拖到程序坞的废纸篓上方**停住不松手**；再拖到一个访达窗口里的文件夹上停一下；最后拖回桌面空白处松手 | 废纸篓照常变亮、显示名称；文件夹照常高亮、稍后自动打开；松手后文件落在新位置。全程和没有演示时完全一样 |
| 7 | 切换空间 | `swift run OverlayDemo --mode follow --seconds 30`，切到另一个桌面再切回来（Control+方向键，再用触控板三指滑动各试一次） | 离开时眼睛跟着桌面一起滑走，不留在原地；第一次到新桌面，动画结束后约半秒眼睛淡入；回到去过的桌面时，眼睛跟着桌面一起滑进来 |
| 8 | 全屏空间 | 同上运行中，把任意窗口切成全屏（绿色按钮），再退出全屏 | 全屏空间里没有眼睛；退出回到桌面后眼睛回来 |
| 9 | 访达隐藏桌面图标 | `swift run OverlayDemo --probe --watch 40`，然后让桌面项目在"显示"和"隐藏"之间切换一次：系统设置 → 桌面与程序坞 → 显示项目「在桌面上」；或者用"显示桌面"（触控板拇指和三指张开，或 F11） | 桌面项目显示着时终端写「图标层=visible」、眼睛在；隐藏时一秒左右变成「图标层=shielded」、眼睛淡出。**请把终端输出贴给总览**（这一项用来确认 §6.3 的判断方法） |
| 10 | 被完全挡住 | `swift run OverlayDemo --probe --watch 30`，把一个窗口拉到盖满一整块屏（按住 Option 点绿色按钮），再挪开 | 那块屏变成「被挡住=true 看得见=false」；所有屏都盖住时「桌面可见=false」；挪开后恢复 |
| 11 | 锁屏与解锁 | `swift run OverlayDemo --probe --watch 40`，按 Control+Command+Q 锁屏，过两三秒解锁 | 终端先出现「锁屏=true … 桌面可见=false」，解锁后回到「桌面可见=true」；解锁的一瞬间眼睛就在 |
| 12 | 显示器插拔 | `swift run OverlayDemo --mode follow --seconds 40`，拔掉外接屏，再插回去 | 拔掉后内屏上的眼睛还在、位置正确；插回后外接屏上的眼睛重新出现 |
| 13 | 调度中心、显示桌面 | `swift run OverlayDemo --mode follow --seconds 30`，按 F3 进出调度中心，再按 F11 显示桌面 | 眼睛留在桌面上（或暂时消失），不会多出一块空白的窗口缩略图；显示桌面时眼睛留在原位 |
| 14 | 退出干净 | 任一演示运行中按 Ctrl-C，然后 `pgrep OverlayDemo` | 眼睛立刻消失；第二条命令没有任何输出 |

另有两条不需要操作、只需贴输出的命令：§4.4 的复测，以及 `swift run OverlayDemo --self-check`（解锁状态下再跑一遍，约 14 秒，最后一行应是 `self-check: PASS`）。
锁屏时这份自检里有一处看不到：内屏停在全屏空间，所以"桌面层窗口排在访达图标窗口之前、所有普通窗口之后"只在外接屏上核对过；解锁并让内屏回到桌面后再跑，两块屏都会核对。

## 8. 已知限制

- **只在 macOS 27.0.1 上跑过。** §6.3 的判断方法尤其依赖这个版本上观察到的窗口布置，别的版本可能不同。
- **锁屏状态下做不了的验证**都在 §7。其中 §6.1（切换空间的肉眼效果）、§6.3（隐藏判断）、"被完全挡住"三项，实现里各留了退路（选项或先验证再采信）。
- **第一次来到一个新的桌面空间**，脸在动画结束后才淡入，晚大约半秒。
- **图标被系统隐藏 / 重新显示**，没有系统通知时最迟约 1 秒发现；重新显示时再加 0.35 秒的确认。期间脸可能在墙纸上多停留不到一秒。
- **第三方的"隐藏桌面图标"工具**用更高层级的窗口遮盖时识别不到（§6.3）。
- **只挪位置不重画**时，图层与精确位置最多差半个像素。
- **跟着 144 Hz 的屏时是每秒 72 帧**，不是 60。
- **30 张脸每帧全部重画超过 15% 的目标**，瓶颈在内容绘制（§4.2）。
- 显示刷新回调偶尔停顿时（目前只在锁屏下见过），会有一次 80～100 毫秒的帧间隔。
- 桌面小组件的层级是"图标层 +2"，比我们高一级：脸会被小组件盖住。这符合"脸贴在图标上"的直觉，但没有专门处理。

## 9. 怎么运行

```bash
swift run OverlayDemo                              # 自动巡演三种模式，约 20 秒
swift run OverlayDemo --mode idle|follow|drag      # 单一模式，默认 20 秒（--seconds N，最长 60）
swift run OverlayDemo --self-check                 # 自动自检，约 14 秒；最后一行 self-check: PASS / FAIL
swift run OverlayDemo --probe [--watch N]          # 系统状态探针；--watch 持续观察 N 秒
swift run -c release OverlayDemo --bench           # 实测选定方案，约 55 秒
swift run -c release OverlayDemo --bench-compare   # 对比四种绘制方式，约 45 秒
scripts/test.sh --filter OverlayTests              # 65 个单元测试
scripts/check.sh Overlay                           # 编译无警告 + 依赖规则 + 测试 + 演示能自己结束
```

公用参数：`--force`（不管桌面看不看得见都照常建窗出帧，锁屏时测试用）、`--pointer mouse|synthetic|auto`、`--count N`、
`--single-window`（每块屏只用一个桌面层窗口）、`--ignore-shield`（不把系统的遮挡窗口当作"图标被隐藏"）、`--fine`（视线不取整，每帧全部重画）。

单元测试覆盖的是纯逻辑：坐标换算、画布（逐像素）、画布池、重画判定、帧调度、图标层判断、可见性判断，以及不建窗的启停。
需要真实窗口的验证都在自检里（51 项）：窗口层级与次序、点击穿透、坐标与清晰度（从图层树离屏读回像素）、重画规则、叠放次序、拖拽层、帧循环、暂停、显示器变化、停止与重启、在回调里暂停或停止、对当前系统状态的判断。

交付前请了一位独立的审阅者（只读，不参与实现）对照接口约定通读实现。它指出的三个确定的缺陷——连续切换空间时可能约 10 秒没有脸、
定时帧可能提前一个节拍白出一帧、在回调里暂停或停止后仍继续作画——以及几处隐患（"电脑睡了"的标记可能卡住、不是数的时刻值让定时器空转、
大得离谱的矩形在换算时出错、没停止就释放时的残留）都已修掉，并各补了单元测试或自检项。

## 10. 待决问题

1. **用户的桌面项目平时是隐藏的。** 这决定了产品在用户自己机器上平时看不到脸。是保持"图标隐藏时脸也隐藏"（任务书的要求、现在的默认），
   还是另有打算，请用户定。它也影响其它模块的人工验证：需要用户拖动真实桌面图标的检查，得先让桌面项目显示出来。
2. **§6.3 的判断方法待确认**（§7 第 9 项）。
3. **应用自检在桌面不可见时会失败**（§2 第 2 条），需要总览改 `SmokeTest`。
4. **15% 的目标与"每张脸 0.3 毫秒"的预算对不上**（§4.2），需要总览在表情、情绪两个模块的任务里定一个办法。
5. **要不要做"共享显存表面"的优化**（§4.2 末尾）：能省叠加层自身开销的一半左右，但必须亮着屏肉眼验证。
6. **接口方面没有需要改的地方。** "每张脸的画布留多大"接口约定已经有了（`OverlayItem.outsets`，由表情模块给出、成档稳定），够用。
