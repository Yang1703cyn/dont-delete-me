## 1. 环境

| 项目 | 要求 / 现状 |
|---|---|

## 2. 常用命令

都在工程根目录 `别删我/` 下执行。

| 要做什么 | 命令 |
|---|---|
| 编译全部 | `swift build` |
| 跑全部测试 | `scripts/test.sh`（就是 `swift test`，外加偶发毛病时自动重跑，见 §6.4） |
| 只跑某个模块的测试 | `scripts/test.sh --filter FacesTests` |
| 跑某个模块的演示程序 | `swift run FacesDemo`（另有 `IconBridgeDemo` `OverlayDemo` `InputSenseDemo` `EmotionDemo`） |
| 直接运行应用（不打包） | `swift run DontDeleteMe` |
| 应用自检（自动走一遍并退出） | `swift run DontDeleteMe --smoke-test 3` |
| 打包成 .app | `scripts/build-app.sh` → `build/DontDeleteMe.app` |
| **交付前一键自检** | `scripts/check.sh`（只查自己的模块：`scripts/check.sh Faces`） |

`scripts/check.sh` 依次检查：编译无警告 → 模块依赖规则 → 测试全部通过 → 每个演示程序都能启动并自己正常结束。
**每个子对话交付前都应该跑一遍，全部通过才算数。**

## 4. 模块依赖规则

```
DDMCore  ◀──  IconBridge / Overlay / Faces / InputSense / Emotion  ◀──  DontDeleteMe
```

- 五个功能模块**只能 `import DDMCore`**（以及系统框架），彼此不能互相 `import`。
- 只有 `DontDeleteMe` 把它们接起来。
- 每个演示程序、每个测试目标只依赖 DDMCore 和它自己的模块。
- `Emotion` 是纯逻辑：不能 `import AppKit / Cocoa / SwiftUI / QuartzCore`（`Foundation`、`CoreGraphics` 可以）。
- 零第三方依赖。

这些规则有三道把关：

1. `Package.swift` 里按此声明了每个目标的依赖；
2. 构建引擎发现"`import` 了没声明的模块"会给出警告（`'Emotion' is missing a dependency on 'Faces' …`），而 `scripts/check.sh` 把任何警告都算作不通过；
3. `scripts/check.sh` 还会再扫一遍源码里的 `import`（"Emotion 不依赖 AppKit"这一条只能靠它）。

想让第 2 条直接变成编译错误，可以用 `swift build --explicit-target-dependency-import-check error`。

## 5. 怎么把占位实现换成真的

每个功能模块的目录里现在有一个最小占位实现，文件顶部写着"占位，由 <代号> 子对话替换"。接手时：

1. 先读 [接口约定.md](接口约定.md) 里和自己有关的几节（§0.3 有对照表）。
2. 在自己的目录里实现协议。文件怎么拆、内部类型怎么命名都随意，**但保留模块入口的类型名和构造方式**（接口约定 §11），这样应用入口不用改。
3. 把占位文件顶部的"占位"说明删掉或改成正式说明。占位测试、占位演示同理，换成真的。
4. 跑 `scripts/check.sh`。
5. 接口不够用：不要自己改 DDMCore，按接口约定 §12.2 提出。

## 6. 测试

### 6.1 结论：用 Swift Testing，不用 XCTest

在这台只有 CommandLineTools 的机器上实测：

| 框架 | 结果 |
|---|---|
| **Swift Testing**（`import Testing`） | **可用**。`swift test` 能编译、能运行、能正确报告通过与失败 |
| XCTest（`import XCTest`） | **不可用**。CommandLineTools 不带 XCTest，编译时报 `unable to resolve module dependency: 'XCTest'` |

所以全工程统一用 Swift Testing。不要写 `import XCTest`——有一个文件这样写，`swift test` 就整个编译不过。

### 6.2 怎么写

测试文件放在 `Tests/<模块名>Tests/`，文件名随意。示范见 `Tests/DDMCoreTests/CoordinateTests.swift`。

```swift
import CoreGraphics
import DDMCore
import Testing
@testable import Faces          // @testable：可以访问模块里 internal 的东西

@Suite("害怕的表情")            // 可选：把一组测试归到一起
struct ScaredFaceTests {
    @Test func 害怕程度越高瞳孔越小() {       // 函数名可以用中文，报告里好认
        let small = pupilRadius(fear: 0.9)
        let large = pupilRadius(fear: 0.1)
        #expect(small < large)               // 断言
    }

    @Test(arguments: [32, 64, 128])          // 参数化：每个参数各跑一遍
    func 各种图标大小都能画(size: Int) throws {
        let context = try #require(makeContext(size))   // #require：不满足就中止这个测试
        // …
    }
}
```

要点：

- **需要主线程的测试**（碰 `@MainActor` 的类型，例如图标提供者、叠加层、交互感知）：在函数或整个 `@Suite` 上加 `@MainActor`。
- **时间靠传入，不靠等待**：逻辑测试自己造 `FrameTime(monotonic:wallClock:)`，用 `time.advanced(by:)` 往后推。不要 `sleep`，不要读真实时钟。
- **随机数靠种子**：用 `SeededRandom(seed:)`，不用全局随机数。
- **不碰真实桌面**：单元测试只用编造的图标数据（`DesktopIcon(id: IconID(rawValue: 1), …)`）。需要真实系统配合的验证放到演示程序里，或写进各模块的人工检查清单。
- **不输出用户的文件名**，测试的输出和断言信息里都不要有。
- **写入类测试只用自己新建的临时文件**，用完清理。
- 暂停开关：测试里 `PauseSwitch()` 新建一个，不要动 `PauseSwitch.shared`。
- 想验证"画得对不对"，可以画到离屏位图上再读像素——写法见 `Tests/DDMCoreTests/DocExampleTests.swift` 里的 `makeCanvas` 和 `alpha(of:pixelX:pixelY:)`。

### 6.3 怎么跑

```bash
scripts/test.sh                              # 全部
scripts/test.sh --filter FacesTests          # 只跑 Faces 模块的测试
scripts/test.sh --filter 害怕                # 只跑函数名（或所在类型名）里带"害怕"的测试
```

`--filter` 按"测试目标名 / 类型名 / 函数名"匹配；`@Suite("…")`、`@Test("…")` 里写的显示名不参与匹配。

`scripts/test.sh` 就是 `swift test`（参数原样传过去），只多做一件事：遇到 §6.4 说的偶发毛病时自动重跑。直接用 `swift test` 也完全可以。

输出里每个测试目标各有一段，以这样一行收尾：

```
✔ Test run with 17 tests in 2 suites passed after 0.004 seconds.
```

有失败时对应行以 `✘` 开头，并且 `swift test` 的退出码不为 0。

### 6.4 已知的小毛病

- **偶发的宏插件报错（已绕开）**：Swift 6.4 的构建引擎在并行编译测试目标时，偶尔会漏给编译器传"测试宏插件"，于是随机报

  ```
  external macro implementation type 'TestingMacros.TestDeclarationMacro' could not be found for macro 'Test';
  plugin for module 'TestingMacros' not found
  ```

  与代码无关。实测不做处理时约四分之一的测试编译会中招（21 次里 5 次），原样重跑又好了。
  现在有两道保险：`Package.swift` 里给所有测试目标点名加载了这个插件（`testSettings`，加上之后连续 22 次重新编译测试无一失败）；
  `scripts/test.sh` 万一还是遇到，会自动重跑。**如果你仍然看到这个报错，重跑一次即可，不必改代码。**
- 不要加 `--build-system native`：旧的构建引擎已被弃用，而且找不到 `Testing` 模块。
- `swift build` 不编译测试目标；测试代码的编译错误要到 `swift test` / `scripts/test.sh` 才会出现。

## 7. 演示程序

每个功能模块有一个可以单独运行的小程序，在 `Demos/<模块名>Demo/main.swift`，用来在不启动整个应用的情况下看自己模块的效果。

```bash
swift run FacesDemo                 # 编译并运行
swift run FacesDemo --某个参数       # 参数直接跟在后面
```

约定：

- 只依赖 DDMCore 和自己的模块（`Package.swift` 里已经这样声明）。可以拆成多个文件，都放在自己的 `Demos/<模块名>Demo/` 里。
- **必须能自己正常结束**：限时自动退出（各模块提示词里有具体上限），退出码为 0。`scripts/check.sh` 会不带参数地运行每个演示程序并等它结束，超过 180 秒会强行结束并判失败。
  需要长时间交互的玩法（例如 faces 的试玩窗口）请做成带参数才进入的模式，不带参数时跑一段限时的自动演示。
- `main.swift` 的顶层代码运行在主线程上，可以直接使用 `@MainActor` 的类型。需要让主线程"转一会儿"等异步结果时：
  `RunLoop.main.run(until: Date().addingTimeInterval(0.3))`。
- 需要开窗口的演示：自己建 `NSApplication.shared`，`setActivationPolicy(.regular)`，到时间调 `NSApp.terminate(nil)`。
- 输出里不要有用户的文件名、窗口标题。
- 结束后不留残余的进程和窗口。

## 8. Swift 6 并发：常见写法

工程用 Swift 6 语言模式，线程约定（接口约定 §8）由编译器把关。碰到并发相关的编译错误，多半是下面几种情况：

**定时器、通知的回调里要回到主线程的状态**——回调本身就在主线程，但编译器不知道，用 `MainActor.assumeIsolated`：

```swift
let timer = Timer(timeInterval: 0.1, repeats: false) { [weak self] _ in
    MainActor.assumeIsolated { self?.tick() }
}
RunLoop.main.add(timer, forMode: .common)     // .common：菜单展开、拖动期间也照常触发
```

**慢的事情放后台，做完回主线程**：

```swift
Task.detached(priority: .utility) { [weak self] in
    let result = MyProvider.slowRead()                 // 后台
    await self?.publish(result)                        // 回主线程（publish 是 @MainActor 类的方法）
}
```

注意：`@MainActor` 的类里，静态方法默认也被隔离在主线程。要在后台跑的函数（上面的 `slowRead`）必须标 `nonisolated`，
否则"后台读取"实际上会回到主线程去做。完整可编译的例子见接口约定 §2.8。

**跨线程只传值类型**：DDMCore 的数据类型都是 `Sendable`，可以随意传。`NSAppleScript`、`CGContext`、`NSImage` 这类系统对象不是，
在哪个线程创建就在哪个线程用完，不要带着它们跨线程。

**`@unchecked Sendable` 尽量不用**；确实要用，写清楚是靠什么保证安全的（例如一把锁）。

**顶层代码**（`main.swift`）和 `@MainActor` 的类、测试函数里可以直接调用 `@MainActor` 的接口。

## 9. 应用外壳与打包

### 9.1 应用外壳

- 菜单栏应用，不出现在程序坞（`LSUIElement` + `.accessory`）。
- 菜单项只有两个：「暂停 / 继续」「退出」。暂停时写全局开关 `PauseSwitch.shared`，菜单栏图标变淡。
- 显示名：中文系统「别删我」，英文系统 Don't Delete Me；可执行文件和 .app 的文件名是 `DontDeleteMe`。
- 界面文案和权限说明有简体中文、英文两份，在 `Sources/DontDeleteMe/Resources/` 的 `zh-Hans.lproj`、`en.lproj` 里；其它语言的系统显示英文。
- `Info.plist` 只有一条权限说明：控制访达（`NSAppleEventsUsageDescription`）。应用自己不读桌面文件夹，所以没有"访问桌面文件夹"的说明。

应用入口的几个文件（`Sources/DontDeleteMe/`）：

| 文件 | 作用 |
|---|---|
| `main.swift` | 入口 |
| `AppDelegate.swift` | 启动时建菜单栏图标、装配并启动帧流水线 |
| `StatusMenuController.swift` | 菜单栏图标和菜单 |
| `Assembly.swift` | **唯一**写明"每个模块具体用哪个类型"的地方 |
| `FramePipeline.swift` | 帧流水线：按接口约定把各模块接成一条数据流 |
| `SmokeTest.swift`、`LaunchOptions.swift` | 自检模式 |
| `L10n.swift` | 界面文案 |

### 9.2 两种运行方式的区别

| | `swift run DontDeleteMe` | `build/DontDeleteMe.app` |
|---|---|---|
| 用途 | 改代码时快速看一眼 | 接近用户实际拿到的样子 |
| `Info.plist`、本地化文案 | 没有（界面文案落到代码里的中文默认值） | 有 |
| 系统授权（控制访达） | 没有自己的身份：授权弹窗会算在启动它的终端程序头上，也没有我们的权限说明 | 以应用自己的身份申请，弹窗里显示我们的权限说明 |

**凡是涉及向访达发请求、授权弹窗的验证，都要用打包后的 .app。**

### 9.3 自检模式

```bash
swift run DontDeleteMe --smoke-test 3
# 或者对打包后的应用（--stdout 把输出存到文件里，-W 等它退出）：
open -n -W --stdout /tmp/ddm-smoke.txt build/DontDeleteMe.app --args --smoke-test 6
```

应用照常启动，然后自动：确认菜单栏图标和两个菜单项都在、图标被系统摆在了某块屏顶部的菜单栏区域里
→ 走菜单项背后的同一个动作把"暂停 → 继续"过一遍，确认暂停期间不出帧、继续后恢复 → 打印报告
→ 走「退出」背后的同一个动作正常退出。
最后一行有三种（用 `open` 启动时，`open` 自己的退出码总是 0，要看输出文件的最后一行）：

| 最后一行 | 含义 | 退出码 |
|---|---|---|
| `smoke-test: PASS` | 全部验证过，全部通过 | 0 |
| `smoke-test: PASS-LIMITED` | 验证得了的都通过了，但**桌面看不见**（锁屏、熄屏、停在全屏空间、系统隐藏了桌面图标）。应用按约定一帧不出，所以"出帧、图标上报"这半边没有验证 | 0 |
| `smoke-test: FAIL` | 有没通过的项，逐条列在前面 | 1 |

桌面看不见时也想把整条流水线跑一遍（例如没人在场、机器锁着屏），加 `--assume-visible`：
`swift run DontDeleteMe --smoke-test 4 --assume-visible`。它让叠加层不管看不看得见都照常建窗出帧，
**只在自检模式下起作用**，输出里会注明；这时"看不见时不出帧"这一条自然就没有验证。

加 `-AppleLanguages '(en)'` 可以强制用英文界面跑一遍：
`open -n -W --stdout /tmp/ddm-smoke.txt build/DontDeleteMe.app --args -AppleLanguages '(en)' --smoke-test 3`

它替代不了肉眼检查：图标是否真的出现在菜单栏、长什么样、点开菜单的样子，仍需人看一眼。
（在 macOS 27 上，状态项的窗口不在本进程名下，用窗口列表查不到，所以没法用程序完全确认。）

### 9.4 打包

```bash
scripts/build-app.sh          # 产物：build/DontDeleteMe.app
open build/DontDeleteMe.app
```

脚本做三件事：编译发布版 → 手工组装 .app 目录结构 → 本机临时签名（ad-hoc）。不做公证，不做安装镜像。

**图标**（归 release，放在 `Assets/` 里；都是可选的，没有也不报错）：

| 文件 | 用途 | 没有时 |
|---|---|---|
| `Assets/AppIcon.icns` | 应用图标 | 用系统默认的应用图标 |
| `Assets/MenuBarIcon.pdf`（推荐，单色矢量图）<br>或 `Assets/MenuBarIcon.png` + `MenuBarIcon@2x.png`（+ `@3x`），18×18 点 | 菜单栏图标 | 用系统符号 `eyes` 占位 |

菜单栏图标会被当作**模板图**：只取形状（不透明度），颜色由系统按深色 / 浅色菜单栏决定。所以请做成单色、透明底。
不管原图多大，应用都会按比例缩到 18 点高。PDF 和 PNG 只放一种就好（两种都放时由系统挑一个）。

想试试别处的图标而不动 `Assets/`：`DDM_ASSETS_DIR=/某个目录 scripts/build-app.sh`。

**关于临时签名，整合阶段要留意：**

- 每次重新打包，应用的签名都会变。系统可能把它当成"另一个应用"，于是之前给过的"控制访达"授权不再算数，会重新弹窗。
  要清掉旧的授权记录重新来过：`tccutil reset AppleEvents io.github.dont-delete-me`。
- 临时签名的应用拿到别的电脑上会被系统拦住（没有公证）。怎么向用户说明归 release。
- 目前只编译本机架构（Apple Silicon）。要不要、能不能出同时支持 Intel 的版本，留到发布阶段。

**版本号和应用标识**都在 `Sources/DontDeleteMe/Resources/Info.plist` 里：版本 `0.1.0`，标识 `io.github.dont-delete-me`（暂定，见回报里的待决问题）。

## 10. 已知的工具链警告

`swift build` 的输出里会有若干条这样的警告：

```
ld: warning: search path '/Library/Developer/CommandLineTools/Developer/Library/Frameworks' not found
ld: warning: search path '/Library/Developer/CommandLineTools/Developer/usr/lib' not found
```

原因：Swift 6.4 的构建引擎给链接器传了两个只在完整 Xcode 里才存在的搜索路径，CommandLineTools 里没有这两个目录。
**与工程代码无关，不影响产物**；一个空的新工程在这台机器上也会报同样的警告。`scripts/check.sh` 判断"有没有警告"时会忽略这两条，其它任何警告都算不通过。

## 11. 代码约定

- 标识符（类型名、函数名、文件名）用英文；注释和文档用中文。测试函数名可以用中文。
- 公开的类型和成员写文档注释（`///`），说清含义和单位。
- 不写日志到文件。调试输出不得包含用户的文件名、窗口标题。
- 应用不联网，不读写用户的任何文件；唯一会持久化的是应用自己偏好设置里的少量数据（例如学到的废纸篓位置）。
